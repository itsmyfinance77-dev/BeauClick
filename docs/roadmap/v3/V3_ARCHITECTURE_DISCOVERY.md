## 6. WooCommerce exit analysis

Confirmed via direct trace of the Booking→Pricing→Campaign→Membership→Checkout→Order→Payment→Receipt→Ledger→Settlement→Refund→Analytics chain this task asks for, cross-referencing `V3_ARCHITECTURE_PLAN.md` §2 and `WORDPRESS_EXIT_MATRIX.md` §6:

**Booking → Pricing**: a booking never touches the WooCommerce cart at all — `BookingOrderBridge` calls `wc_create_order()` + `add_product()` directly (a deliberate structural choice, confirmed correct in `PRODUCT_GAP_REGISTER.md` COM-05).

**Pricing → Campaign/Membership**: both hook `beauclick/booking/after_create` at explicit priorities (payments 10, membership 20, campaign 30), both compute independently against the same pre-discount subtotal, never compound — real, tested, load-bearing logic (`WORDPRESS_EXIT_MATRIX.md` §6).

**Checkout → Order → Payment**: WooCommerce's native order/payment-gateway plumbing, used unmodified in its data layer, fully overridden at the template layer (only 3 real template overrides remain per §3/§5) — no real gateway ever configured (`GAP-06`).

**Payment → Receipt → Ledger**: `woocommerce_payment_complete` triggers financial's commission recording (chosen deliberately over a generic status-changed hook — precision preserved in `V3_EVENT_CATALOG.md`'s `OrderPaid`). Receipt is a read-only view over the authoritative order, never a second price calculation.

**Ledger → Settlement → Refund**: settlement records against system-computed amounts; refund reversal reuses the *original* captured commission rate, never live config; `woocommerce_order_refunded` independently triggers `RefundRecorder` (listens to the fact, not the intent — a real, deliberate discipline).

**Refund → Analytics**: campaign usage-release listens to the same order-dead hooks payments does (multiple independent consumers per hook, an established, deliberate V2 convention).

**What BeauClick actually needs, not a WooCommerce recreation**: order/cart/checkout state machine, one unified pricing-rule chain, gateway-abstracted payment, refund lifecycle, receipt presentation — all already scoped as `commerce-service`/`payment-service` in `V3_ARCHITECTURE_PLAN.md` §1/§2. **Every WooCommerce-native data shape (coupons [confirmed unused — zero `shop_coupon` rows], tax classes) is RETIRE per `V3_MIGRATION_MATRIX.md` — must not be recreated under a different name.** Decision: **ADR-001**, pricing-engine design: **ADR handled within `V3_ARCHITECTURE_PLAN.md` §2** (no separate ADR needed — already fully specified there).

## 8. Target architecture: options and recommendation

Full evaluation and decision: **ADR-002**. Summary: **Option D, Hybrid** — a modular monolith at launch, organized around the same 12 (13, with Journey) evidence-based logical boundaries from `V3_ARCHITECTURE_PLAN.md` §1, with financial-service and payment-service physically separate from day one for structural (DB-permission-boundary, PCI-adjacent) reasons, not anticipated-scale reasons. Rejected: pure single-process monolith (financial/payment's isolation need is structural, not optional), 12-services-from-day-one (disproportionate to confirmed team size and "no production dataset yet"), and finer-grained-than-12 microservices (no domain evidence supports it). The module boundaries are deliberately extraction-ready — promoting any module to its own deployable later is an infrastructure change, not a redesign, because schema-per-module and event-driven cross-module calls are already the rule.

## 13. Financial architecture

### SEO findings (closing `GAP-09`'s discovery-coverage gap)

Direct source inspection of `wordpress/wp-content/themes/beauclick/inc/seo.php` (485 lines) and `inc/sitemap.php` (151 lines) — the only two SEO-bearing files in the codebase, confirmed via `PRODUCT_GAP_REGISTER.md` SEO-01 through SEO-04 ("Resolved in V2.2 Step 12") and re-verified fresh here, line-cited:

- **`<title>` tag**: dynamic, via a `document_title_parts` filter (`seo.php:77-84`) feeding `bc_seo_title_and_description()` (`:109-190`) — city/specialty-aware for the marketplace (the architecture proposal's own flagship query, «میکاپ عروس در یزد», was confirmed unable to rank before this existed — every `/marketplace/` variant shared identical metadata until V2.2 Step 12), provider-bio-aware for professional/business profiles, product-excerpt-aware for shop. A real, since-fixed bug is documented in the file's own comments: the dynamic title fed `og:title`/meta-description correctly from the start but never the actual `<title>` element until this fix, because `add_theme_support('title-tag')` pulls from WP core's own filter chain, which nothing was feeding.
- **Meta description**: dynamic, trimmed to 30 words (`wp_trim_words`, `:88`).
- **Open Graph / Twitter**: `og:site_name`, `og:locale` (`fa_IR`), `og:type` (`article`/`website`), `og:title`, `og:description`, `og:url`, `og:image` (product thumbnail where available, else a theme gradient-icon SVG fallback — never a broken/missing image tag), `twitter:card` = `summary_large_image` (`:96-105`).
- **Canonical URLs**: explicit for every page type (WP core only auto-adds one on singular views; core's own `rel_canonical` is explicitly removed, `:58`, to prevent a real duplicate-canonical-tag bug found during V2.2 Step 12's own live verification). Marketplace canonical logic (`:282-314`) is the most sophisticated piece: a **meaningful** city/specialty combination (real IDs, a launched city, ≥1 actual matching provider — `bc_get_meaningful_marketplace_filters()`, `:215-240`, shared by the meta/canonical/robots/sitemap logic so all four always agree) gets a self-referencing canonical; anything thin, unrecognized, or zero-result collapses **up** to the plain `/marketplace/` root, never down to the homepage, never left ambiguous. A second real, since-fixed bug is documented: an earlier version's branch ordering let a generic `is_singular()` check shadow the marketplace-specific branch entirely, silently discarding every city/specialty canonical.
- **Robots**: `/dashboard/` and `/auth/` are `noindex,nofollow` (no other mechanism in the codebase protected these — WooCommerce protects its own account/cart/checkout pages, nothing protected BeauClick's own equivalents before this); a thin/zero-result marketplace filter combination is `noindex,follow` (not fully blocked — a crawler can still follow its links back to real content) (`:326-345`).
- **Structured data (JSON-LD)**: `LocalBusiness` + `Offer`/`Service` (`makesOffer`) + conditional `AggregateRating` (only when `review_count > 0` — never a fabricated default rating for a new professional, `:425-434`) on professional/business profiles; `BreadcrumbList` on profile and filtered-marketplace pages; `WebSite`+`Organization` on the homepage (`:363-376`). Explicitly never fabricates data not actually present (no invented street address — only `addressLocality`+`addressCountry`, since no street-level address is ever collected, `:406-416`). **WooCommerce's own native `Product`/`BreadcrumbList` JSON-LD on shop pages is deliberately left untouched, not duplicated** (`:7-9, 350-352`) — confirmed live by the original V2.2 Step 12 audit.
- **Sitemap**: WP core's own `wp-sitemap.xml` (WP 5.5+, active by default) already covers `bc_professional`/`bc_business` automatically since they're real `publicly_queryable` post types — `bc_service`/`bc_portfolio_item` are explicitly excluded from it as defense-in-depth (`sitemap.php:65-71`) on top of their own already-private registration. A **custom sitemap provider** (`BC_Marketplace_Sitemap_Provider`, registered on `wp_sitemaps_init` — a real, since-fixed bug is documented: hooking plain `init` instead ran too early relative to the sitemaps registry, silently falling through to the front page with no error) adds the city/specialty query-string marketplace URLs core's own walker can never discover on its own (it only walks real posts/taxonomy terms, not arbitrary parameter combinations) — bounded strictly to launched cities × specialties with ≥1 real matching provider row today (no thousands of thin/empty pages, `sitemap.php:14-30`). A second real, since-fixed bug: the provider's internal `name` must be **hyphen-free** because WP core's own sitemap rewrite regex for a provider type capture group is pure `[a-z]+` — a hyphenated first attempt (`bc-marketplace-locations`) registered successfully but its URL could never match the regex, silently falling through to the front page.
- **Marketplace URL scheme**: deliberately kept as `?city_id=`/`?specialty_id=` query-string parameters, not new pretty paths — an explicit, disclosed decision (`seo.php:20-41`) to avoid the risk of a rewrite-rule flush mistimed to plugin/theme activation (a real, easy-to-get-wrong moving part; this project's own implementation notes in `ARCHITECTURE_PROPOSAL.md` separately document a real rewrite-rules corruption incident during initial setup, corroborating that this caution was well-founded, not theoretical). This is Google-supported faceted-navigation practice given the canonical/robots/sitemap treatment layered on top — a well-reasoned V2 tradeoff, not an oversight.
- **Persian-slug behavior**: the three public CPTs use **ASCII English rewrite-slug prefixes** — `/professional/`, `/business/`, `/specialty/` (`Registrar.php:42,60,112`) — confirmed by direct inspection, not assumption. The individual post slug after that prefix (`post_name`, auto-derived by WordPress core from each profile's Persian title via `sanitize_title()`) was **not independently re-verified against a live-rendered URL in this pass** — WordPress core does not transliterate Persian/Arabic script to Latin by default, so the real-world behavior (a percent-encoded UTF-8 slug vs. a numeric-ID fallback) needs a live check, not a code-reading assumption; flagged here as an open verification item rather than claimed either way.

**V3 portability**: the *rules* (title/description generation logic per page type, the "collapse thin combinations up, never fabricate structured data, always agree across meta/canonical/robots/sitemap" discipline, the query-string-faceted-navigation pattern) are cleanly portable business/product logic — genuinely reusable in a V3 SSR/SSG frontend regardless of framework. The *mechanism* (`wp_head` hooks, `document_title_parts` filter, `WP_Sitemaps_Provider` subclassing, WP's rewrite-rule system) is 100% WordPress-specific and must be rebuilt entirely against whatever SSR/SSG solution V3's frontend adopts (e.g. Next.js `generateMetadata`/`sitemap.ts` equivalents) — classified **BUSINESS-RULE EXTRACTION** per the `V3_MIGRATION_MATRIX.md` taxonomy, joining the rest of that document's classifications (this pass's SEO section was the one domain missing from it — see `V3_MIGRATION_PLAN.md` §3 row, now filled in).

**Open product/technical decision surfaced, not resolved by this discovery**: whether V3's frontend rebuild should finally introduce pretty city/specialty paths (V2's own stated reason to avoid them — WordPress rewrite-flush timing risk — does not exist in a Next.js-class router) is a real design choice for the frontend-strategy phase, not decided here.

## 17. Frontend strategy

**Reusable, confirmed by this pass's own inspection of `app/src`**: design tokens (`shared/design-tokens.json`, already framework-agnostic JSON), design-system primitives (`app/src/design-system/primitives`, zero WP/REST coupling), Jalali calendar math + Persian formatting (`app/src/lib/jalali.ts`/`format.ts`, pure functions, already unit-tested), RTL enforcement pattern (CSS logical properties throughout). 11 feature modules exist (`ai, auth, booking, cart, chat, dashboard, journey, notifications, privacy, reviews, search`) — UI/UX mostly survives per-feature; the data-fetching layer (`api.ts`) needs a real rewrite (WP-nonce/cookie auth → JWT, envelope/error-hygiene pattern carries over) per `V3_MIGRATION_MATRIX.md`'s Frontend section.

**Needs rewrite**: routing (currently no real top-level router — PHP template hierarchy does that job; a real SPA/SSR router is needed once WordPress's routing is gone), state (Zustand per-surface pattern is fine to keep as a *pattern*, but store composition needs revisiting once there's real client-side routing), the API layer (`api.ts` rewritten for JWT; `storeApi.ts`, the WooCommerce Store API wrapper, dropped wholesale), and — the one V2-specific mechanism with **no V3 equivalent, DROP not port** — the mount-point architecture (`data-bc-*-trigger` + delegated click listeners, confirmed present: `app/src/mounts/` has 11 files, one per feature, exactly matching this pattern), purpose-built solely for "React islands inside PHP pages that must work without React." A real SPA/Next.js-class app owns routing/composition directly and has no PHP template to signal into.

## 18. AI architecture

Full design: `V3_MIGRATION_MATRIX.md` (AI domain — provider abstraction, two-stage authorization/curation, output-validation, all DIRECT REUSE *patterns*; one-thread-per-tenant limitation flagged **revisit, don't re-adopt**, `GAP-12`), `V3_SECURITY_MODEL.md` §5 (the concrete architecture satisfying "AI must never receive unrestricted database access"). Confirmed by this pass's own file inspection: `beauclick-ai`'s structure (`ProviderInterface`, `ProviderFactory`, `AnthropicProvider`, `RuleBasedProvider`, mirrored exactly for the professional variant under `Professional/`) is the clearest "this generalizes" evidence in the whole codebase — the identical shape built three times independently (SMS, customer-AI, professional-AI) is exactly what ADR-003's shared provider package formalizes. Beauty Journey's `JourneyContextProvider` (§4, `GAP-29`) is this pass's one addition to the AI picture: a real, narrow, already-correctly-curated (notes field deliberately excluded) context seam that should be designed into ai-service's context-assembly stage from the start, not bolted on after the fact.
