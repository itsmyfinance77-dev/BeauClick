## 4. Detail — every open item

Format per item: current implementation state (verified), evidence, the four impact

### R31-01 · Privileged roles are ungrantable; the entire admin API is unreachable · **NEW · HIGH**

- **Domain:** Identity / Admin · **Status:** OPEN · **Type:** PRODUCT GAP / OPERATIONAL
- **Current implementation state.** `AccountResolverService.resolveOrCreate()`
  (`services/identity/src/account/account-resolver.service.ts:34`) creates every user with
  `roles: ['customer']`. A repo-wide grep for any write to `roles` after creation returns
  **nothing**: `MeController.updateMe` touches `displayName` only, and no other service,
  controller, migration, or seed writes the column. `database/seeds/` contains one file,
  `reference-data.seed.ts` (cities and specialties).
- **Evidence.** `CAPABILITIES_BY_ROLE` (`services/identity/src/rbac/capabilities.ts`)
  grants `bc_manage_platform` only to `platform_operator` and `administrator`,
  `bc_moderate_verification`/`bc_moderate_reviews` only to `moderator` and
  `administrator`. Five admin controller groups exist and every route is
  `@RequireCapability('bc_manage_platform')`: `/v1/admin/analytics`, `/v1/admin/finance`,
  `/v1/admin/loyalty`, `/v1/admin/notifications`, `/v1/admin/search`.
- **What is actually unreachable.** Platform analytics; cross-party financial totals;
  settlement creation and settlement **reversal**; loyalty policy inspection (the endpoint
  `GAP-10` relies on to make provisional values visible); notification delivery status and
  retry-due; search **reindex** and **rebuild-projection** — i.e. the only recovery path
  for a corrupted or stale search index.
- **User impact.** None directly; this is invisible to customers until something needs
  operating.
- **Security impact.** Neutral-to-positive today (nothing over-privileged exists), but the
  eventual fix creates the platform's first privileged principal and must be designed as
  such — audit-logged, least-privilege (`platform_operator` by default, per
  `V3_SECURITY_MODEL.md` §9), and never a static seeded superuser.
- **Revenue impact.** Settlement cannot be run, so professionals cannot be paid out
  through any product path.
- **Operational impact.** **Total.** The platform cannot be administered at all except by
  hand-editing `identity.users.roles` in the database. That is the definition of an
  unoperable system.
- **Dependencies.** None upstream. Blocks: Admin UI, review moderation, R31-02, QA-25,
  GAP-20, GAP-24.
- **Complexity.** M. Either build `identity.roles`/`identity.capabilities` per
  `V3_DATABASE_BLUEPRINT.md` §8, or ship a narrower grant path plus a bootstrap
  mechanism. The register has flagged the code-based simplification since Phase 1; this
  finding is that the simplification has a consequence nobody costed.
- **Phase:** A.

### R31-02 · Verification workflow has no caller; the `verified` signal is inert · **NEW · MEDIUM-HIGH**

- **Domain:** Provider / Search · **Status:** OPEN · **Type:** PRODUCT GAP
- **Current implementation state.** `ProviderService.transitionVerification()`
  (`services/provider/src/provider.service.ts:141`) is a complete, CAS-hardened,
  event-emitting state machine. Its only callers in the entire workspace are four lines in
  `apps/api/test/search-projection.pg-spec.ts`. `ProviderController` exposes six routes;
  none of them is a verification route. There is no `verification_requests`,
  `verification_evidence`, or `verification_history` table — `V3_DOMAIN_BOUNDARIES.md`
  §provider names all three.
- **Consequence.** Every professional is `unverified` permanently.
  `SearchProvidersDto.verifiedOnly` therefore matches nothing;
  `RankingConfig.WEIGHT_VERIFIED * verified` is always `0`; the `verified` badge is never
  awarded. This is structurally identical to **QA-18** (rating signals with no writer) and
  was never recorded — the QA pass found the rating half and not this one.
- **User impact.** Customers get no trust signal at all in a marketplace where trust is
  the purchase decision. Two of the five ranking badge keys are unreachable, so ranking is
  flatter than designed.
- **Security impact.** None directly. Indirect: an unverified-by-default marketplace with
  no verification path means nobody has checked that a listed professional is real.
- **Revenue impact.** Medium — verification is a standard conversion lever and a standard
  premium/priority-placement lever.
- **Operational impact.** High — there is no moderation queue, so the platform cannot
  perform its own core supply-side quality control.
- **Dependencies.** R31-01 (needs `bc_moderate_verification` to be grantable);
  R31-03 (evidence upload needs object storage).
- **Complexity.** M — routes, request/evidence tables, a moderation queue, and the admin
  screen. The state machine and its event already exist and are tested.
- **Phase:** A.

### R31-03 · No file upload or object storage capability exists anywhere · **NEW · HIGH (prerequisite)**

- **Domain:** Infrastructure · **Status:** OPEN · **Type:** PRODUCT GAP
- **Current implementation state.** A repo-wide search of `v3/` for `S3`, `multer`,
  `presign`, and `upload` returns **zero** matches outside `node_modules`. There is no
  `public/` directory in `apps/web`. `V3_IMPLEMENTATION_ROADMAP.md` Phase 1 listed
  *"Object storage wired for portfolio media + verification evidence"* as a deliverable;
  it was never built and no phase report records dropping it.
  `V3_INFRASTRUCTURE_PLAN.md` §5 names an S3-compatible, Iran-reachable provider as the
  strategy, with no provider chosen.
- **User impact.** Indirect but total: it is why the product has zero images (§IMAGERY).
- **Security impact.** Designing this is where the protected-file model in
  `V3_SECURITY_MODEL.md` §8 has to become real — verification evidence is sensitive
  personal documentation and must never be publicly addressable, including after a
  backup restore (`V3_INFRASTRUCTURE_PLAN.md` §9).
- **Revenue impact.** High, via IMAGERY — a beauty marketplace where customers cannot see
  work is not competitive.
- **Operational impact.** Medium — media lifecycle, quota, and abuse handling are new
  operational surfaces.
- **Dependencies.** Hosting/region decision (`HOSTING`) — provider choice is downstream of
  it. Blocks: GAP-23 (Portfolio), IMAGERY, R31-02's evidence upload.
- **Complexity.** M for the adapter + presigned-upload path + validation; the abuse,
  quota, and moderation policy around it is where the real cost is.
- **Phase:** C, and it is the gate for the whole phase.

### R31-04 · `EXC-001` does not cover `v3.0.1` and does not extend to `v3.1.x` · **NEW · MEDIUM**

- **Domain:** Release process · **Status:** OPEN · **Type:** BUSINESS DECISION
- **Current implementation state.** `V3_RELEASE_POLICY_EXCEPTIONS.md` states EXC-001
  "Applies to: The `v3.0.0` release only", and its Review condition fires when *"any
  subsequent release (`v3.0.x`, `v3.1.0`, …) is proposed while GAP-06b is still open — the
  exception covers `v3.0.0` **only** and does not automatically extend to successors."*
  The `v3.0.1` tag message records `EXC-001 = STILL ACTIVE, unchanged and unextended`.
- **Reading it honestly.** That sentence is accurate about EXC-001 and, read together with
  the exception's own scope clause, means `v3.0.1` was released **without a covering
  release exception**. Nothing harmful followed — `v3.0.1` changes no payment behaviour and
  the production gate still fails closed — but the exception index no longer describes the
  release history, and the same condition will fire again, more consequentially, at
  `v3.1.0`.
- **Impact.** No user, security, or revenue impact. Operational/governance impact only:
  the document that exists specifically to prevent silent policy drift has drifted.
- **Dependencies.** None. Resolution is a decision, not engineering: either record
  `EXC-002` covering the `v3.0.x`/`v3.1.x` line, or re-scope EXC-001 with an explicit,
  dated amendment. **Do not let it lapse by convention** — that is the exact failure mode
  the document forbids.
- **Complexity.** XS.
- **Phase:** F, but it must be settled *before* any V3.1 tag is cut, not with the gateway.

### R31-05 · `identity` schema missing four specified tables · **NEW · INFORMATIONAL**

`identity` has `users`, `otp_requests`, `refresh_tokens`, `phone_conflicts`.
`V3_DOMAIN_BOUNDARIES.md` §identity also names `roles`, `capabilities`,
`sessions`/`refresh_tokens`, and `business_account_approvals`. The first two are R31-01's
landing site. `sessions` is partially covered by `refresh_tokens` (and its absence is why
QA-20 cannot be fixed without a JWT claim). `business_account_approvals` is unnecessary
under ADR-023, which resolves business ownership by row rather than by an approval
workflow — recorded so the divergence is deliberate rather than forgotten. **Phase A.**

### R31-06 · Four fully-specified domains have no schema or module · **NEW · INFORMATIONAL**

`referral`, `ai`, `admin` (`admin_audit_log`), and `privacy` (`data_requests`) each have a
complete responsibility, schema, API, event, and data-ownership specification in
`V3_DOMAIN_BOUNDARIES.md` and **zero** implementation. This is not a defect — none was in
any delivered phase's scope — but it means four of the fourteen designed domains are
absent, and the design work for each is already done and does not need repeating. See
`V3.1_PRODUCT_ROADMAP.md` §21 for the reuse assessment.

### R31-07 · No campaign/promotion domain exists in V3 · **NEW · MEDIUM · supersedes GAP-04 and GAP-19**

- **Current implementation state.** `commerce` has `orders`, `order_items`,
  `order_adjustments`, `outbox_events`. There is no `campaigns`, `campaign_usages`, or
  `b2b_price_tiers` table. `PricingService` takes an injected `PRICING_RULES` array and
  exactly one rule is registered anywhere: `apps/api/src/pricing/membership-discount.rule.ts`.
  Every other "Campaign" mention in `v3/` is a comment describing the design.
- **Why this is a re-classification.** GAP-04 describes a confirmed TOCTOU race in V2's
  `CampaignService`. GAP-19 describes B2B orders being excluded from campaign eligibility.
  Both have been carried through every V3 phase addendum as OPEN. Neither can be true of
  V3, which has no campaign code. Continuing to list them as open V3 gaps overstates V3's
  risk surface and understates its **scope** gap.
- **The real question,** which is a business one: does V3 want promotional pricing at all,
  and if so is it a launch capability or a growth-phase one? V2 had it, V3 dropped it
  silently, and no document records the decision.
- **Impact.** Revenue/marketing capability absent; no security or integrity risk (there is
  nothing to exploit). The pricing chain was explicitly designed to accept it additively.
- **Complexity.** L. **Phase:** V3.2+, pending the business answer.

### GAP-06b · No real production payment gateway · **OPEN / EXTERNAL · PRODUCTION-BLOCKING**

Unchanged in substance and re-verified: `PAYMENT_DEFAULT_PROVIDER=sandbox`,
`PAYMENT_ENVIRONMENT=sandbox`, `SandboxPaymentProvider` the only registered provider, no
merchant credential of any kind in `.env` or `.env.example`, no adapter file. The
production gate is two independent conditions with no override, re-read and confirmed.
**Revenue impact: absolute — no real money can move.** User impact: none today (nothing is
deployed). Security impact: currently positive (fail-closed). Operational impact: blocks
launch entirely. Dependencies: real merchant credentials (external), the hosting decision
(callback reachability), and the `failureCode` redirect-contract change QA-21 needs — all
three should be settled in one pass, not three. Complexity: XL, externally gated.
**Phase F.** `QA-10` has already reduced its risk surface by making the amount check
currency-aware before an adapter exists; that was the right order.

### HOSTING_GRANTS · Ledger role contract proven only against CI · **EXTERNAL · EVIDENCE-GATED · HIGH**

`database/scripts/financial-roles.sql` has been verified only against CI's ephemeral
PostgreSQL 16 container. `PHASE4-03` (PostgreSQL 15+ revokes the default `CREATE ON SCHEMA
public` grant) is a live consideration on any managed provider. Both are one action:
provision the real target host and run the script. **This is a deployment prerequisite of
equal standing to GAP-06b** and should not be discovered on launch day. Complexity S once
a host exists; blocked on `HOSTING`. **Phase F.**

### HOSTING · The hosting/region decision has never been made · **OPEN · BUSINESS DECISION · HIGH**

`V3_INFRASTRUCTURE_PLAN.md` §1 calls this *"the one deliberately open item in this entire
blueprint"* and *"a Phase 0 exit blocker"*. Phase 0 exited, five phases shipped, and two
releases were cut without it. It is coupled to three other decisions and must be resolved
as one: AI-provider reachability, payment-gateway callback reachability, and object-storage
provider (R31-03). **This is the single highest-leverage unresolved decision in the
project** — four separate V3.1 items are downstream of it. Complexity: a decision, not
work. **Phase F, but it should be started on day one of V3.1, not at F.**

### PRO-UI · No professional-specific frontend · **OPEN · HIGH**

- **Current implementation state, measured.** The web app consumes 24 distinct API paths.
  The API exposes far more. Endpoints that are **built, tested, and gated but have no UI
  at all**: `GET/POST/DELETE /v1/me/availability/slots`, `/slots/bulk`,
  `GET /v1/me/professional-bookings`, `POST /v1/bookings/:id/complete`, `/no-show`,
  `/reschedule`, `GET /v1/bookings/:id/history`, `POST /v1/providers` (create profile),
  `PATCH /v1/providers/:id`, `POST /v1/providers/:id/services`, all of
  `/v1/me/finance/*` (summary, outstanding orders, settlements, per-order ledger), all of
  `/v1/me/analytics/*`, `/v1/me/loyalty/tiers`, `/v1/me/loyalty/membership`,
  `GET /v1/auth/sessions`, `POST /v1/auth/logout-all-devices`, and every `/v1/admin/*`
  route.
- **What that means concretely.** A professional cannot, through the product: create or
  edit their profile, publish availability, list their own bookings, mark a booking
  complete or no-show, reschedule, see what they have earned, or see any analytics.
  `/dashboard` is a three-field shared identity page.
- **User impact.** The supply side of a two-sided marketplace cannot operate. This is the
  largest single gap in the product.
- **Revenue impact.** Direct — no completed bookings means no commission, and completion
  is a professional action with no UI.
- **Operational impact.** Every professional interaction would have to be performed by
  support on their behalf, which is not possible either (R31-01).
- **Dependencies.** None on the backend — this is the rare item where the expensive half
  is already built, tested against real PostgreSQL, and secured with ownership resolvers.
  Benefits from G (UI kit) running alongside.
- **Complexity.** L, but low-risk: no new API, no migration, no new security surface.
- **Phase:** B. **This is the highest value-per-unit-of-risk work in the entire plan.**

### ADMIN-UI · No admin frontend · **OPEN · HIGH**

Zero admin pages. The API half exists and is correctly gated on every route (verified by
enumerating all seventeen controllers). Minimum operational set, in the order
`V3_IMPLEMENTATION_ROADMAP.md` Phase 4 itself recommends under time pressure:
**verification queue** (R31-02), **role/capability management** (R31-01), **audit log
viewer** (GAP-02-V3), **financial settlement + reversal**, **search reindex / index
health**, **notification delivery status**, **phone-conflict resolution** (GAP-20),
**loyalty policy** (GAP-10 visibility). Deliberately *not* minimum: ranking-weight tuning
(GAP-24), review moderation (needs D), user impersonation (never). Complexity L.
**Phase A.**

### REVIEWS · No review domain exists · **OPEN · HIGH**

No entity, no table, no write path, no `ReviewCreated` contract in
`libs/event-contracts/src/catalog/`. `booking.service.ts:383` still describes reviews as
something *"later phases … will consume"*. `bc_moderate_reviews` exists as a capability
with nothing behind it. `V3_DOMAIN_BOUNDARIES.md` places reviews in the `provider` schema
with a `ReviewCreated` v1 event consumed by search and loyalty — that design is done.
User impact: customers have no quality signal and no voice; professionals have no
reputation asset. Revenue: reviews are the primary conversion driver in this category.
Dependencies: `BookingCompleted` (exists), moderation capability (A), professional
response UI (B). Complexity L. **Phase D.** Closes QA-18 as a consequence, and makes
`LOYALTY_POINTS_REVIEW_SUBMITTED` (already configured at 5) meaningful.

### QA-18 · Rating signals have no writer · **OPEN · MEDIUM**

`search.ranking_signals.rating_sum` / `.review_count` are written by nothing; the
migration says so in a comment. `ratingAvg` is permanently 0, `high_rating` unreachable,
the Bayesian term always collapses to cold-start. Blast radius limited today because the
frontend exposes neither `minRating` nor the `rating` sort. **The fix is a consumer, not a
feature** — an S-sized signal writer on `ReviewCreated`, using the existing
`search.signal_applications` idempotency table. **Phase D**, bundled with REVIEWS.

### GAP-22 / GAP-21 · Privacy: no export, no deletion, no anonymization, no cooldown · **OPEN · HIGH / LEGAL**

Verified absent: no export endpoint, no deletion endpoint, no anonymization path.
`identity.users.deletedAt` exists as a column and **nothing ever sets it**.
`confirm_deletion` exists only as an OTP purpose. `V3_DOMAIN_BOUNDARIES.md` specifies the
correct design — a thin `privacy` orchestrator calling each module's own self-registered
`exportSubjectData(userId)` / `eraseSubjectData(userId)`, which closes V2's `PRIV-06`
hardcoded-call-list blind spot by construction. Fourteen domains own user data; a
hand-maintained list would go stale immediately, so the self-registration property is the
whole design and must not be traded away for speed. GAP-21 (deletion grace period) is a
**business decision** riding on the same work. User impact: users cannot get their data
or leave. Security: erasure is also a breach-blast-radius control. **Legal: this is the
item with actual regulatory weight, and it is not currently on anyone's critical path.**
Complexity L. **Phase E.**

### GAP-02-V3 · Audit logging is logger-based, not DB-persisted or structurally enforced · **OPEN · MEDIUM**

V2's `GAP-02` was closed by a boot-time route-registration guard that made an unaudited
admin mutation impossible to register. V3 has no equivalent: `AuditLogService` writes to
the structured logger, there is no `admin.admin_audit_log` table, and nothing prevents a
new admin route from shipping unaudited. `V3_DOMAIN_BOUNDARIES.md` specifies the
structural contract (`libs/audit`, every mutation-capable controller must call
`AuditLog.record` or fail to register). The gap register calls this the "recurring bug
class, not a one-off" — three separate instances in V2 across two plugins. Building the
admin UI (A) without this rebuilds the conditions for the fourth. Security/data-integrity
impact: an unauditable privileged action is unattributable. Complexity M. **Phase A —
same phase as the first privileged principal, deliberately.**

### QA-17 · Vazirmatn named but never shipped · **OPEN · MEDIUM · BUSINESS DECISION**

`--bc-font-family: 'Vazirmatn', …` with no `@font-face`, no `next/font`, no font file, no
`public/`. Every user without it locally installed gets a Latin-first system fallback on
every screen of a Persian-only product. The UI/UX audit's #1 recommendation and its own
words: *"the one finding here that affects literally every pixel of Persian text."* The
blocker is a decision — self-host (~100KB+ per weight, into repo and build) vs CDN (an
external origin with genuine availability problems for an Iranian audience). Prior
recommendation, which this pass endorses: **self-host a Latin+Arabic subset at 400/600/700
via `next/font/local`.** Complexity S once decided. **Phase E**; it is the cheapest
high-impact item in the plan and could reasonably be pulled earlier.

### QA-23 · No footer, no terms, no privacy, no contact, no support · **OPEN · MEDIUM · BUSINESS DECISION**

`AppShell` is `<header>` + `<main>`; landmarks confirmed live as exactly `HEADER, NAV,
MAIN`. The markup is XS; the **content is the blocker** — terms of service, privacy
policy, contact, and support are legal artifacts someone must author and approve. For a
platform that takes payments and holds personal data this is a commercial and probably
regulatory gap. Shipping an empty shell or links to 404s is worse than shipping nothing.
Pairs naturally with GAP-22 (the privacy policy and the privacy *mechanism* should be
written together). **Phase E.**

### GAP-09 · SEO, frontend half · **PARTIALLY_RESOLVED · MEDIUM**

The V2 discovery-coverage half is closed. The V3 frontend half is not: `layout.tsx` sets
only `title` and `description` — no favicon, no apple-touch-icon, no OpenGraph or Twitter
metadata, no `robots`, no `sitemap`. Any link shared into a messaging app renders bare, in
a market where sharing happens in messaging apps. Also still open and never settled: the
Persian-slug `post_name` question, which needs a live URL check rather than more code
reading, and the pretty city/specialty path decision. Complexity S for metadata,
M including SSR/slug decisions. **Phase E.**

### QA-16r · Homepage is a placeholder, not a landing page · **OPEN · MEDIUM**

QA-16 removed the Phase 1 scaffold copy; it did not design a homepage. There is no hero,
no value proposition, no category entry points, no social proof, no imagery. Depends on C
(imagery) to be worth doing properly. Complexity M. **Phase E.**

### QA-19 / QA-20 / QA-21 / QA-25 · The four "looks trivial, isn't" items

Each was correctly excluded from `v3.0.1` because the cheap version is worse than the
current state. Restated with what each actually needs:

| ID | Needs | Phase |
|---|---|---|
| QA-19 resend OTP | The API to return remaining cooldown seconds so the button can count down instead of failing with an unanticipated `RATE_LIMITED` | E |

| QA-25 business nav link | A business-membership signal on `/v1/me`, or dynamic roles (R31-01) | B (falls out of A) |

### UIKIT / TOUCH-CLASS / A11Y-CONTRAST · The component-layer items · **OPEN · MEDIUM**

Six UI primitives; almost all layout is inline `style={{}}` objects. The UI/UX audit's
diagnosis is the important part and this pass agrees with it: **five independent
empty-state bugs and five independent 44px touch-target bugs are symptoms of a thin
component layer, not of carelessness.** 44px is enforced inside `Button` and nothing
enforces it for a `Link`, so each new link surface re-learns it. Colour contrast has never
been measured — the palette is `oklch` with plausible separation, but no ratio has been
computed, and it is the most significant unverified accessibility dimension. No modal or
dialog exists anywhere, so the first one added will need focus management with no
precedent in the codebase. Complexity M. **Phase G, running alongside B** — building the
professional surface on the current component layer would manufacture the sixth and
seventh instance of both bug classes.

### GAP-10 · Every business-tunable numeric policy is provisional · **OPEN · BUSINESS DECISION**

Unchanged and correctly handled: made *visible* rather than silently settled. Every value
is environment-configurable and `GET /v1/admin/loyalty/policy` reports which are still V2
placeholders — though R31-01 means nobody can currently call that endpoint. Full list in
`V3.1_PRODUCT_ROADMAP.md` §16. **Phase: all**, as a decision track running parallel to
engineering.

### THROTTLE-STORE · In-memory per-process throttler storage · **OPEN · MEDIUM**

At multi-instance scale the effective limit multiplies by instance count. Correct fix is a
shared Redis store; deliberately not adopted at single-instance scale. Becomes real the
moment the hosting decision produces more than one instance, so it belongs **with** that
decision. **Phase F.**

### GAP-11 · SMS / email / AI providers never exercised live · **OPEN / EXTERNAL · MEDIUM**

Handled well: channels report `providerVerified: false` so a logging provider can never be
mistaken for a delivering one. But it means **no notification the product sends actually
reaches anyone off-platform** — including the OTP that is the only way to log in. In-app
delivery is genuinely real; SMS and email are not. Blocked on credentials (external) and
coupled to the hosting/region decision. **A real SMS provider is a launch prerequisite,
not a nice-to-have** — without it nobody can authenticate. Complexity M. **Phase E, and
it should be treated as blocking alongside GAP-06b.**

`V3.1-B`'s first task is implemented. Full report: `V3.1_TASK1_IMPLEMENTATION.md`. This
section records only what changes **this** document.

### Closed

**`PRO-UI` — CLOSED.** All nine professional capabilities that had an API and no frontend
now have one, across seven `/pro` routes. Verified by the complete live browser trace
(profile → service → availability → customer booking → payment → completion → earnings →
history). No backend capability was recreated; three thin routes were added over existing,
already-tested service methods (`GET /v1/me/provider`, `PATCH`/`DELETE` on a service, and

specified and nobody had built).

**`QA-25` — reclassified, not closed.** The professional-mode nav link is shown to every
authenticated user *deliberately*: becoming a professional in V3 is self-service, so `/pro`
is the entry point to a mode anyone may enter. That is not the same situation as the
business link, which is shown to everyone because **no signal exists** to condition it on.
`QA-25` itself is unchanged and still waits on Phase A.

**`TOUCH-CLASS` — partially closed.** `TextLink` now carries the 44px baseline as an
inheritable property rather than a lesson each surface re-learns. The seven new routes were
measured at 375/412/1280 with **zero** sub-44px interactive targets. The class is not fully
closed until the existing customer surfaces adopt the primitive.

**`UIKIT` — materially advanced.** `TextLink`, `PageHeader`, `EmptyState`, `Badge`,
`Select`, `Textarea`, and the codebase's **first** `ConfirmDialog` (with a real focus trap,
which had no precedent anywhere in V3) now exist. Still open for the customer surfaces.

### New findings

**`R31-08` — CORS blocked `Idempotency-Key`, so browser checkout has never worked.
PRE-EXISTING / HIGH / FIXED.** `POST /v1/bookings` requires the header and the web app sends
it, but `main.ts`'s CORS allow-list never named it, so every cross-origin booking was
rejected at **preflight** and the POST was never issued. Customer checkout therefore failed
in every real browser in the deployed topology (API and web on different origins). Invisible
to all 407 API tests, because supertest sets headers directly and no preflight exists. This
is a second instance of the exact class Phase 1 recorded when CORS was found entirely
unconfigured — same file, same reason. Fixed; the fix was strictly required to run Task 1's
mandated end-to-end trace.

**`R31-09` — `persian-utils`' date helpers read host-local time, not the platform zone.
OPEN / MEDIUM.** `formatShortDate`, `formatFullJalaliDate`, and `formatTime` resolve a
`Date` through `getHours()`/`getDate()`, which read whatever zone the browser is in, while
booking-service materializes every slot from a wall clock in `Asia/Tehran`. Correct for a
user in Iran on a machine set to Iran; silently an hour or a day wrong otherwise. Task 1
added an additive, zone-explicit module (`zoned.ts`) and used it throughout `/pro`, leaving
every existing customer call site untouched — changing their behaviour was outside the task.
**The customer surfaces remain latently inconsistent.** Recommended phase: G, alongside the
component-layer work.

**`R31-10` — service update leaked existence as a 500. INTRODUCED AND FIXED IN TASK 1.**
`ServiceOfferingService.update()`'s `findOneOrFail` was harmless while the method had no HTTP
route; exposing it turned TypeORM's `EntityNotFoundError` into a 500, distinguishable from
the response a well-formed nonexistent id gets. Recorded because the *pattern* generalises:
**every service method that gains its first HTTP route needs its not-found path re-examined
at the boundary**, and Phase A will expose several.

### Evidence position — materially changed

**The authenticated application ran locally, in a real browser, for the first time in V3's
history.** Every phase report and both release gates recorded this as impossible in this
environment. It was achieved by provisioning a PostgreSQL 16 container using the project's
own CI provisioning steps and `database/scripts/financial-roles.sql` — no credential
guessing, no `pg_hba.conf` edit.

Consequences for items this document tracks:

- The full real-PostgreSQL suite now runs **locally** as well as in CI: **20 suites / 407
  tests / 0 skipped**, up from 378.
- Three of the four unverified accessibility dimensions in `V3.1_UIUX_BACKLOG.md` §2.7
  (items 21 and 23 — keyboard traversal and populated protected-route layouts) are now
  *reachable*, though only item 23 was exercised in this pass.
- **`HOSTING_GRANTS` is unchanged.** A local container is not a real target hosting
  provider, and this pass makes no claim that it is.

## 9. Phase B + G addendum (2026-08-27) — professional surface completion and the component layer

Full report: `V3.1_PHASE_B_IMPLEMENTATION.md`. This section records only what changes
**this** document.

### Closed

**`R31-09` — CLOSED, and it was NOT latent.** This document recorded the host-local date
helpers as a latent inconsistency confined to the customer frontend. It was live and
server-side: `apps/api/src/events/notification-analytics.handlers.ts` builds the `date` and
`time` variables of the booking-confirmed, booking-cancelled and booking-rescheduled
notifications with `formatFullJalaliDate` and `formatTime`, in the API process, where
**nothing sets `TZ`** — not `apps/api/.env`, not the bootstrap, not the CI workflow. On the
ordinary UTC host a container runs on, every customer has been told an appointment time
three and a half hours earlier than their real appointment, and the wrong **day** for any
appointment before 03:30 Tehran.

Fixed centrally: the three helpers delegate to `zoned.ts`, so the platform zone is the
default rather than an opt-in and no call site changed — the defect was reachable from any
call site, including ones not yet written. `toPersianDigits`/`normalizeDigits` moved to a
leaf `digits.ts` to break the resulting import cycle.

**Severity reclassified MEDIUM → HIGH**, on the same reasoning as `R31-08`: a defect that
is invisible to every test and only appears in the deployed topology is not a smaller
defect for being invisible.

**`R31-11` — CLOSED, and it was five pairs, not four.** `ink-faint` on `background` measured
**3.81**; Phase A measured `ink-faint` against `surface` and `surface-tint` but not against
the page background, where it also renders. All 25 pairs the product renders text in now
pass WCAG AA for normal text, **worst 4.66**, measured in a real browser by the same
canvas-readback method and independently asserted by 71 test cases computed from
`tokens.json` itself.

Corrections were central — `ink-faint`, `warning` and `error` darkened with hue preserved,
`error-soft` re-authored into gamut. **No component took a local colour override.**

### New findings

**`R31-12` — two design tokens were outside the sRGB gamut. PRE-EXISTING / MEDIUM /
FIXED.** `warning` (`oklch(0.55 0.13 70)`) and `error-soft` (`oklch(0.95 0.05 25)`) were
clipped by the browser, so the authored colour and the rendered colour were different
colours and any ratio computed from the authored value described something nobody sees.
Nothing had ever checked. `warning`'s AA correction brings it into gamut as a side effect;
`error-soft` is re-authored as the nearest in-gamut colour, rendering `rgb(254,226,222)`
against the clipped original's `rgb(255,226,222)` — a one-unit difference in the red
channel. A test now asserts every token is in gamut.

**`R31-13` — four irreversible actions had no confirmation. PRE-EXISTING / MEDIUM /
