# V3.1 Release Strategy

**Status:** PLANNING ONLY. **No tag was created by this document.** `v3.0.0` (`cfecfdf`)
and `v3.0.1` (`68d3d5e`) are untouched, as are all nine historical V1/V2 tags.

**Baseline:** `HEAD` = `origin/master` = `v3.0.1` = `68d3d5e`.

---

## 1. Recommendation

**Ship V3.1 as a sequence of four minor/patch releases, not one large `v3.1.0`.**

```
v3.1.0   Operability + Professional surface     (Phases A, B, G)
v3.1.1   Media, Portfolio, Imagery              (Phase C)
v3.1.2   Reviews and the rating signal          (Phase D)
v3.2.0   Trust, legal, and production payment   (Phases E, F)
```

The final step is deliberately **`v3.2.0`, not `v3.1.3`**. Enabling real money and shipping
privacy erasure are not patch-shaped changes, and the version number should say so.

---

## 2. Why not one large release

Four independent reasons, in order of weight:

**1. The phases have genuinely different external gates.** A, B, and G need no decision and
no infrastructure. C needs a storage provider, which needs the hosting decision. E needs
legal content and SMS credentials. F needs merchant credentials and a verified production
host. Bundling them means the whole release waits on the slowest external party — and the
hosting decision has already slipped past two releases. A single `v3.1.0` would very likely
become a single `v3.1.0` that never ships.

**2. Each phase has a real, demonstrable user-facing outcome.** "A professional can operate
their business" is a release. So is "the marketplace has images" and "customers can leave
reviews". Bundling them hides three distinct product milestones behind one date.

**3. Risk isolation, specifically around the first privileged principal.** V3.1-A creates
the platform's first account that can grant roles, settle money, and reverse settlements.
That deserves its own release boundary and its own rollback story, not to be entangled with
an object-storage rollout.

**4. It matches how V3 has actually been delivered.** Five phases, each with its own report,
CI run, and gap-register addendum. That discipline works; there is no reason to abandon it
for V3.1.

## 3. Release-by-release

### `v3.1.0` — Operability and the professional surface

**Contains:** Phase A (dynamic roles/capabilities, verification workflow, DB-persisted
audit log, admin route group), Phase B (professional operating surface, staff invite by
phone), Phase G (UI kit primitives, contrast measurement).

**Version class: MINOR.** New features, new database schemas (`admin`, plus `identity` and
`provider` additions), new API routes. No breaking change to any existing contract —
`capabilitiesForRoles()` keeps its signature and every existing guard and controller is
untouched.

**Why these three together:** A and B are the two phases with no upstream dependency; G is
consumed by B from the first screen. Splitting B from G would ship the professional surface
on the component layer that produces the recurring touch-target and empty-state bugs.

**Release gate:**
- CI green: all three jobs, 0 skipped, on the release commit.
- A named human can be granted `platform_operator` through the documented bootstrap
  procedure, and every action they take appears in the audit log.
- **The live trace:** a professional publishes availability, receives a booking, and marks
  it complete through the browser — and loyalty points, the journey timeline entry, and the
  `completed_bookings` ranking signal all observably move. This trace has never been
  runnable in V3; running it is the gate.
- A professional is verified end to end and the `verified` badge appears in search.
- Adversarial: a `customer` reaches no `/v1/admin/*` route; an admin route registered
  without an audit call fails to boot.
- **`EXC-002` recorded, or `EXC-001` amended** — see §5. Non-negotiable.

**Not in this release:** anything visual, anything legal, anything involving real money.

---

### `v3.1.1` — Media, portfolio, imagery

**Contains:** Phase C. Also the natural home for the two cheap visual items that need no
decision: favicon and OG/Twitter/robots/sitemap metadata (`GAP-09` frontend half), and —
if the font-delivery decision (#15) has landed by then — Vazirmatn.

**Version class: MINOR.** New capability (object storage), new schema
(`provider.portfolio_items`), new routes.

**Release gate:**
- A professional uploads portfolio work and an avatar; both render in search results and on
  the profile **with zero layout shift**, measured, not assumed.
- Verification evidence uploads and is reachable **only** with the moderation capability —
  asserted adversarially, including from an authenticated non-moderator session.
- A presigned upload URL cannot write outside its own key prefix.
- Server-side content-type and size validation, never client-trusted.
- Responsive sweep re-run at 375/390/412/desktop with images present. The current
  "zero layout shift" result is only true because there are no images; it must survive them.

---

### `v3.1.2` — Reviews and the rating signal

**Contains:** Phase D.

**Version class: MINOR.** New schema (`provider.reviews`), new event contract
(`ReviewCreated` v1), new routes, plus the `search.ranking_signals` writer.

**Why it is its own release:** ranking behaviour changes for every provider in the index the
moment real rating data starts arriving. The formula's Bayesian shrinkage and cold-start
blending were designed for exactly this transition but have **only ever run at 0/0**.
That deserves an isolated release boundary and a relevance QA pass, not to be one line item
inside a larger deploy.

**Release gate:**
- `search.ranking_signals.review_count > 0` for a real provider, and `high_rating` awarded
  for the first time in the project's history.
- The rating signal is idempotent under event redelivery, proven through
  `search.signal_applications`.
- A review without a completed booking is refused; a second review for the same booking is
  refused. Both server-side, both adversarially tested.
- `minRating` and the `rating` sort exposed in the UI and returning sensible results.
- **A relevance QA pass**, explicitly: search results compared before and after real rating
  data exists, with any surprise investigated rather than accepted.

---

### `v3.2.0` — Trust, legal, and production payment

**Contains:** Phase E (font if not already shipped, footer, privacy export/deletion/
anonymization, real SMS, designed homepage, auth polish) and Phase F (real gateway adapter,
`failureCode` contract, real-host role verification, CD, backups with a tested restore
drill, error tracking, monitoring).

**Version class: MINOR, at the second position — deliberately not `v3.1.3`.** Two reasons,
both substantive rather than cosmetic:

1. **Real money becomes possible.** That is the largest behavioural change since `v3.0.0`
   and the version string should be legible to someone who reads only the version string.
2. **Erasure is irreversible.** A privacy deletion that completes cannot be undone. A patch
   number understates what an operator is deploying.

**Release gate — the strictest in the plan:**
- `GAP-06b` formally closed in `V3_GAP_REGISTER.md` **on real evidence**: a real adapter, real
  credentials held as deployment secrets, a completed sandbox-test cycle against the
  *gateway's own* sandbox covering money units, field semantics, error codes, and network
  failure modes.
- **`EXC-001` retired, not lapsed.** The exception document is explicit that lapsing
  silently is the failure mode it exists to prevent.
- A live browser transaction against the gateway sandbox, then **one controlled real-money
  transaction**, before general availability.
- The real target PostgreSQL host verified with `database/scripts/financial-roles.sql`
  (`HOSTING_GRANTS`), with `PHASE4-03`'s PostgreSQL 15+ `CREATE ON SCHEMA public` grant
  handled.
- **A restore drill actually performed**, not documented. `V3_INFRASTRUCTURE_PLAN.md` §9 is
  already explicit that a backup which has never been restored is not a verified backup.
- Privacy: every data-owning module covered by the export contract, **asserted structurally**
  — a new module that owns user data and does not register must fail the suite. Erasure
  leaves `financial.ledger_entries` intact and the identity anonymized. A cancelled deletion
  inside the grace window fully restores the account.
- Terms and privacy policy live, reachable from every page, and **describing what the
  mechanism actually does**.
- A real SMS OTP arrives on a real phone.
- If the deployment topology is multi-instance: Redis-backed throttler storage, or the
  documented limit is a fiction.

## 4. Versioning rules for V3.1

| Change | Version bump |
|---|---|
| New domain, new schema, new routes | MINOR |
| New frontend surface over existing API | MINOR |
| Bug/UI fix, no contract change | PATCH |
| Additive field on a response | MINOR (it is a contract change, even when compatible) |
| Anything enabling real money | MINOR at minimum, and announced as such |
| Breaking change to a public contract | **Does not happen in V3.1.** §17 of the roadmap rejects any candidate that would require one |

**On the `VerifyPaymentResult.paidCurrency` precedent:** `v3.0.1` tightened a provider
contract inside a patch release. That was defensible because exactly one provider existed
and the field was additive. **Do not treat it as precedent** once a real adapter exists —
after `v3.2.0`, a provider-contract change is a minor bump.

## 5. The `EXC-001` question — must be settled before any V3.1 tag

`V3_RELEASE_POLICY_EXCEPTIONS.md` states EXC-001 "Applies to: The `v3.0.0` release only",
and its Review condition fires when:

> Any subsequent release (`v3.0.x`, `v3.1.0`, …) is proposed while GAP-06b is still open —
> the exception covers `v3.0.0` **only** and does not automatically extend to successors.

The `v3.0.1` tag message records `EXC-001 = STILL ACTIVE, unchanged and unextended`. Read
against the scope clause, that means **`v3.0.1` was released without a covering exception**
(`R31-04`). Nothing harmful followed — `v3.0.1` changed no payment behaviour and the
production gate still fails closed with no override — but the document that exists
specifically to prevent silent policy drift has drifted, and the same condition fires again
at `v3.1.0`.

**Two acceptable resolutions. Doing nothing is not one of them.**

**Option A (recommended) — record `EXC-002`**, scoped to "every release in the `v3.0.x` and
`v3.1.x` lines while GAP-06b remains open", retrospectively covering `v3.0.1`. It must carry
the same rigour EXC-001 does: the unmet criterion named, the reasons the exception is
acceptable re-verified rather than copied, the risks accepted stated plainly, the safeguards
relied upon re-read, the production-activation requirements restated, and a review
condition. Retire it at `v3.2.0` alongside EXC-001.

**Option B — amend EXC-001's scope** with an explicit, dated amendment and a re-verification
of every "Reasons the exception is acceptable" item against the then-current code.

**Why this matters more than it looks.** EXC-001's own list of safeguards includes: *"The
production gate's two-condition, no-override property is weakened in any way, by anyone, for
any reason. That property is load-bearing for this entire decision."* An exception nobody
re-reads is an exception whose load-bearing property nobody re-checks. The re-verification
is the point; the paperwork is the mechanism.

## 6. Release discipline carried forward from V3

These held across five phases and two releases and should not be relaxed:

1. **Never move, re-point, delete, or re-sign a published tag.** Every fix is a new commit
   after the tag.
2. **Annotated tags with a "READ THIS FIRST" block** stating what the release does and does
   not change — specifically the production-payment status. Both V3 tags do this well.
3. **CI green on the exact release commit**, with the "assert no suite was silently skipped"
   step passing so the 0-skipped figure is enforced rather than reported.
4. **A gap-register addendum per release**, recording what changed in the register
   specifically — not a restatement of the release notes.
5. **State what was not verified.** Both V3 releases disclosed their live-QA limitations
   plainly rather than presenting CI coverage as equivalent to browser coverage. V3.1 has
   the chance to remove that limitation entirely by restoring a bootable local environment,
   and should.
6. **No release closes a gap it did not actually close.** GAP-06b has survived five phases
   and two releases without being quietly reclassified. That is the single best habit in
   this project's documentation.

## 7. Pre-tag checklist — every V3.1 release

- [ ] `HEAD == origin/master`; working tree clean except known untracked local files
- [ ] CI green on the exact release commit, all jobs, **0 skipped**, skip-assertion step passed
- [ ] `typecheck`, `lint` (including Nx module boundaries), `build` all clean
- [ ] Real-PostgreSQL suite passing; **any new migration exercised against real Postgres,
      not only pg-mem** — the standing Phase 1 lesson
- [ ] `pnpm-workspace.yaml` overrides re-verified if any package was added
- [ ] All nine historical V1/V2 tags byte-identical to their remote counterparts
- [ ] `v3.0.0` and `v3.0.1` unmoved
- [ ] Release-exception status explicitly stated and, if GAP-06b is still open, **covered**
      (§5)
- [ ] Gap-register addendum written
- [ ] Live browser QA performed and its **limitations stated**, not omitted
- [ ] Annotated tag with a "what this does and does not change" block, naming the
      production-payment status
- [ ] No business decision from `V3.1_PRODUCT_ROADMAP.md` §12 was taken implicitly by an
      implementation phase

## 8. What would change this strategy

Stated so the plan can be revised on evidence rather than argued about:

- **The hosting decision lands immediately and a provider is ready.** Then C's gate opens
  early and `v3.1.1` could merge into `v3.1.0`. Nothing else changes.
- **Merchant credentials arrive early.** F is no longer last; it becomes its own `v3.1.x`
  ahead of E, since payment has fewer content dependencies than the legal work.
- **Legal content is delayed indefinitely.** E splits: privacy *mechanism*, SMS, font, and
  auth polish ship without the footer, and the footer waits. The mechanism is worth having
  even before the policy describing it exists — but do not ship the policy link before the
  policy.
- **B reveals the API is less complete than it appears.** The premise of this whole plan is
  that ~40% of the built API is UI-ready. If Task 1 (roadmap §20) disproves that, everything
  downstream needs re-estimating — which is precisely why Task 1 is first and small.
