# V3.1 External Enablement Strategy

**Status:** ACTIVE EXECUTION POLICY — approved by the project owner on 2026-08-29.

**Purpose:** keep implementation, design, and QA moving while hosting, legal content,
vendor selection, and production credentials are unavailable, without representing a mock,
local harness, or unperformed live check as production evidence.

**Authority:** this document changes execution order and status vocabulary only. It does
not weaken any security gate, release gate, Definition of Done, exception condition, or
gap-closure criterion in the V3/V3.1 roadmap and release documents.

---

## 1. Decision

BeauClick will proceed through the implementable portions of Phases E and F, the final
design/UI implementation, and global QA before the externally controlled production
dependencies are available.

The work is split into two explicit milestones:

1. **IMPLEMENTATION COMPLETE / SANDBOX READY** — code, migrations, contracts, UI, local and
   sandbox tests, security behaviour, runbooks, and configuration surfaces are complete to
   the extent possible without a selected external service or production credential.
2. **PRODUCTION ENABLED / RELEASE READY** — every applicable external dependency has been
   selected and configured, and every live-evidence gate has actually been performed.

The first milestone permits continued development. It does **not** close an external gap,
complete Phase F, authorize general availability, or substitute for the second milestone.

---

## 2. Non-negotiable rules

1. **No fabricated evidence.** A local HTTP double, mock provider, sandbox, configuration
   schema, or runbook is not a live SMS, production gateway, deployed host, or restore drill.
2. **External gaps stay open.** Items waiting on a vendor, credential, host, approved legal
   text, or real-world verification remain `EXTERNAL`, `BUSINESS DECISION REQUIRED`, or
   `PRODUCTION VERIFICATION REQUIRED` until the named evidence exists.
3. **Fail closed.** Missing production credentials must leave SMS and payment unavailable;
   no development fallback may activate in production. The payment sandbox gate and its
   no-override property remain load-bearing.
4. **No invented vendor decisions.** Engineering may define ports, configuration contracts,
   error handling, test harnesses, and runbooks. It must not select a gateway, SMS provider,
   host, legal policy, or business policy on the owner's behalf.
5. **No secrets in Git.** Only environment-variable names, secret-manager references, and
   redacted examples may be committed.
6. **Continue around blockers.** An external blocker is isolated and recorded; it does not
   stop unrelated backend, design, UI, accessibility, security, or QA work.
7. **Production claims require production evidence.** Phase F's existing Definition of Done
   and the `v3.2.0` release gate remain the authority for production enablement.

---

## 3. What can proceed before external enablement

### Phase E

- Privacy export, erasure, anonymization, cancellation, and admin status surfaces.
- Session/device management and resend-OTP cooldown behaviour.
- SMS provider port, configuration validation, failure mapping, timeouts, retries where
  safe, observability hooks, and tests against a real local HTTP server.
- Homepage, footer structure, legal-route shells, SEO metadata, and responsive/accessibility
  work, while approved legal copy and the font decision remain visibly blocked.
- Claude Design handoff and production frontend implementation for all supported states.

### Phase F

- Gateway-port hardening, trusted-server-state verification, money-unit validation,
  idempotency, timeout/duplicate-callback behaviour, and the `failureCode` contract.
- Provider-neutral deployment configuration, secret contracts, health checks, CD workflow
  structure, rollback/runbook documentation, and environment validation.
- Backup and restore automation plus non-production rehearsal; the real-host restore drill
  remains a separate live gate.
- Sentry/OpenTelemetry/metrics instrumentation and local or sandbox verification; receiving
  real production telemetry remains a live gate.
- Redis throttling support only if the selected deployment topology is multi-instance.

Engineering must not create a fake provider-specific adapter merely to mark an item done.
If vendor selection determines protocol details, that adapter waits at the external gate.

---

## 4. External Enablement Gate

The following evidence is deferred but mandatory before `PRODUCTION ENABLED / RELEASE READY`:

| Dependency | Required evidence |
|---|---|
| Approved legal content | Final terms, privacy, contact, and support content approved by the owner and reachable from every page |
| Font decision | Owner-approved delivery choice, implemented and verified for Persian rendering |
| SMS vendor and credentials | One real OTP delivered to a real phone through the selected production path, with secrets held outside Git |
| Hosting/region | Application deployed on the selected host with production environment validation passing |
| PostgreSQL grants | `financial-roles.sql` and applicable schema grants verified on the real target host |
| Payment gateway | Selected adapter, merchant credentials, provider sandbox lifecycle, failure modes, and one controlled real-money transaction |
| Backups | A backup restored into a clean target and the restored system verified |
| Observability | Production errors, traces, and required metrics received by the selected backends |
| Multi-instance throttling | Redis-backed shared throttling verified if and only if production runs more than one API instance |

Any failed item keeps its corresponding gap open and blocks production enablement, but does
not invalidate completed implementation or sandbox QA.

---

## 5. Execution order

```text
Finish Phase E implementation that is independent of external services
  -> Claude Design Phase E sync
  -> implement the non-external portion of Phase F
  -> Claude Design Phase F/final sync
  -> implement the Phase C/D/E/F frozen frontend surfaces
  -> global UI/UX, accessibility, browser, security, and regression QA
  -> declare IMPLEMENTATION COMPLETE / SANDBOX READY with an explicit blocker ledger
  -> execute the External Enablement Gate
  -> final production QA
  -> declare PRODUCTION ENABLED / RELEASE READY
  -> release
```

The exact ordering of UI work and non-external Phase F work may change when doing so reduces
risk, provided neither is reported as production verification.

---

## 6. Required phase reports

Every Claude Code and Claude Design closure report after this decision must separate:

- `IMPLEMENTED AND VERIFIED LOCALLY`
- `VERIFIED AGAINST PROVIDER SANDBOX`
- `UI/DESIGN COMPLETE`
- `BUSINESS DECISION REQUIRED`
- `EXTERNAL CONFIGURATION REQUIRED`
- `PRODUCTION VERIFICATION REQUIRED`
- `FUTURE / DEFERRED`

Reports must name the exact missing decision, credential, environment, or live check. The
words `complete`, `closed`, and `production-ready` must not collapse those categories.
