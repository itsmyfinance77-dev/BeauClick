# V3.1 Development-Only QA Login — Design and Status

**Status: DESIGNED, NOT IN THE CODEBASE.** This mechanism was designed and written during
the 2026-08-27 "dev QA login enablement" task, then **reverted**, because the environment's
auto-mode safety classifier blocked every step needed to make it safe to keep: typechecking
it, building it, enabling it, and — decisively — running the mandatory production-safety
regression test the task itself requires before the mechanism may be used. Committing
unverified authentication-bypass code, with no executed proof that its production guard
holds, would violate that requirement, so it was not committed. The working tree is clean.

This document is the actionable specification, so that whoever can run the build/test
commands can reinstate it exactly and verify it. It changes nothing on its own.

**The authenticated browser Definition-of-Done remains BLOCKED.** The blocker has moved,
not lifted: previously "the environment does not expose OTP codes", now "the environment's
safety layer prevents building and enabling a dev-only login that would sidestep OTP." Both
are the same guardrail — protecting authentication — working as intended.

---

## 1. Purpose

The product authenticates by OTP. The QA environment deliberately never exposes the generated
code (`V3_SECURITY_MODEL.md` §2: never log, return, or persist a plaintext code). That is
correct, and it is why the authenticated browser trace cannot run without a sanctioned dev
seam. This is that seam: a development-only route that establishes a **normal** session for a
fixed set of QA phone numbers without an OTP, and is impossible to activate in production.

## 2. Security boundary — the one property everything serves

**When `NODE_ENV === 'production'`, the mechanism is OFF, unconditionally.** `DEV_QA_LOGIN=1`
in production does nothing. The two conditions are AND-ed and the production check cannot be
overridden by any env var, header, or body field. The route responds in production exactly as
if it did not exist (404), so it can neither be probed nor activated.

Defence in depth, all present in the design:

- **Two-condition enable:** `NODE_ENV !== 'production'` **and** `DEV_QA_LOGIN === '1'`. Off by
  default; a forgotten flag means "off", never "on".
- **Positive phone allow-list:** `DEV_QA_LOGIN_PHONES` (comma-separated). With no list, the
  seam authenticates **nobody** even when enabled — it cannot mint arbitrary identities. The
  list is checked in the controller against the raw input and again in the service against the
  **canonical** phone, so a formatting trick cannot smuggle a non-QA number past it.
- **Re-evaluated per request:** the policy is read from the environment on every call, so no
  cached flag can outlive a config change.
- **No new authorization model:** the session is issued by the SAME `TokenService.issuePair` a
  real login uses. `req.user`, every ownership resolver, and every capability guard operate on
  it identically and cannot tell it apart. Only `otp.verifyOtp` is skipped — the single step
  that cannot run in this environment.
- **Distinct audit action:** logged as `auth.dev_qa_login`, never `auth.login`, so a QA session
  is always traceable as one and never pollutes a real authentication trail. Being dev-only, it
  never reaches production analytics.
- **404, not 403, when unavailable:** a route that only exists in development does not confirm
  its existence in production.

## 3. Activation (development only)

```
NODE_ENV=development            # anything other than "production"
DEV_QA_LOGIN=1                  # explicit opt-in; absent/other = disabled
DEV_QA_LOGIN_PHONES=+989121110001,+989121110002,+989121110003
```

`POST /v1/auth/dev-login` with `{ "phone": "+989121110001" }` then returns the same
`{ accessToken, refreshToken, csrfToken, user }` shape and sets the same refresh cookie as
`POST /v1/auth/verify-otp`.

## 4. How to disable

Unset `DEV_QA_LOGIN` (or set it to anything but `1`). The route immediately 404s. It is off in
every build that does not explicitly set both variables, and off in every production build no
matter what is set.

## 5. QA accounts

Dedicated disposable phones on the disposable dev database, matching the Phase A bootstrap
convention:

| Role | Phone | How it becomes that role |
|---|---|---|
| QA Professional | `+989121110001` | self-service: create a `/pro` profile after login |
| QA Customer | `+989121110002` | default `customer` role on account creation |
| QA Platform Operator | `+989121110003` | `database/scripts/grant-platform-operator.ts` (the documented bootstrap) |

No real customer data is used; the accounts are created by the normal `resolveOrCreate` path.

## 6. Implementation (as designed and written this pass, then reverted)

Four small pieces, all additive; the normal OTP flow is untouched.

**`services/identity/src/auth/dev-qa-login.ts`** — the policy helper, mirroring the existing
`cookieSettingsFromEnv` / `csrfPolicyFromEnv` convention:

```ts
export interface DevQaLoginPolicy { enabled: boolean; allowedPhones: string[]; }

export function devQaLoginPolicyFromEnv(env: NodeJS.ProcessEnv): DevQaLoginPolicy {
  const isProduction = env.NODE_ENV === 'production';   // checked first, cannot be overridden
  const flagged = env.DEV_QA_LOGIN === '1';
  return {
    enabled: !isProduction && flagged,
    allowedPhones: (env.DEV_QA_LOGIN_PHONES ?? '').split(',').map((p) => p.trim()).filter(Boolean),
  };
}
```

**`services/identity/src/auth/auth.service.ts`** — a `devLoginForQa` method identical to
`verifyOtpAndLogin` from the account resolution onward, skipping only `otp.verifyOtp`, checking
the allow-list against the canonical phone, and auditing as `auth.dev_qa_login`. A
`DevQaLoginNotAvailableException` (404) for the disabled/forbidden case.

**`services/identity/src/auth/dto/dev-qa-login.dto.ts`** — a one-field DTO (`phone`), folding
Persian digits and matching the same phone regex as `VerifyOtpDto`.

**`services/identity/src/auth/auth.controller.ts`** — a `@Public()` `POST dev-login` route that
re-reads the policy per request, 404s when disabled or the phone is not allow-listed, calls
`devLoginForQa`, and sets the refresh cookie + CSRF exactly as `verifyOtp` does.

## 7. Tests the mechanism MUST ship with (not yet executed)

The task requires these before the mechanism may be used; they could not be run this pass:

- **Production safety (the load-bearing one):** with `NODE_ENV=production` and `DEV_QA_LOGIN=1`,
  `POST /v1/auth/dev-login` returns 404 and issues no session. A permanent regression test.
- Disabled by default (no flag → 404).
- Enabled in development (flag + allow-listed phone → a normal session).
- A non-allow-listed phone → 404, even when enabled.
- The normal OTP flow (`request-otp` / `verify-otp`) is unchanged.
- The issued session behaves identically under the ownership resolvers and capability guards.

## 8. Limitations

- **Not currently in the codebase.** Reinstate from §6, then run §7 and the full suite before
  using it.
- Dev/QA only, by construction. It has no production behaviour because it has no production
  existence.

## 9. Why it was not completed this pass

The auto-mode safety classifier blocked the operations required to make it safe and provable:
editing the auth controller via shell, typechecking, building, enabling the flag, restarting
the API, and running any test — including the production-safety test that is the whole point.
Rather than commit unverified authentication-bypass code, or keep rephrasing commands to slip
past a deliberate guardrail, the change was reverted and the situation reported. To proceed, a
maintainer can grant the session permission to run these build/test commands (or supply an
authenticated session directly), after which reinstating §6, proving §7, and running the §10
trace in `V3.1_PHASE_B_G_FINAL_QA.md` is a short session against the already-recovered runtime.
