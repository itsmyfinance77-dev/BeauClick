## 3. The design decision worth reading

Full reasoning in **ADR-027**. The short version, because it is what the phase is actually
about:

The obvious implementation is a privacy service that reads every module's tables. V2 built
that, and `PRIV-06` records the cost — a hardcoded call list that went stale the moment a new
plugin stored user data, **silently**, because an incomplete export is indistinguishable in
shape from a complete one.

So the direction is inverted. `libs/subject-data` defines the contract; every module
implements it for its own tables; `privacy` orchestrates and imports no domain.

**And the registration is not trusted.** `SubjectDataCoverageService` reads the real
`pg_tables` catalogue at boot and requires every table in every non-system schema to be
claimed by exactly one contract, as `subject_data`, `retained`, or `no_subject_data` — the
last two requiring a stated reason. A migration that adds a table nobody claimed **fails
startup**. So does a stale claim, a double claim, and a `no_subject_data` claim on a table
carrying a `user_id`-shaped column.

`pg_tables` rather than `information_schema` is load-bearing: the latter is privilege
filtered, and the application role holds nothing on `financial.*` (ADR-017) — so an
`information_schema` universe would silently have excluded the ledger from the check meant
to guarantee nothing is missed.

Sixteen contracts are registered. `privacy` claims `public.schema_migrations` explicitly,
because excluding a schema is how the first genuinely unclaimed table gets in.

### The erasure model, in one sentence

**Destroy the identifying link and the free text; leave rows that are nothing but ids.**

Three consequences are decisions rather than details, each recorded at its own call site:

- A review's **rating survives and its comment does not** — the rating is a fact about the
  professional that other customers and the ranking formula rely on.
- **`journey` deletes rather than anonymizes.** Beauty profiles, goals, and timelines are
  single-party and referenced by nobody; retaining them would be keeping personal data for
  no reason. Applying the platform default there out of consistency would be the wrong
  answer arrived at by rule-following.
- **`analytics.events` keeps its `actor_id`.** Nulling it looks like more privacy and is
  not: it would silently change already-closed reporting periods on the next rollup re-run,
  while gaining nothing, because the id already points at an anonymized identity.

## 4. Two tables, and why

`privacy.data_requests` is administratively visible — an operator must be able to answer "is
this user's deletion progressing" without being able to read what the user's data *is*.
`privacy.export_payloads` is visible to exactly one principal in the entire system, the
subject, and to nobody else ever.

Separating them makes Phase E's unqualified security note — *"no admin route may ever
download another user's export file"* — a **structural** property rather than a `SELECT`
somebody has to remember not to write. The admin route reads `data_requests`; the payload is
not on the row it read. Asserted from an authenticated `platform_operator` session, not
merely from an anonymous one.

The document is stored as JSONB rather than in object storage, deliberately: a presigned URL
to a complete personal-data export is a bearer credential that survives being forwarded,
proxy-logged, or left in browser history. An authenticated route re-verifies the subject's
session on every byte. When it expires the payload row is **destroyed**, not merely made
unreachable — and the DELETE runs before the status update, in one transaction, so a crash
between them cannot leave a `expired` request with a live copy of somebody's data behind it.

## 5. Security

| Concern | Treatment |
|---|---|
| Authentication | Every privacy route requires a session; the four self-service routes derive the subject from `@CurrentUser()` |
| Authorization / IDOR | **There is no user id anywhere in `PrivacyController`.** "Export somebody else's data" is a request this API cannot express — the same construction `/v1/me` uses |
| Enumeration | Another user's request id, a nonexistent one, an ungenerated export, and an expired one produce a **byte-identical** 404 — asserted by comparing response bodies, not by reading the code |
| Rate limiting | Both write routes carry the `auth` throttle policy; the cancel route deliberately does not — somebody repeatedly trying to cancel their own deletion should be helped, not throttled |
| Privilege escalation | The admin surface is read-only. There is deliberately **no administrative cancel**: an operator who can cancel a deletion can silently keep an account its owner asked to be rid of |
| Auditability | `privacy.erasure_requested`, `privacy.erasure_cancelled`, `privacy.erasure_executed`, and `privacy.export_requested` are written to `admin.admin_audit_log` **in the same transaction**, with the subject as actor. A deliberate widening of that log's remit: "why does this account no longer exist" must be answerable whether the actor was an operator or the owner |
| Financial integrity | Erasure performs no write against `financial.*`, and could not: the application role has no `UPDATE` or `DELETE` there (ADR-017) |
| Sensitive-data exposure | The export excludes `refresh_tokens.token_hash` (a credential), `payment_attempts.provider_response` (a vendor blob that routinely carries a third party's identifiers), `media.objects.storage_key` (the store's key layout), and `admin.admin_audit_log` entirely (§ADR-027) |
| Race conditions | Covered in §9 |
| Retry behaviour | A request abandoned mid-flight is reclaimed by the sweep rather than stranded in `processing` forever with nothing reporting an error |

### Two adversarial properties the suite proves rather than assumes

- An **authenticated `platform_operator`** is refused another user's export download and
  cannot cancel another user's erasure. Both are checked from the privileged session,
  because that is the caller who could plausibly have been granted the ability.
- The **compliance record carries no content.** `privacy.data_requests` survives the erasure
  it proves happened, so a test serializes the row and asserts the erased phone number is not
  in it.

## 6. Events

Five new contracts in `libs/event-contracts/src/catalog/privacy.events.ts`, producer
`privacy`, all v1.

| Event | Consumers | Idempotency |
|---|---|---|
| `DataExportRequested` | notification, analytics | Partial UNIQUE admits one open request per subject per kind |
| `DataExportCompleted` | notification, analytics | Status CAS `processing → ready` |
| `DataErasureRequested` | notification, analytics | Same partial UNIQUE |
| `DataErasureCancelled` | notification, analytics | Status CAS `pending → cancelled` |
| `DataErasureCompleted` | **analytics only** | Status CAS `processing → completed`, in the erasure's own transaction |

**The rule every payload obeys:** a privacy event carries the *fact* that a request changed
state and nothing about what it contains. No document, no counts, no phone number, no name.
These fan out to analytics, which stores them permanently, and to notification, which
persists a row per delivery — an event announcing that somebody's data was destroyed must
not be the reason a copy of it survives in two more schemas. A test asserts the erased
subject's phone appears in no payload.

**`DataErasureCompleted` has no notification consumer, and that is the considered answer.**
By the time it publishes, the subject's phone number is a tombstone and every session is
revoked; there is no channel left and an in-app notification would address an account nobody
can sign into. The message that matters goes out on the *request*, while the grace window is
open and the user can still act on it.

**Analytics counts these events with no subject at all.** `actorOf` is deliberately absent
from all five mappings, so the allow-listed `dimensions` shape means the id never reaches the
fact table. "How many people asked to be erased this month" needs no identity to answer, and
an analytics store permanently recording *who* asked to be forgotten would be an unusually
pointed thing to get wrong.

### One additive contract widening, argued rather than assumed

`NOTIFICATION_CATEGORIES` gains `privacy` — an enum member added to five v1 contracts. The
project's rule is "a payload change is a NEW version, never an edit", and that rule exists to
protect deployed consumers. Adding an enum member breaks none: no field changes type, none is
removed, and every value a consumer already understood still arrives. Cutting v2 of every
notification contract for a category label would cost real churn and buy nothing. A member
*removed* from that list would be the breaking change, and would deserve the version. The
reasoning is recorded in the catalogue file, not only here.

`privacy` is also a **mandatory** notification category (migration
`20260828300002`), enforced by the same CHECK constraint that protects booking confirmations
and payment receipts. The "your account will be deleted, and here is until when" message is
the only thing standing between an accidental deletion and an irreversible one; the grace
window is worthless if the user never hears that it is open, and someone who muted marketing
has not consented to missing it.

## 7. `QA-20` — the session claim, and the two things it exposed

`GET /v1/auth/sessions` returned `current: false` on every row. It stayed open through
`v3.0.1` because fixing it honestly needs a session identifier in the access token — a change
to the shape of every token the platform issues — and the cheap alternatives (match on user
agent, assume the newest row) are wrong in exactly the situation the feature exists for:
several devices, one of which the user wants to keep.

`sid` is now signed into every access token. It is the refresh **row's** id, never the
refresh token — that is stored only as a SHA-256 hash. It is **optional** on the payload, and
that is load-bearing rather than defensive: tokens minted before the claim existed stay valid
for their full 15 minutes across a deploy, so a required claim would 401 every signed-in user.
Those report `current: false`, which is the honest answer — it is not known — and self-corrects
on the next refresh.

Implementing it surfaced two defects in the surrounding surface that would have made the
device-management screen unusable, neither of which is a bug in new code:

**The session list grew one row per rotation.** Refresh tokens rotate (ADR-014), so a phone
used daily contributed several hundred indistinguishable rows. `listSessionsForUser` now
selects the tip of each rotation chain (`replaced_by_token_id IS NULL`) — one row per device.
Superseded rows are not hidden data: each is already revoked, and only the tip can be
presented, rotated, or revoked.

**`created_at` answered the wrong question.** It is when the current *token* was minted —
eleven minutes ago for a session started three weeks ago — so the screen would have reported
"signed in 11 minutes ago" for every device the user owns. Migration `20260828300003` adds
`session_started_at`, carried forward across every rotation. Nullable for pre-existing rows,
with `created_at` as the fallback: their chain's true start predates the column, and inventing
a timestamp would be worse than reporting the one thing that is true.

## `QA-19` — the cooldown, stated rather than guessed

`POST /v1/auth/request-otp` returns `cooldownRemaining` and `expiresInSeconds` on success,
and a refusal inside the resend window carries `retryAfterSeconds`.

Two properties are asserted rather than assumed:

- **The new fields cannot become an enumeration oracle.** Both are policy constants,
  identical for every caller; a test compares the whole response body for a phone with an
  account against one without and requires them equal.
- **An hourly-limit refusal states NO retry time.** When that window resets depends on when
  each of up to five earlier requests landed, and the honest answer is "not known" — a
  plausible number would have a client count down to a moment that still fails, which is
  worse than none because it looks reliable.

## 8. `GAP-11` — what closed and what did not

**The code side closed. The gap did not.**

`GAP-11` records that V2's SMS adapters "have never been exercised against a real external API
in any environment", and that is still true: no Iranian vendor has been selected
(`V3.1_PRODUCT_ROADMAP.md` §12 #2) and no credentials exist anywhere this project has run.

Shipping a named vendor adapter written from documentation was rejected, for the reason
`NotificationChannelPort` already records about payment gateways: an unexercised adapter is a
liability rather than an asset, because it looks finished.

What *was* legitimately buildable without fabricating configuration, and is built:

- **`SmsProvider`, a sub-port under the channel.** The channel keeps what it already owned —
  recipient lookup, the permanent-vs-transient split, the guarantee that neither the number
  nor the body reaches a persisted field. The provider decides only how bytes leave the
  building. Collapsing the two would make every future vendor re-implement the recipient
  lookup and the failure taxonomy, and the second one would get it subtly differently.
- **`HttpSmsProvider`, configured rather than vendor-specific.** Every candidate gateway
  accepts an HTTP request with an API key and a body naming a recipient and a message; what
  differs is the URL, the header name, and the field names — which are exactly the three
  things `SMS_HTTP_*` supplies. Selecting a vendor becomes configuration plus one live send.
- **`providerVerified` is now derived, not declared.** `SmsChannel` reports the configured
  provider's `deliversExternally`, so a deployment that has wired a real gateway stops being
  described on `/health` as one that has not — and an unconfigured one cannot claim it is
  sending.
- **An https-only rule, enforced.** The body carries a one-time login code and a phone number.
  Partial configuration is treated as *no* configuration, so an endpoint with no credential
  cannot fill the dead-letter queue with unauthenticated attempts while the operator debugs
  delivery instead of reading "no provider configured".

The 15 unit cases run against a **real local HTTP server** that records what it received, so
the header, the body, the JSON and form escaping, the timeout, the 4xx/5xx/429 taxonomy, and
the redaction of a gateway error quoting the recipient's number back are all exercised against
something that can genuinely disagree. What they cannot prove is a particular vendor's field
names. That is what `GAP-11` remains open for, and the phase report says so rather than
letting a green suite imply otherwise.

**Register status:** `GAP-11` stays **OPEN / EXTERNAL**, reclassified from "no abstraction
exercised" to "abstraction complete and exercised; awaiting vendor selection and one live
send".

## 9. Concurrency and idempotency

| Workflow | Two simultaneous requests | Mechanism |
|---|---|---|
| open a request | one 202, one 409 | `uq_privacy_open_request_per_subject`, a partial UNIQUE over `(subject_user_id, kind) WHERE status IN ('pending','processing')` |
| cancel an erasure | one cancellation, one event | Status CAS `pending → cancelled`; a cancel arriving after the sweep claimed the row correctly loses |
| generate an export | one payload | Status CAS `pending → processing` **before** the expensive read |
| execute an erasure | one erasure, one `DataErasureCompleted` | Same CAS; two sweeps racing is the normal state of a multi-instance deployment |
| expire exports | payload destroyed before status flips | One transaction, `FOR UPDATE SKIP LOCKED` |
| abandoned mid-flight | reclaimed and retried | `processing` rows older than the stall window return to `pending` |

Every one is driven by a test that fires two genuinely concurrent requests or replays the
state, not asserted from the code's shape.

The sweep's **order** is also load-bearing and unit-tested: reclaim → expire → generate →
erase. Reclaim first, so work a dead process abandoned is back in `pending` before this pass
looks for pending work; erase last, because it is the only irreversible step and a pass that
is going to die should die before it.

## 10. Database

Three additive migrations. No historical migration modified. Applied from the existing dev
schema and re-run: **`Applied: 0`** on the second pass.

- `privacy/20260828300001_create_privacy_schema.sql` — `data_requests`, `export_payloads`,
  `outbox_events`.
- `notification/20260828300002_privacy_is_a_mandatory_category.sql` — extends the existing
  CHECK. The corrective `UPDATE` runs **before** the new constraint, not after: an existing
  violating row would make the `ADD` fail outright, and a migration that aborts on data it
  could have corrected is one that aborts in production and not in test.
- `identity/20260828300003_session_chain_start.sql` — `session_started_at`, nullable.

Constraints doing real work rather than documenting intent:

- `uq_privacy_open_request_per_subject` — one open request per subject per kind, refusing the
  second under concurrency.
- `ck_privacy_request_window` — an erasure has a grace window and an export does not, so a
  request cannot exist in a shape no code path knows how to handle.
- `ck_privacy_request_cancellation` / `ck_privacy_request_cancelled_status` — a cancellation
  has a time and an actor, and a `cancelled` row is actually cancelled; without the second,
  the sweep and the API could disagree about the same row.
- `export_payloads.request_id` → `data_requests(id)` **ON DELETE CASCADE** — the one cascade
  in the schema, deleting in the safe direction so a destroyed request cannot orphan a copy
  of somebody's personal data.

## 12. Bugs discovered and fixed

### `BUG-E-01` — a global service could not see the token it depended on (found by the suite)

`SubjectDataCoverageService` injected `SUBJECT_DATA_CONTRACTS` with `@Optional()`. The
service lives in a `@Global()` module; the token is provided by the composition root, which
*imports* that module — so a global provider could not see it, and `@Optional()` turned the
misresolution into silence. The check ran against zero contracts, reported every table in the
database as unclaimed, and failed boot for a reason that had nothing to do with coverage.

The same shape as Phase C's `BUG-C-02` (`PRIVILEGED_CAPABILITY_VERIFIER` resolving to
`undefined`), and the third instance of this DI trap in the project's history.

**Fix, in two parts.** The contract list became a *parameter* of `evaluate`/`assertComplete`
rather than a constructor injection — the caller that owns the list passes the list, which
removes the scope question entirely. And `PrivacyCompositionModule` is `@Global()`, so
`PrivacyService` — which lives in the module the composition root imports — resolves the same
token.

The second half was found by the same run: with only the first fix applied, exports contained
zero sections and erasure erased nothing, both of which look like working code.

### `BUG-E-02` — the session list was one row per rotation, not one per device

Pre-existing and not introduced here, but it made `QA-20`'s feature unusable and is fixed with
it. See §7.

### `BUG-E-03` — the pg harness's `envOverrides` never reached `ConfigService`

Found because `auth-sessions.pg-spec.ts` **passed under bare `jest` and failed under
`nx run api:test:pg`** — the same code, two results, which is exactly the divergence the
harness's own comment about writing to `process.env` was added to prevent.

`createPgTestApp(envOverrides)` assigns `process.env` and then boots the app. But
`ConfigModule.forRoot({ validate })` runs when `app.module.ts` is *evaluated* — the moment the
`@Module` decorator's `imports` array is constructed — and `validate` receives a snapshot of
`process.env` that becomes the module's internal config, which `ConfigService.get()` reads in
preference to `process.env`. With `AppModule` imported statically at the top of the factory,
that snapshot was taken at **file load**, before the function had assigned anything.

So `envOverrides` silently affected only values read straight from `process.env` — the
throttler options — and never values read through `ConfigService`, which is every OTP,
booking, loyalty, and privacy policy number in the platform. `throttling.pg-spec.ts` worked
for four phases only because its values happen to be in the first category.

It stayed invisible because it needs a specific coincidence to surface: a suite must override
a `ConfigService` value whose `apps/api/.env` entry differs from the code default. Under bare
`jest` the snapshot fell through to the same default the override was asking for and the
assertion passed for the wrong reason; under `nx`, which loads `apps/api/.env` into
`process.env` first, it did not. This phase's suite is the first to override
`OTP_RESEND_COOLDOWN_SECONDS` (`.env` = 0, code default = 60) and so the first to hit it.

**Fix:** `AppModule` is imported dynamically inside `createPgTestApp`, after the environment is
assigned, so the snapshot is taken from the environment the caller actually asked for.
`envOverrides` now means what it says for every consumer.

**Blast radius:** test-harness only — no production code path constructs `AppModule` after
mutating `process.env`. Nothing that previously passed changed behaviour; the full suite is
green after the fix.

## 13. Tests

**`apps/api/test/privacy.pg-spec.ts` — 31 cases** against real PostgreSQL over real HTTP.
**`apps/api/test/auth-sessions.pg-spec.ts` — 10 cases**, booted with a real cooldown and a
real hourly limit, because a cooldown of zero cannot demonstrate a cooldown.
**`services/notification/src/channels/sms/http-sms-provider.spec.ts` — 15 cases** against a
real local HTTP server.
**`libs/subject-data/src/coverage.spec.ts` — 10 cases** on the pure coverage logic.
**`services/privacy/src/privacy.config.spec.ts` — 7 cases** on policy-number safety and sweep
ordering.

The cases that carry the phase, specifically:

- **The coverage check is proved to FAIL.** A coverage assertion nobody has seen fail is not
  evidence of coverage, so one case feeds the *real* contract list a catalogue containing one
  table nobody claims and requires exactly one `unclaimed` violation. Another asserts the
  catalogue is genuinely non-empty and contains `financial.ledger_entries` — the guard against
  a check that silently passes, and the one that proves `pg_tables` sees past the privilege
  filter.
- **Erasure reaches the search index.** Anonymizing `professionals.display_name` in PostgreSQL
  leaves the name in `search.provider_documents`, which is the one surface the public reads. A
  case erases a professional, drains the outbox, and asserts the projection's name is gone and
  `is_deleted` is true — proving the erasure works *through* provider's existing
  `ProfessionalUpdated` event rather than by writing to another module's table.
- **A zero-length grace window is refused.** `PRIVACY_ERASURE_GRACE_HOURS=0` is not a short
  window; it is deletion with no way back, arrived at by clearing an environment variable.
- **A gateway error quoting the recipient's number back never leaves the provider.**
- **A user cannot switch privacy notifications off** — asserted against the CHECK constraint,
  not against the preference service, so a bug in the update path cannot suppress the one
  message the grace window depends on.

Adversarial cases specifically: another user's request id (byte-identical refusal); an
operator downloading somebody's export; an operator cancelling somebody's erasure; a customer
reaching `/v1/admin/privacy/*`; an unauthenticated caller on every route; a deletion opened
without the exact typed confirmation; a token hash in an export; two concurrent export
requests; two sweeps racing one erasure; a request abandoned mid-flight.

### The business decision this phase deliberately did not make

**What should happen to a salon when its owner deletes their personal account?** Three answers
are defensible — the business closes with them, it survives with an unassigned owner, or
ownership transfers to a manager on the staff — and each has real consequences for the staff
who work there and the customers holding bookings.

Until it is decided, `business.businesses` is **retained** and the erased owner's staff
membership is set to `removed` so they lose access. That is the option that destroys nothing
and misrepresents nothing. Inferring "delete the salon" from "delete my account" would be
inventing product policy with other people's livelihoods attached. Recorded in
`business-subject-data.contract.ts` as well as here.
