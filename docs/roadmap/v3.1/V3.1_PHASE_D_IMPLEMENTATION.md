## 3. The one design decision worth reading

Phase D's security requirement is that *"eligibility must be proven server-side from booking
data, never asserted by the client"*. The obvious implementation is an application check:
look the booking up, confirm it completed, confirm the caller is its customer, confirm no
review exists. Four assertions in a service that every future caller has to remember, and a
read-then-write that two concurrent submissions can both pass.

It is also **impossible as stated**: provider-service cannot read booking-service's tables
(ADR-011), so that check would need a synchronous cross-domain port — reintroducing exactly
the coupling `ProviderEventsService`'s docblock records V2 suffering from, and making
reviews undeployable without booking.

`V3_DOMAIN_BOUNDARIES.md` §provider has said since Phase 0 that provider **consumes**
`BookingCompleted` for review eligibility. Following that literally turns two invariants
into database facts:

```
booking-service            provider-service                        search-service
──────────────             ────────────────                        ──────────────
BookingCompleted ────────► review_eligibility (PK booking_id)
                                    ▲
                                    │ FOREIGN KEY  ── "no review without
                                    │                  a completed booking"
                           reviews.booking_id
                                    │
                                    │ UNIQUE       ── "one review per booking"
                                    │
                           ReviewCreated ─────────────────────────► rating_sum += rating
                           ReviewModerated ───────────────────────► rating_sum -= rating
```

Neither invariant is reachable by forgetting a check, and neither races. The only rule left
in application code is the one a constraint cannot express — that the **caller** is the
customer named on the eligibility row — and that is read from provider's own projection,
never from the request.

`review_eligibility` is deliberately a narrow projection, not a second source of truth about
bookings: it carries no price, no status, and no schedule, and the single thing it claims
("this booking completed") is not a fact that later changes.

## 4. Post-moderation, and why

Reviews are **public and counted the moment they are written**. A moderator's job is
takedown, not gatekeeping.

That is forced by Phase D's own Definition of Done rather than chosen for convenience: it
requires `review_count > 0` and `high_rating` awarded, neither of which can happen if every
review waits for a human before it counts.

The queue is therefore **untriaged** reviews (`moderated_at IS NULL`), and a decision drains
it either way. `publish` on an untriaged review changes no visibility and still records a
decision — without a way to say "I looked at this and it is fine", the only way to clear a
queue would be to hide things.

## 5. Events

### `ReviewCreated` v1 — as the roadmap specified

`{ reviewId, bookingId, professionalId, customerId, rating, createdAt }`.

**The review TEXT is deliberately absent.** `V3_DOMAIN_BOUNDARIES.md` §ai names "raw review
text" on the excluded-by-construction list. An event payload is the widest distribution
channel in this architecture — every consumer, persisted in an outbox, replayable — so
putting the prose in it would make that exclusion unenforceable downstream no matter how
carefully each consumer behaved. The rule is now recorded in three places that carry the
data: the column, the contract, and the audit snapshot. A test asserts the outbox row does
not contain it.

### `ReviewModerated` v1 — a deliberate addition, recorded rather than silent

The roadmap names only `ReviewCreated`. Shipping only that would leave **moderation
decorative for ranking**: a review hidden for abuse would keep its rating in
`search.ranking_signals` forever, because the counter was moved by an event that already
happened and nothing would undo it. A provider would then be ranked on reviews no longer
visible to the customers deciding whether to book them.

That is precisely the QA-18 bug class — a signal whose writer does not match reality — which
this phase exists to close. Closing half of it would have been worse than not noticing.

Consumers: search (compensating signal, both directions), analytics. Not loyalty — see §9.

## 6. Search — QA-18

The gap register's own words: *"The fix is a consumer, not a feature."* That is exactly what
this is. `rating_sum` / `review_count` have existed since Phase 3, and the Bayesian shrinkage
term, the `high_rating` badge, the `minRating` filter and the `rating` sort were all built
against them and have been inert at 0/0 ever since. **Not one line of `ranking.ts` changed.**

`applyRatingSignal` is separate from the existing `applySignal` because the shape is
genuinely different: the counter signals move one column by one, while a rating moves two
columns by an amount the event carries. Folding a value-carrying signal into a fixed column
map would have meant a fake column name or a second meaning for the same parameter.

**`GREATEST(0, …)` on the subtraction is load-bearing, not defensive habit.** The CHECK
constraint forbids a negative `rating_sum`, and a compensating signal can legitimately arrive
with no matching increment — most obviously after a projection rebuild resets the counters.
Without the clamp that raises a constraint violation, the handler throws, the outbox row
never publishes, and the relay retries it forever: one impossible subtraction would wedge
every event behind it. Clamping degrades to a slightly-wrong counter the next rebuild
corrects, and logs it. A test drives that exact case.

**No index mapping change and no reindex.** `ratingAvg` and `reviewCount` were already in the
mapping; only their values were always zero. `PROVIDER_INDEX_MAPPING_VERSION` stays at 2.

### One stale comment left deliberately unmodified

`database/migrations/search/20260820200004_create_search_schema.sql` says of these columns:
*"NO V3 PRODUCER WRITES THESE YET."* That is now false. It is **not** edited, because
historical migrations are immutable — a migration is a record of what was applied, and
rewriting one to read better today breaks the reproducibility every release depends on. The
claim is corrected here and in `ranking.ts`'s docblock, which is code rather than history.

## 7. Security

| Route | Auth | Authorization | Concurrency | Audited |
|---|---|---|---|---|
| `POST /v1/bookings/:id/review` | required | eligibility row's `customer_id` must equal the session | UNIQUE index refuses the second | no |
| `GET /v1/providers/:id/reviews` | **public** | published only | — | no |
| `GET /v1/me/reviews` | required | scoped to the session's own id | — | no |
| `POST /v1/providers/:id/reviews/:reviewId/respond` | required | `@ResolveOwner` **and** service-level `professionalId` scoping | last write wins (own text) | no |
| `GET /v1/admin/reviews/queue` | required | `bc_moderate_reviews` + live re-check | — | read |
| `POST /v1/admin/reviews/:id/moderate` | required | `bc_moderate_reviews` + live re-check | CAS, see BUG-D-01 | **yes**, same transaction |

**Enumeration.** "No such booking", "not completed", and "not yours" all produce one
identical `REVIEW_NOT_ELIGIBLE`. A customer who could distinguish them would have an oracle
for other people's booking ids and their states. Asserted byte-for-byte by a test.

**The reviewer's identity is not public.** `customerId` is absent from the public review
shape. Publishing it would let anyone assemble one customer's entire visit history across
every professional they have ever booked, from public data alone. The author sees their own
review's state via `GET /v1/me/reviews`; a moderator sees it in the queue; nobody else does.

**Free-text handling.** The review comment, the professional's reply, and the moderator's
reason are all free text and all excluded from event payloads and audit snapshots. A
moderator does read the comment in the queue — deciding whether it should stay up is the
whole job — and that is the only surface where it appears beyond the author and the profile.

## 8. Bugs discovered and fixed

### `BUG-D-01` — a second `hide` overwrote the audit trail (found by the concurrency test)

The moderation compare-and-swap was `WHERE id = :id AND status = :fromStatus`, with
`fromStatus` read at the top of the transaction. That correctly handles two moderators whose
transactions **overlap**: the second blocks on the row lock, re-evaluates against the newly
committed row, and matches nothing.

It did not handle the **sequential** case. A second moderator pressing `hide` on an
already-hidden review reads `fromStatus = 'hidden'`, computes `toStatus = 'hidden'`, and its
CAS matches its own no-op — so the decision "succeeded", a second audit row was written, and
`moderated_by` was overwritten. The takedown would be attributed to whoever pressed the
button last.

Found because the concurrency test's two requests did not in fact overlap, and the test
failed for a better reason than the one it was written for.

**Fixed** with `AND (status <> :toStatus OR moderated_at IS NULL)`, which refuses a decision
that changes nothing on an already-triaged review while preserving the one legitimate no-op
transition — keeping an untriaged review public.

### `BUG-D-02` — a test asserted the wrong property (found by the test failing)

The first version of the shrinkage assertion compared a 1-review provider against a
250-review one with no other evidence, and expected the larger base to score higher. It
failed, and it was right to: `evidence = reviewCount + completedBookings` drives the
cold-start blend, so that comparison measures evidence volume rather than the Bayesian term,
and the newcomer is legitimately pulled *up* toward the 0.55 baseline.

The existing `ranking.spec.ts` already had this right, with `completedBookings: 50` and a
comment explaining why. **The duplicate was removed from the pg suite rather than fixed** —
it is pure-function logic already proven in the fast suite, and duplicating it in the serial
real-database suite costs wall-clock for no new information.

Recorded because it is the kind of near-miss worth naming: a test that "passes" by measuring
something other than what its name claims is worse than no test.

## 10. UI implementation status

**NOT IMPLEMENTED — the UI remains intentionally frozen.**

No page, token, component, or navigation entry changed. Zero files under `apps/web` were
modified.

One **additive** API change: every professional shape now carries
`rating: { average, count }`, always present, `average: null` when nobody has reviewed —
the same always-present-with-explicit-nulls treatment `images` received in Phase C, and for
the same reason.

**Phase D's roadmap Definition of Done is therefore partially met**, and the split is exact:

- ✅ `search.ranking_signals.review_count > 0` for a real provider — asserted by test.
- ✅ `high_rating` awarded for the first time in the project's history — asserted by test.
- ❌ `minRating` and the `rating` sort "exposed in the UI" — the API returns sensible results
  for both; no screen calls them.

Everything the eventual UI needs is in `PHASE_D_CLAUDE_DESIGN_HANDOFF.md`.

modified. Applied from zero and re-run: **`Applied: 0`** on the second pass.

Constraints doing real work rather than documenting intent:

- `reviews.booking_id` → `review_eligibility(booking_id)` — "no review without a completed

- `uq_reviews_booking` — "one review per booking", refusing the second under concurrency.
- `ck_review_rating` — 1–5, matching `rating_sum`'s INTEGER assumption in search.
- `ck_review_response` — a reply has a time, or there is no reply. No half-written response.
- `ck_review_moderation` — a hidden review has a moderator and a timestamp. There is no such
  thing as an unattributable takedown.
- `ix_reviews_untriaged` — the queue, as a partial index.

## 12. Concurrency and idempotency

| Workflow | Two simultaneous requests | Mechanism |
|---|---|---|
| review submission | one review, one 201, one 409 | UNIQUE index on `booking_id` |
| eligibility from a redelivered event | written once | `booking_id` is the PRIMARY KEY; `ON CONFLICT DO NOTHING` |
| rating signal | applied once per event | `signal_applications (event_id, signal)` |
| moderation | one decision, one audit row | CAS on status **plus** the untriaged clause (BUG-D-01) |
| moderation redelivery | compensates once | distinct signal name per direction |
| loyalty award | awarded once | ledger UNIQUE on `(reference_type, reference_id, reason)` |

Every one of these is driven by a test that replays the event or fires two concurrent
requests, not asserted from the code's shape.

## 13. Tests

`apps/api/test/reviews.pg-spec.ts` — **27 cases** against real PostgreSQL over real HTTP.

Bookings are created through `BookingService` and completed through the real
`POST /v1/bookings/:id/complete`, so `BookingCompleted` comes from its real producer. An
earlier version of the helper inserted the outbox row by hand; that was rejected because
eligibility is the thing under test, and a hand-written event would have proved the review
path works when given a well-formed event while proving nothing about whether one is ever
produced.

Adversarial and invariant cases specifically: a review for a booking that never completed; a
review of somebody else's booking (byte-identical refusal); a second review for one booking;
**two concurrent submissions racing**; a direct `INSERT` bypassing the service (refused by
the foreign key); a rating outside 1–5; a reply to another professional's review, tested
through **both** the ownership guard and the service-level scoping independently; a reply
from a customer; a customer and a `platform_operator` reaching the moderation queue; **two
moderators deciding simultaneously**; event redelivery for the rating signal, the
compensating signal, the eligibility row and the loyalty award; an unmatched compensation
driving counters negative; and the review text appearing in neither the outbox payload nor
the audit snapshot.
