**Baseline:** `feb12be` = `origin/master`. `v3.1.0` (`7196041`) and every earlier tag untouched.
**Scope:** the BACKEND half of `V3.1_PRODUCT_ROADMAP.md` §15's Phase C. No release tag created.
**Frontend:** intentionally not implemented — see §9.

## 1. Why this phase, and how that was determined

`V3.1_PRODUCT_ROADMAP.md` §16 sequences the phases as **B + G → A → C → D → E → F**.
`V3.1_PHASE_A_IMPLEMENTATION.md`, `V3.1_PHASE_B_IMPLEMENTATION.md`, and
`V3.1_PHASE_B_G_FINAL_QA.md` record A, B, and G as complete and released as `v3.1.0`.
A repo-wide search confirms C is genuinely unstarted: before this phase there was no
`media` schema, no `provider.portfolio_items`, no storage adapter, and no match for
`presign`, `S3`, or `upload` anywhere in `v3/` outside `node_modules`.

**C is therefore next.** `V3.1_RELEASE_STRATEGY.md` §1 assigns it to a future `v3.1.1`;
that tag is **not** created here.

### The dependency that had to be resolved before starting

The roadmap states Phase C's dependency as "Hosting decision (#1) → storage provider", and
`R31-03` says the same more precisely: *"Dependencies. Hosting/region decision — **provider
choice** is downstream of it."*

Provider **choice** — not architecture. `V3_INFRASTRUCTURE_PLAN.md` §5 already fixed the
architecture as "S3-compatible, Iran-reachable provider (ArvanCloud/Liara-class)", and the
roadmap's own reuse assessment (§18) says the adapter is a "new adapter behind a port,
following `PaymentProvider`/`NotificationChannelPort`'s established shape". What decision
`#1` actually produces is an endpoint, a bucket, a region, and a credential pair.

That is **EXTERNAL CONFIGURATION**, and it is classified as such rather than being converted
into an implementation decision. The engineering was done against the architecture that was
already decided; no vendor was selected by this phase, and none is named anywhere in the code.

## 3. What was built

### 3.1 `libs/media` — a new shared library

Placed in `libs/`, not `services/`, and the reasoning is in ADR-026 §5: media is
infrastructure with no business rules of its own, and `libs/audit` is the exact precedent —
it owns the `admin` schema, has an entity and a service, and is injected directly into
`provider`'s `VerificationService`.

| File | What it is |
|---|---|
| `storage/object-storage.port.ts` | The driver interface. Three rules every driver honours, all security properties. |
| `storage/local-object-storage.driver.ts` | Filesystem-backed. `durable: false`. Real, not a stub. |
| `storage/s3-object-storage.driver.ts` | S3-compatible over plain HTTP + SigV4. `durable: true`. |
| `storage/sigv4.ts` | AWS Signature V4, query flavour. Hand-written; see §6. |
| `storage/upload-grant.token.ts` | The local driver's signed upload credential. |
| `image-probe.ts` | PNG/JPEG/WebP identification and intrinsic dimensions, pure TS. |
| `media-policy.ts` | One table: purpose → access class, size cap, quota, dimension bounds. |
| `media.service.ts` | The lifecycle, and the only place that decides what is acceptable or reachable. |
| `media.controller.ts` | `/v1/media/*` and `/v1/admin/media/*`. |
| `testing/image-fixtures.ts` | Byte-accurate PNG/JPEG/WebP/PDF/SVG fixtures, shared by two projects. |

### 3.2 The lifecycle

Presigned direct upload means the API never sees the request body. Three steps follow from
that, and every content rule lands in the third:

```
POST /v1/media/upload-url    quota + caps + an unguessable key + a `pending` row
                             + a target scoped to ONE key, with an expiry
PUT  <target>                bytes go to the store (or, on the local driver, back to a
                             signed-token route on this API)
POST /v1/media/:id/finalize  the object is read BACK, sniffed, measured, then `stored`
```

Nothing in the product may reference an object that is not `stored`.

### 3.3 Two access classes

`MEDIA_POLICY` maps purpose → access class, and the class is denormalized onto the object
row **at creation**, so a later policy edit cannot retroactively reclassify stored objects.

- `public` — portfolio, avatar, cover. Permanently addressable, cached `immutable`.
- `protected` — verification evidence. **No public URL exists**, at any layer. Reachable only
  through `GET /v1/media/:id/content?token=…`, which re-authorizes the viewer named in the
  token against live data on **every** request.

## 4. Security

### 4.1 Every new mutation

| Route | Auth | Authorization | Idempotent | Audited |
|---|---|---|---|---|
| `POST /v1/media/upload-url` | required | owner = session; quota + pending bound | n/a | no (not privileged) |
| `PUT /v1/media/upload/:token` | token | one key, one content type, one size, expiring; row must be `pending` | yes | no |
| `POST /v1/media/:id/finalize` | required | owner re-derived from the row | **yes** — returns the stored object unchanged | no |
| `POST /v1/media/:id/report` | required | public + stored objects only | one open report per (object, reporter), by partial unique index | no |
| `POST /v1/admin/media/reports/:id/decide` | required | `bc_moderate_media` + live re-check | **yes** — CAS on `status='open'` | **yes**, same transaction |
| `POST /v1/providers/:id/portfolio` | required | `@ResolveOwner` **and** media claim | no | no |
| `DELETE /v1/providers/:id/portfolio/:itemId` | required | `@ResolveOwner` + scoped by professional | yes | no |
| `PATCH /v1/providers/:id/avatar` / `/cover` | required | `@ResolveOwner` + media claim | yes | no |
| `POST /v1/verification/evidence` | required | professional resolved from session; own `pending` request only | no | no |

### 4.2 The two-check rule for attachment

Every route that accepts a media id performs **two independent authorization checks**,
because they answer two different questions:

1. `@ResolveOwner(ProviderOwnerResolver)` — *is this profile yours?*
2. `MediaService.claimForAttachment` — *is this upload yours, finalized, and of this purpose?*

Neither implies the other. The first would happily attach somebody else's image to your
profile; the second would happily attach your own image to somebody else's profile. Both
failures return the identical `NOT_FOUND_OR_NOT_YOURS`, so the endpoints cannot be used to
discover which media ids exist. Both directions are covered adversarially by tests.

The **purpose** check in (2) is load-bearing beyond tidiness: purpose is what decided the
access class, so a `verification_evidence` object can never become a portfolio item and
therefore can never become publicly addressable.

### 4.3 The protected-download model (`V3_SECURITY_MODEL.md` §8, point by point)

| §8 requirement | How |
|---|---|
| stored outside any publicly-addressable, predictable path | key is `protected/<purpose>/<uuidv7>`; no driver produces a public URL for a protected object, and `describe()` returns `url: null` for one regardless of driver |
| access control re-checked on **every single request** | `resolveProtectedDownload` re-reads the row and re-runs `canView` per request; capability is read live via `PrivilegedCapabilityVerifier` |
| capability is a random, unguessable token, never a sequential id, never derived from the filename | HMAC-SHA256 over `{mediaId, viewerUserId, expiry}`; the key is `uuidv7()` and nothing in it comes from the uploader |
| content-sniff server-side; never trust client MIME or extension | `probeImage` against bytes read back from the store |
| carry the token IN THE URL for GET-navigated downloads (the real V2 CSRF bug §8 records) | `?token=` on a `@Public()` route; ambient cookie auth is deliberately not relied on |
| metadata visibility ≠ raw content access | listing evidence is gated on `bc_moderate_verification`; reading it requires a separately minted, separately re-authorized token |

**Why a moderator may read evidence at all**, given §8 also says a general moderation
capability must not confer downloading another user's private files: verification evidence is
submitted **for review**. Reviewing it is the purpose of the submission, and the professional
knows that when they upload it. That is a different thing from a privacy-export archive,
which is generated for the subject alone — and Phase E must keep those moderator-invisible,
exactly as V2 did. The distinction is recorded here so Phase E inherits the rule rather than
rediscovering it.

### 4.4 The new capability

`bc_moderate_media`, privileged, granted to `moderator` and `administrator` and **not** to
`platform_operator`.

This is not a new policy. It applies the reasoning
`20260824100001_create_roles_and_capabilities.sql` already recorded when it decided
`platform_operator` should hold `bc_moderate_verification` but not `bc_moderate_reviews`:
deciding whether a professional is who they claim to be is the operational tier's work;
removing somebody's published work from the marketplace is content moderation. Folding the
second into the first would hand every platform operator takedown authority as a side effect
of being able to approve a verification. A test asserts a `platform_operator` is refused.

Being on `PRIVILEGED_CAPABILITIES` gives it both properties that list confers: the live
revocation re-check in `CapabilityGuard`, and `libs/audit`'s refusal to boot if a mutation
gated on it declares no audit record.

### 4.5 Abuse and takedown

`media.abuse_reports`, reportable only for `public`, `stored` objects — accepting a report
against a protected id would confirm to the reporter that an id they cannot see exists. An
upheld report marks the object deleted, records `taken_down_by` (so a takedown is
distinguishable in the data from the owner deleting their own work), removes the bytes, and
writes an audit row — **all in one transaction**, which is GAP-02-V3's property applied to a
mutation that removes somebody else's content.

## 5. Events

### One new contract: `ProfessionalMediaChanged` v1

**This is a deliberate, recorded deviation from the roadmap**, which proposed
`PortfolioItemAdded` v1.

The roadmap's own stated consumer need is *"a provider with work shown is a different search
result than one without"* — a **projection** need, which an `-Added` event cannot serve. It
has no way to express an item being removed, an avatar being replaced, or a moderator taking
an image down, so each would need a sibling event and the consumer would have to reconstruct
the current set by replaying all four in order. At-least-once, unordered delivery cannot
promise that.

`ProfessionalUpdated` solved this exact problem in Phase 3 and its docblock says why: *"A
full snapshot plus a revision is self-sufficient: the newest one wins and nothing needs
replaying."* `ProfessionalMediaChanged` is that pattern applied to imagery.

It is a **separate** event rather than new fields on `ProfessionalUpdated` because the
contract registry forbids editing a published payload — a change is a new version, and
bumping that contract to v2 would force a migration on every one of its consumers for a
change none of them care about.

Both events carry the **same** per-professional `revision` counter, so they remain orderable
against each other; they simply own disjoint columns, which is what stops a bio edit blanking
an avatar. Asserted directly by a test.

## 6. Verification of the S3 driver

The signing is hand-written. `sharp`-style reasoning applies in reverse here: the honest risk
of hand-writing a signing algorithm is that it looks right and is wrong, and a unit test
comparing its intermediate strings against values the same file produced would be a tautology
dressed as verification.

So `media-s3.pg-spec.ts` performs **real HTTP against a real S3-compatible server** (MinIO,
now a CI service container): bucket creation with this codebase's own signer, presigned PUT,
HEAD, ranged GET, DELETE — plus the three refusals that make a grant a grant:

- an upload whose content type differs from the one that was **signed** → 403
- an expired target → 403
- a target **repointed at another key** by editing the URL → 403

A wrong signature cannot pass any of these.

**`content-length` is deliberately not among the signed headers.** Signing it would let the
store itself reject an oversized upload, which is strictly better — but support varies across
S3-compatible vendors, and the vendor is exactly what has not been chosen. The size cap is
therefore enforced where it is enforceable against every driver: at finalize, against the size
the **store** reports, with the object deleted when it exceeds it. A per-user bound on
outstanding `pending` grants limits what can be in flight meanwhile. Disclosed rather than
papered over.

## 7. Bugs found

### `BUG-C-01` — the OpenSearch mapping version was inert (pre-existing, fixed here)

`SearchIndexerService.currentPhysicalIndex()` returned the physical index named in
`search.index_state` and **never looked at `mappingVersion`**. `PROVIDER_INDEX_MAPPING_VERSION`
has existed since Phase 3, is documented as *"bumped whenever the mapping changes in a way
that requires a reindex"*, and the machinery to act on it (`fullReindex`, which already writes
the new version into the state row) was fully built. Nothing connected the two.

**Impact if it had shipped unnoticed:** the provider index is `dynamic: 'strict'`, so an index
created under version 1 *rejects* a document carrying `avatarUrl`. Every flush would have
failed with a mapping error — not a stale index that self-heals, which is the degradation the
rest of that class is designed around, but a hard error on every sweep with dirty rows piling
up behind it.

**Found by:** bumping the mapping for this phase and asking what would actually happen on a
deployment that already had an index.

**Fixed:** `staleMappingVersion()`, consulted by `ensureAliasReady()` before any write, which
rebuilds into a new physical index rather than writing into one that cannot accept the
documents. A version *newer* than the running build is left alone and logged — that means a
newer instance has already reindexed, and rolling the mapping back under it would be worse.

**Classification:** a latent defect in code released in `v3.0.0`, not part of this phase's
feature scope. It is fixed here because this phase is the first that makes it reachable.

### `BUG-C-02` — the privileged-capability verifier was invisible to imported modules (introduced and fixed within this phase)

`PRIVILEGED_CAPABILITY_VERIFIER` was bound as a provider on `AppModule`. A provider declared
in a module's own `providers` array is visible to that module's controllers and providers, and
to **nothing it imports**. `CapabilityGuard` is an `APP_GUARD` registered on `AppModule`, so
the arrangement worked for the guard and only for the guard.

`MediaService` is the second consumer, and its `@Optional()` injection resolved to `undefined`
— so `viewerHasCapability` correctly failed **closed** and refused every moderator every
document. Nothing was ever wrongly authorized; the feature simply did not work. Found by the
suite, not in production.

**Fixed:** `PrivilegedCapabilityModule`, `@Global()`, one binding, unchanged fail-closed
behaviour.

### `BUG-C-03` — the protected-download path segment was decorative (found by an adversarial test, fixed here)

`resolveProtectedDownload` resolved the object from the **token's** claims and ignored the
`:id` in the path, so a valid token for object B presented at object A's URL returned B with a
200.

Not a privilege escalation — the token is minted for one object and one viewer, and the
`canView` re-check is what enforces authorization — but it is the confused-deputy shape, and
it meant every log line, cache key, and error report downstream named the wrong object. Now
the path and the token must agree.

### `BUG-C-05` — a taken-down image left its portfolio item unremovable (found in review, fixed here)

Upholding an abuse report marks the media object `deleted` and leaves the portfolio item
behind with `media: null`, which is correct. But `removeItem` deleted the item **and** the
object, and the object deletion refused an object that was already `deleted` — so the
professional could never clear the leftover item. Replacing a taken-down avatar failed the
same way.

A dead end reachable entirely through supported actions, and one the owner could not get out
of. `markDeletedOwnedIfLive` now treats "already gone" as an answer rather than a failure,
while still checking ownership; two regression tests drive the full report → uphold → remove
path and the avatar equivalent.

### `BUG-C-04` — an oversized upload reset the connection instead of answering (found in test, fixed here)

The first implementation of the local driver's body limit called `request.destroy()` on
exceeding the declared size. That is a connection reset, not a diagnosable refusal: an
uploader cannot tell a rejected file from a broken network. Now the remainder is **drained and
discarded** — memory stays bounded, which is the actual goal — while the connection stays
healthy enough to carry a 400 back.

## 9. UI implementation status

**NOT IMPLEMENTED — the UI remains intentionally frozen.**

No page was redesigned, no visual token changed, no component replaced, no screen added. The
only frontend-visible change is an **additive** one to an existing API contract: every
professional shape now carries `images: { avatar, cover }`, always present, `null` when
absent. No existing client breaks; nothing was removed or renamed.

Everything the eventual UI needs to represent — routes, request and response shapes, states,
permissions, empty/loading/error cases, business rules, and what is deliberately unavailable
— is documented in `PHASE_C_CLAUDE_DESIGN_HANDOFF.md`. This phase describes what the UI must
show; it does not decide how it should look.

Consequently **Phase C's roadmap Definition of Done is not met**, and that is stated plainly
rather than implied: it requires a professional to upload portfolio work and an avatar and see
both render with zero layout shift, which needs screens that do not exist. The backend half is
complete and verified; the visual half is deferred to the Claude Design workflow by explicit
instruction.

- `uq_portfolio_media_live` — one media object backs at most one live item, so deleting one

- `uq_portfolio_position_live` — a concurrent double-add fails loudly instead of producing two

- `uq_media_report_open_per_reporter` — one user cannot inflate a queue a human has to read.

Applied from zero and re-run: **`Applied: 0`** on the second pass — idempotent, verified
against a real PostgreSQL 16 server.

## 11. Concurrency and idempotency

| Workflow | Two simultaneous requests | Mechanism |
|---|---|---|
| finalize | one transition; the second returns the stored object | CAS on `status='pending'`, then a re-read |
| portfolio add | one wins the slot; the other fails loudly | partial unique index on `(professional_id, position)` |
| avatar replace | last writer wins; neither leaks the old object | superseded object marked deleted inside the same transaction |
| abuse decision | one decision, one audit row | CAS on `status='open'` |
| media projection | newest revision wins; a stale redelivery writes nothing | `WHERE revision <= :incoming` guard, tested with an out-of-order redelivery |
| grant reaping | a row is reaped once | CAS on `status='pending'` before the byte delete |

**Ordering of row-versus-bytes is deliberate everywhere and always the same way round:** the
row is marked inside the caller's transaction, the bytes are removed after it commits. The
reverse would mean a rolled-back deletion leaves a live portfolio item pointing at bytes that
are gone — a broken image on a live profile. A failure to delete bytes leaves an orphaned
object, which is an operational cleanup problem rather than a correctness one, and is logged.
