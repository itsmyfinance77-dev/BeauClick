# V3.1 Task 1 — Professional Operating Surface

**Status:** COMPLETE. The full Definition-of-Done trace was run end to end in a real
browser against a real API and a real PostgreSQL 16 database.

**Baseline at start:** `HEAD` = `origin/master` = `v3.0.1` = `68d3d5e`.
`v3.0.0` (`cfecfdf`) and `v3.0.1` untouched. No historical tag touched. No `v3.1.0` tag
created. V2 / WordPress / WooCommerce untouched — zero diff against `wordpress/`, `app/`,
`shared/`.

**Scope:** the seven-screen `/pro` route group, the UI primitives it needed, and the three
thin API routes without which it could not exist. Nothing from Phases A, C, D, E, or F was
started.

---

## 1. The one thing that changed

`BookingCompleted` is now reachable through the product.

Before this task, completing a booking was a professional-only action with no interface, so
the event could only be produced by a test. Five consumers were wired to it and none had
ever fired from a real product path: loyalty points, the journey timeline, the
`completed_bookings` ranking signal, review eligibility (once Reviews exist), and referral
qualification (once Referrals exist). That is why this task was sequenced first, and the
live trace in §11 is the evidence it worked.

## 2. Baseline audit — what already existed

Verified by reading the current source, not by trusting the roadmap. Nine professional
capabilities were built, ownership-gated, and covered by real-PostgreSQL tests, with **no
frontend at all**:

| Capability | API | Authorization | Existing tests | Was missing |
|---|---|---|---|---|
| Profile create | `POST /v1/providers` | session-derived `ownerId`, never from body | `provider.service.spec`, `real-postgres.pg-spec` | UI |
| Profile edit | `PATCH /v1/providers/:id` | `ProviderOwnerResolver` + `ownerId` in WHERE | same | UI |
| Service create | `POST /v1/providers/:id/services` | `ProviderOwnerResolver` | `provider.service.spec` | UI |
| Service edit / delete | **service layer only** | `professionalId` in WHERE | — | **HTTP route + UI** |
| Availability list/create/bulk/delete | `/v1/me/availability*` | session→`professionalId` via port | `booking-*.pg-spec` | UI |
| Professional bookings | `GET /v1/me/professional-bookings` | session→`professionalId` | `booking-lifecycle.pg-spec` | UI |
| Complete / no-show | `POST /v1/bookings/:id/{complete,no-show}` | `BookingProfessionalResolver` | `booking-lifecycle.pg-spec` | UI |
| Reschedule / history | `POST .../reschedule`, `GET .../history` | `BookingPartyResolver` | `booking-lifecycle.pg-spec` | UI |
| Finance | `/v1/me/finance/*` (4 routes) | party resolved internally (GAP-05) | `financial-integrity.pg-spec` | UI |
| Analytics | `/v1/me/analytics`, `/series` | subject resolved via port | `analytics-isolation.pg-spec` | UI |
| Notifications | `/v1/me/notifications/*` | session-scoped | `notification-delivery.pg-spec` | already had UI |

**Three gaps made the surface impossible to build without touching the backend**, and each
is a thin controller over an already-tested service method rather than new capability:

1. **A professional could not discover their own `professionalId`.** Nothing returned it.
   Every `/v1/providers/:id/...` route was therefore unaddressable by its own owner.
   `ProviderService.findByOwnerId()` had existed and been tested since Phase 1 with no
   route. → `GET /v1/me/provider`, mirroring `GET /v1/me/business` exactly, `null` (not
   404) when none exists.
2. **Service edit and delete had no HTTP route.** `ServiceOfferingService.update()` and
   `.remove()` are transactional and event-emitting since Phase 3, and unreachable. A
   professional could add a service and never correct its price. → `PATCH` / `DELETE
   /v1/providers/:id/services/:serviceId`.
3. **No endpoint listed cities or specialties.** The only source was search FACETS, which
   are derived from indexed providers — so on a marketplace with no indexed providers the
   pickers were empty and a professional could not name their own city or specialty at all.
   `V3_DOMAIN_BOUNDARIES.md` §provider names `GET /v1/specialties` and it was never built.
   → `GET /v1/cities`, `GET /v1/specialties`, both public read-only.

No new table, no migration, no new event contract, no change to any existing contract.

## 4. Professional context

The UI/UX audit recorded that V3 has "no visual distinction between customer, business, and
(absent) professional contexts". This task adds the third context, so it establishes the
pattern: `ProShell` renders a tinted band directly under the app header carrying the mode
badge (**حالت متخصص**), the professional's display name, their verification status, the
mode's own seven-item nav with `aria-current` on the current page, and a permanent
**بازگشت به نمای مشتری** exit.

It sits *inside* the existing `AppShell` rather than replacing it. A separate chrome would
mean a second header, a second nav, a second skip-link target, and a second place for the
notification badge to drift — a second design system by accretion.

**The verification badge is honest about a real gap.** No route anywhere in V3 moves a
professional past `unverified` (`R31-02` in the reconciliation), so every professional sees
**تأیید نشده** permanently. Showing the true status is correct; implying the user can act on
it would not be, so the badge carries no call to action and the profile page says the status
is set by platform review.

## 6. Timezone handling

This was the most technically sensitive part of the task, and it needed new code.

`AvailabilityService` materializes every slot from a wall clock in **`Asia/Tehran`**
(`services/booking/src/availability/platform-time.ts`). But `persian-utils`'
`formatShortDate` / `formatFullJalaliDate` / `formatTime` read a `Date` through
`getFullYear()` / `getHours()`, which resolve in **whatever zone the browser happens to be
in** — a documented, deliberate choice there, and correct for a user in Iran on a machine
set to Iran.

It is not correct for this surface. A professional publishing "۰۹:۰۰" means 09:00 in Tehran
regardless of their laptop's clock. A traveller, a misconfigured machine, or a QA browser in
UTC would each see a different hour for the same slot and would publish or release slots
they did not intend.

**Resolution: a new, additive `zoned.ts` module** that names the zone explicitly, mirroring
the backend's own converter (IANA rules via `Intl`, two-pass offset resolution — not a
hardcoded +03:30, because Iran abolished DST in 2022 and that policy can be reversed). The
`/pro` surface formats and parses through it; **every existing customer-facing call site is
untouched**, because changing their behaviour is not this task's to make.

The latent inconsistency in the customer surfaces is recorded as a finding, not fixed here.

Verified against the real database: a slot published as ۰۹:۰۰ stores as `05:30 UTC` /
`09:00 Asia/Tehran` and renders back as ۰۹:۰۰ (§11).

## 7. Security

Every route this surface calls is either a `/v1/me/...` route that **takes no owner
identifier at all**, or a `/v1/providers/:id/...` route guarded by `ProviderOwnerResolver`,
which reads the row's real `ownerId` from the database and compares it against the session.
No authorization logic was duplicated in the frontend. No `professionalId`, `businessId`, or
`partyId` is ever sent as an ownership source.

**Adversarial coverage** (`professional-surface.pg-spec.ts`, 29 cases, all passing):

- `GET /v1/me/provider` never returns another user's profile, even when one exists; the
  response is asserted not to contain the other id anywhere.
- Professional B editing A's service **via A's provider id** → `NOT_FOUND_OR_NOT_YOURS`
  (ownership guard).
- Professional B editing A's service **via B's own provider id** → `NOT_FOUND_OR_NOT_YOURS`
  (the second check, in the service's own WHERE clause). *This is the case a
  controller-only check would miss, and it is the one that found a real defect — see §9.*
- Deleting another professional's service leaves it intact; a repeat delete gets the generic
  refusal rather than reporting success twice.
- A customer cannot complete a booking; an unrelated professional cannot complete or read
  the history of one.
- Releasing a **booked** slot is refused with the slot left booked; releasing another
  professional's slot is refused.
- A reschedule onto another professional's slot is refused and that slot stays open.

## 9. Bugs found

Five, of which **two are pre-existing defects in shipped code** and three were mine, caught
before merge.

### 9.1 — CORS blocked `Idempotency-Key`, so browser checkout has never worked · PRE-EXISTING · HIGH

`POST /v1/bookings` requires an `Idempotency-Key` header (`checkout.controller.ts:51`) and
`booking-api.ts:109` sends it — but `main.ts`'s CORS `allowedHeaders` never listed it. A
cross-origin request carrying a header the server does not allow is **rejected at
preflight**; the POST is never issued.

**Consequence: customer checkout fails in every real browser whenever the API and web app
are on different origins**, which is the deployed topology. Every existing test passed
because supertest sets headers directly and no preflight exists.

This is precisely the class Phase 1 recorded when CORS was found entirely unconfigured:
*"API-only testing cannot surface browser-enforced policy; live browser verification is not
redundant with e2e tests."* It recurred, in the same file, for the same reason.

Fixed by adding the header to the allow-list. Widening it grants nothing: the key is a
client-chosen opaque string whose only effect is to make a repeat of the caller's own
request return the caller's own first result, and `findByIdempotencyKey` is scoped by
customer id as well as key. **This fix was strictly required to run the mandated
Definition-of-Done trace** — it is reported here rather than folded in silently.

### 9.2 — Service update returned 500 for a foreign service id · INTRODUCED THEN FIXED

`ServiceOfferingService.update()` used `findOneOrFail`. That was harmless while the method
had no HTTP route; the moment this task gave it one, TypeORM's `EntityNotFoundError` reached
the exception filter and became a **500**. A 500 both looks like a crash and is
distinguishable from the response a well-formed nonexistent id gets — the existence leak
`V3_SECURITY_MODEL.md` §3 forbids. Found by the adversarial spec case, not by review. Fixed
with `findOne` + `NotFoundOrNotYoursException`.

### 9.3 — `OutstandingOrder` declared three fields the API never returns · MINE

I wrote `{ orderId, amountToman, currency, occurredAt }`. The real shape is
`{ orderId, outstandingToman }`. `new Date(undefined)` threw `RangeError: Invalid time
value` and the error boundary swallowed the entire finance screen.

**Typecheck could not catch this**: a hand-written response type is an *assertion* about the
server, not a check of it, and the compiler faithfully verified the UI against a shape that
was wrong. Found only by opening the page in a browser.

### 9.4 — `SeriesResponse` had the wrong value field · MINE

I wrote `{ day, value }`; `MetricsService.dailySeries` returns `{ day, count, sum }`. The
chart rendered a literal `undefined` next to every date. Same class as 9.3, found the same
way.

### 9.5 — A completion refused by the server left the card showing stale state · MINE

`complete()` on a booking the customer cancelled a moment earlier throws
`InvalidBookingTransitionException` → 409 (deliberate: `booking.service.ts:716` explains
that `onIllegal: 'throw'` suits human-initiated actions, while `'report'` exists for the
payment path where throwing would roll back a real charge). My screen showed the error but
kept the stale "تأیید شده" card. Now it reloads on a rejected action, so the true state
replaces the stale one. Found by a spec case whose original assertion was wrong about the
API — the code was right and the test was not.

### Failure paths verified live

- A **booked** slot offers no delete control at all, only "برای آزاد کردن، رزرو را لغو کنید".
  Not a disabled button: a control that never works is worse than an explanation. The server
  enforces this independently (`deleteSlot` matches `status='open'`), proven in the spec.
- **No-show** is not offered before the slot ends, and the rule is stated.
- **Reschedule** is not offered past the cap or inside the notice window, and the rule is
  stated with the real numbers.
- Submitting a malformed phone produced the correct Persian message in `role="alert"` and
  re-enabled the form (encountered accidentally, verified deliberately).

### What live QA could NOT isolate, stated rather than omitted

With the API stopped, `ProtectedRoute` redirects to `/auth` before any screen mounts, so the
**in-app failed-load states cannot be reached in the browser** — the session guard fires
first. Those five states (profile, guard, services, availability, bookings) are covered by
dedicated component tests that mock a successful session restore and a failing resource
call, which is the level at which the distinction is actually testable. No browser claim is
made for them.

Colour contrast was not measured; no screen-reader testing was performed. Both remain open
in `V3.1_UIUX_BACKLOG.md`.

## 13. Known limitations

- **The booking API exposes no customer identity beyond a UUID** — no name, no phone, by
  design. The professional's booking card shows a truncated reference rather than inventing
  an identity. A real "who is this customer" story needs a product decision about what a
  professional may see.
- **Verification is display-only** (`R31-02`), so every professional is `unverified`
  permanently until Phase A.
- **Business owners still cannot manage a staff professional's bookings or availability** —
  ADR-023's disclosed scope boundary, unchanged.
- **Reschedule is same-provider, same-service, different-slot only** — the backend's own
  constraint, surfaced faithfully.
- **`persian-utils`' original date helpers still read host-local time.** Only the `/pro`
  surface is zone-explicit. The customer surfaces' latent inconsistency is recorded, not
  fixed.
- **The local dev database is a container provisioned for this task.** It is not the
  `HOSTING_GRANTS` verification against a real target provider, which remains open.
