## 1. What this phase actually found

The brief asked for completion, and completion is most of what happened. But verifying
"what is already there" against the running product turned up four defects that were not
on any list, and two of them matter more than anything that was:

- **Every customer on a UTC-hosted deployment has been told the wrong appointment time.**
  Not a display inconsistency — the notification the platform SMSes them. §4.
- **Cancelling a booking, the single most consequential thing a customer can do in this
  product, took one click and asked nothing.** §6.
- A sixth instance of the touch-target class the audit has been tracking since Phase 2.
- Two design tokens that were outside the sRGB gamut, so the colour authored and the
  colour rendered were different colours and every ratio computed from the authored value
  described something nobody sees.

The pattern is the same one Task 1 recorded and Phase A recorded again: **the defects that
survive are the ones no test asks about.** Each of the four is now asserted rather than
observed.

## 3. Professional surface completion

**Zero new endpoints.** Every route consumed already existed, as V3.1-B promised.

**Bookings — pagination.** The list asked for one page of fifty and stopped, so a
professional with more than fifty bookings could not reach the fifty-first. The worse half
is that nothing said so: the list simply ended and looked complete.

Pagination is **additive**, not page-swapping, and the reason is structural rather than
aesthetic. `listForProfessional` orders by `slotStart DESC`, so future bookings sit at the
head of the list and past ones accumulate behind them, and the upcoming/past tabs are
computed from what is held. Replacing the held page with the next one would empty the
"upcoming" tab the moment a professional paged into their history — not what "next page"
means to somebody looking at tabs.

The tab counts gain a `+` while pages remain unread, because they count what is **loaded**.
The server's `total` counts every booking, not the half a given tab shows; printing it
there would be a different number answering a different question.

Reloading after an action re-reads **every held page**, so completing a booking on page 3
no longer drops the user back to page 1.

**Availability — the visible window.** Hard-coded at 60 days with no control, while bulk
generation happily accepts a 90-day range. A professional could publish availability, see
no trace of it, and publish it again. Now 30 / 60 / 120, default 60, and the empty state
names the window: *"you have no free slots"* and *"you have no free slots in the next 60
days"* are different facts and only the second was ever asked.

**Analytics — the reporting window.** Hard-wired to 30 days though `/v1/me/analytics` and
its `/series` sibling have accepted `from`/`to` since Phase 3. Now 7 / 30 / 90. Three fixed
windows rather than two date fields: a professional wants "this week", not date arithmetic,
and fixed options cannot produce an inverted range for the server to reject.

Also fixed there: the "no activity to show" empty state rendered directly **above** a grid
of cards showing activity, all of them zero. Saying nothing and then showing something is
wrong whichever half the reader believes. They are exclusive now.

**Services — saving.** A successful save produced no acknowledgement at all; on edit, the
changed row can be off-screen, so nothing confirmed the server had accepted it.

And a real defect behind a React key warning that had been firing on every run of the test
suite: `res.data as ServiceOffering` is an **assertion, not a check**, so a response of the
wrong shape was spliced into the list unexamined, producing a row with no `id`. It is
guarded by a narrow runtime check now — only the field the screen breaks without, because
validating every field would be a second copy of the DTO living in the browser.

The warning's actual cause was **a test bug**, reported rather than quietly fixed: the mock
answered the services `POST` with the *list* shape. It answers a GET and a POST differently
now, which is what the API does. This is the same class as Task 1's `OutstandingOrder` and
`SeriesResponse` findings — a hand-written response type describes the server, it does not
verify it — and it is the third time that class has produced a defect.

## 4. `R31-09`, reclassified: the platform timezone

The reconciliation recorded this as **latent** and confined to the customer frontend:
`formatShortDate`, `formatFullJalaliDate` and `formatTime` resolve a `Date` through
`getFullYear()`/`getHours()`, which read whatever zone the process happens to be running
in, while every instant the platform stores is materialized from an `Asia/Tehran` wall
clock.

**It is not latent.** `apps/api/src/events/notification-analytics.handlers.ts` builds the
`date` and `time` variables of the booking-confirmed, booking-cancelled and
booking-rescheduled notifications with those two helpers — **server-side, in the API
process.** Nothing sets `TZ`: not `apps/api/.env`, not the API bootstrap, not the CI
workflow. On the ordinary UTC host a container runs on, every customer has been told an
appointment time **three and a half hours earlier than their real appointment**, and the
wrong **day** for any appointment before 03:30 Tehran.

Telling somebody the wrong time to turn up is a different severity of defect from a
display inconsistency, and it is why this was fixed centrally rather than call-site by
call-site.

**The fix.** The three helpers delegate to `zoned.ts`, so the platform zone is the default
rather than an opt-in. No call site changed — which is the point, because the defect was
reachable from any call site, including ones not yet written. `timeZone` remains an
optional parameter for a caller that genuinely means another zone; it is no longer how
correctness is obtained.

`toPersianDigits`/`normalizeDigits` moved to a new leaf `digits.ts`. `format.ts` now
depends on `zoned.ts`, which already depended on `format.ts`; one leaf both import breaks
the cycle rather than resting on function-declaration hoisting surviving every bundler.

**Four copies of the conversion existed.** `zoned.ts`, booking-service's
`platform-time.ts`, and *two* in `apps/web/lib/booking-api.ts` — `slotTimeLabel` and
`groupSlotsByDay` each built their own `Intl.DateTimeFormat` with the zone spelled out
inline rather than reading `PLATFORM_TIMEZONE`. Both were right about the concept and
would not have heard about a change to the zone. Two copies remain by design (the frontend
package and the backend service are separate deployables); the two in `booking-api.ts` now
delegate.

### Three test defects, all real

- **`zoned.spec.ts` asserted the defect as a requirement.** Its host-independence case
  said `formatTime` must *disagree* with `formatZonedTime` on any host outside Tehran. That
  is why it had to be rewritten rather than merely re-run, and the rewrite is stated
  plainly in the file: the replacement is **strictly stronger** — it pins the absolute
  value, asserts the delegation on every host rather than conditionally, and still fails if
  either function starts reading the ambient clock.
- **`format.spec.ts` and `rtl-persian.spec.tsx` built fixtures with `new Date(y, m, d)`**,
  a local-time constructor. Those assertions passed on this machine (`Asia/Tehran`) and
  would have passed in CI (UTC) *by luck*, while failing on any host east of Iran. A test
  whose expected value depends on the runner's clock is not testing the function.

The suite is now verified green under **`TZ=UTC`, `Asia/Tehran`, `Pacific/Auckland` and
`America/Los_Angeles`**. It had only ever been run in one of them.

## 5. `R31-11`: the accessibility token correction

Phase A measured contrast for the first time and found four pairs below WCAG AA for normal
text, deferring the fix here because a token change affects every screen.

**Re-measuring against real call sites found a fifth.** `ink-faint` on `background` at
**3.81** — Phase A measured `ink-faint` on `surface` and `surface-tint` but not on the page
background, where it also renders (the profile screen's verification footnote, among
others).

### The corrections

Hue preserved; lightness reduced to the largest value clearing 4.5 on **every** background
the token is actually rendered against.

| Token | Before | After |
|---|---|---|
| `--bc-color-ink-faint` | `oklch(0.6 0.02 290)` | `oklch(0.535 0.02 290)` |
| `--bc-color-warning` | `oklch(0.55 0.13 70)` | `oklch(0.53 0.115 70)` |
| `--bc-color-error` | `oklch(0.55 0.19 25)` | `oklch(0.535 0.19 25)` |
| `--bc-color-error-soft` | `oklch(0.95 0.05 25)` | `oklch(0.935 0.032 26)` |

### Measured, in a real browser, before and after

By the same canvas-readback method Phase A used — painting each token onto a canvas and
reading the pixel back, which forces the browser's own `oklch`→sRGB conversion.

| Pair | Before | After | Used for |
|---|---|---|---|
| `error` / `error-soft` | **4.36** | **4.66** | `Alert` error text, error `Badge` |
| `warning` / `warning-soft` | **4.29** | **4.67** | admin context band, warning `Badge` |
| `ink-faint` / `surface` | **3.98** | **5.22** | 12px metadata in a card |
| `ink-faint` / `surface-tint` | **3.58** | **4.70** | 12px metadata on a tinted card |
| `ink-faint` / `background` | **3.81** | **5.00** | 12px metadata on the page |
| `warning` / `surface` | 4.97 | 5.41 | pending booking status |
| `error` / `surface` | 5.33 | 5.71 | field error text, danger button |
| `error` / `background` | 5.11 | 5.48 | error text outside a card |

**All 25 pairs the product renders text in now pass AA for normal text. Worst ratio 4.66,
measured in the browser.** The seventeen unchanged pairs are unchanged to two decimals.

### The gamut finding, which nobody had recorded

`warning` — `oklch(0.55 0.13 70)` — and `error-soft` — `oklch(0.95 0.05 25)` — were
**outside the sRGB gamut**. The browser clipped both, so the authored colour and the
rendered colour were different colours, and any ratio computed from the authored value
described something nobody sees.

`warning`'s correction brings it into gamut as a side effect. `error-soft` was re-authored
as the nearest in-gamut colour rendering to the same pixel: it renders `rgb(254,226,222)`
against the clipped original's `rgb(255,226,222)`. **A one-unit difference in the red
channel** — imperceptible, but not the byte-identical match the commit message for
`a9de7a3` claims, and corrected here. The browser's ratio is 4.66 where the pure-TS model
predicted 4.67, from the same one-unit difference.

### Contrast is now an assertion, not a measurement

`packages/design-tokens/src/contrast.ts` does the real
`OKLCH → OKLab → LMS → linear sRGB → 8-bit` conversion. The naive approach reads
`oklch(0.2 0.02 290)` as RGB and produces confident nonsense — Phase A's first attempt did
exactly that and was discarded.

`contrast.spec.ts` — **71 cases, all passing** — asserts:

1. every rendered pair against AA, computed from `tokens.json` itself;
2. every token against the sRGB gamut, so a clipped token fails rather than lying;
3. that `tokens.css` and `tokens.json` **agree**, without which the whole suite could pass
   green against values no screen uses (they are hand-synced, and this correction had to be
   applied to both);
4. that the maths reproduces **all eleven** of Phase A's browser canvas measurements to two
   decimals — the anchor that makes the other three assertions evidence rather than
   assumption.

The browser re-measurement in §5 above independently confirms the model: every one of the
25 ratios matches the pure-TS computation to ±0.01.

## 6. Customer and business surfaces

Phase G's scope includes the customer surfaces this phase touches. `/bookings` and
`/business` predate both the component kit and the destructive-action contract `/pro`
established, and had drifted from both.

**Four irreversible actions had no confirmation, all one click:**

- **Cancelling a booking.** It releases the slot to whoever takes it next and, on a paid
  booking, starts a refund. The most consequential action a customer can take in this
  product, and the only destructive one anywhere in it that asked nothing.
- **Removing a staff member, declining an invitation, leaving a business.** Re-entry after
  any of the three needs a fresh invitation from the owner.

All four route through the existing `ConfirmDialog` — not a second modal implementation —
and all four close the dialog on failure and surface the error on the page, because a modal
left open over an error the user cannot act on inside it is a trap.

The three business handlers were near-identical copies differing only in which call they
made, which is how they had drifted into three different failure behaviours. They are one
function now.

**Two touch-target violations:**

- `/bookings`' empty-state link was a bare `<Link style={{ fontWeight: 600 }}>`, roughly
  29px tall. This is **instance six** of the class the audit has tracked since Phase 2
  (25px nav, 43px logout, 21px homepage CTA, 24px search result, 18px payment result), each
  previously fixed individually because nothing made the baseline inheritable. It is now
  asserted in a test, so instance seven fails CI instead of shipping.
- `/business`' role radios were two bare inputs in labels with no `minHeight` — the
  tappable area was the glyph plus a 14px line, around 20px. Replaced with
  `SegmentedControl`, which is what a two-option exclusive choice actually is.

**Backlog item 17** (`/business` "mixes three concerns in one undifferentiated stack") is
**improved, not closed**: each concern is now a named section with a `PageHeader` and
status `Badge`s, but the page still shows all three, because that is the real data model —
a user can hold an invitation, own a business, and staff another simultaneously.

or more hand-written implementations that had **already drifted**.

All three had independently rediscovered exact-match-not-prefix-match, `aria-current`, and weight-and-colour-not-colour-alone |
| `ContextBand` | **2** — `ProShell`, `AdminShell` | Phase A copied the structure on the reasoning that re-deciding it would produce a second convention. True — but copying produced two implementations of one convention, the same problem one refactor later |

**`SegmentedControl` deliberately is not a `tablist`.** That role promises arrow-key
traversal and an associated tabpanel; claiming a keyboard contract that is not implemented
is worse for a screen-reader user than claiming no role. It is a labelled `group` of
`aria-pressed` toggle buttons, which is what it is, and Tab-then-Enter is exactly how it
behaves. `/pro/bookings` keeps its real tablist, which genuinely switches panels.

**`ContextBand`'s exit link is a required prop**, so a future fourth role context cannot
ship without a way out of it.

`StatCard`'s `overflowWrap: anywhere` fixes something real rather than theoretical: a
formatted Toman figure is a long unbroken run of Persian digits and separators, and inside
a 180px grid track at 375px the eight inline versions could push their own card past its
column.

## 10. Security

No authorization logic was added, moved, or duplicated. Every route this phase touches is
either a `/v1/me/...` route that **takes no owner identifier at all**, or a
`/v1/providers/:id/...` route guarded by `ProviderOwnerResolver`.

The pagination work is the only change that alters what is requested, and it changes only
`page` and `limit` — `PageQueryDto` bounds both (`@Min(1)`, `@Max(100)`), and the
professional is resolved server-side from the session by
`directory.professionalIdForOwner(user.userId)` before any query runs. **There is no
parameter on any request this phase constructs that identifies a party.**

The adversarial suites from Task 1 (`professional-surface.pg-spec.ts`, 29 cases) and Phase
A (`operability-foundation.pg-spec.ts`, 41 cases) cover professional→professional,
professional→customer, customer→professional, forged booking/slot/service ids, and
unauthorized update/delete/completion/reschedule. **All pass unchanged in CI** — see §13.
This phase adds no new endpoint, so it adds no new attack surface; the suites were re-run
rather than extended.

## 12. Live QA — BLOCKED, and exactly why

**The authenticated Definition-of-Done trace in §20 of the brief was not run.**

Task 1 and Phase A both ran it against a PostgreSQL 16 **container** provisioned with the
project's own CI steps. That container no longer exists, and it could not be recreated:

1. **Docker's engine will not start on this machine.** Docker Desktop was launched and its
   backend processes run, but the `docker-desktop` WSL distribution returns to `Stopped`
   immediately after being started, and `docker info` never succeeds. Waited past ten
   minutes; `wsl -d docker-desktop` reports a networking-mode fallback and a localhost-proxy
   configuration WSL cannot mirror.
2. **A real PostgreSQL 16 service *is* running locally on 5432**, but its superuser
   password is not available and there is no `pgpass.conf`. The application's `.env` points
   at **5433**, the dead container.
3. **`pg_hba.conf` was not edited.** Task 1 recorded "no credential guessing, no
   `pg_hba.conf` edit" as the discipline, and weakening a database's authentication
   configuration to make a test pass is not a trade this phase will make.

**What that means for the trace.** Steps 1–3 and 9–24 of §20 — login, profile, service
CRUD, availability, customer booking, completion, the loyalty / journey /
`completed_bookings` / earnings fan-out, no-show, analytics, logout, and the authenticated
protected-route sweep — are **not evidenced by this phase**. Task 1 §11 evidences that
trace end to end against the code as it stood then, and this phase changed no endpoint and
no authorization path; but that is an argument, not evidence, and it is recorded as the
former.

**To unblock:** either the credentials for the local PostgreSQL 16 instance, or a working
Docker engine. Given either, the trace is a short run.

## 14. QA-25 — re-examined, and answered differently

The backlog records the `/business` nav link showing to every authenticated user as a
**BUG**, blocked on a role signal, and expects it to "fall out of Phase A for free".

It did not, and re-reading the code says it should not. `POST /v1/businesses` is **fully
self-service** — any authenticated session may create a business, exactly as
`POST /v1/providers` may create a professional profile. `app-shell.tsx` already records
why the `/pro` link is shown to everyone: *"becoming a professional in V3 is self-service,
so this is the entry point to a mode anyone may enter, not a link to something only some
users have."* `/business` is structurally identical.

Phase A did make a `business` role grantable, but **nothing grants it on business
creation**, and adding that would mean business-service writing to identity's tables to
support a nav link — a domain-boundary crossing to solve a presentation problem.

**Recorded as a re-classification, not a fix:** QA-25 is **NOT A BUG** as stated. The real
complaint underneath it — "most users click into a create-a-business form they have no use
for" — is a *landing* problem, and it is addressed in §6 by giving that screen a
`PageHeader` and subtitle that say what a business is for before asking anyone to create
one. If a future decision makes business creation non-self-service, QA-25 returns as
written.
