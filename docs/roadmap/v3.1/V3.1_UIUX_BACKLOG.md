# V3.1 UI/UX Backlog

**Source:** `V3_GLOBAL_UIUX_AUDIT.md` (2026-08-24), `V3_GLOBAL_QA_REPORT.md`, plus
frontend re-verification at `68d3d5e`.

**Status:** BACKLOG ONLY. Nothing here is implemented.

**Classification:** every item is one of **BUG** (something is wrong), **POLISH**
(something is unfinished), or **PRODUCT FEATURE** (something does not exist). The
distinction matters because it determines who owns the item: bugs are engineering's,
polish is design's, product features need a decision first.

**Baseline reality, for context.** The V3 frontend is 15 routes, 1 shell, 6 UI primitives,
1 design-token package, ~87 kB shared First Load JS with no route above ~101 kB, 2.6 kB of
CSS total, zero horizontal overflow at any width, zero remaining sub-44px touch targets,
`dir="rtl"`/`lang="fa"` correct everywhere, and logical CSS properties used exclusively.
**The accessibility and RTL discipline is genuinely strong and should not be "fixed".**
What follows is what is missing, not what is broken.

## 2. Detail

### 2.1 Typography

**QA-17 · Vazirmatn is named but never shipped · POLISH · MEDIUM · Phase E**

`--bc-font-family: 'Vazirmatn', -apple-system, BlinkMacSystemFont, sans-serif`, with no
`@font-face`, no `next/font`, no font file of any extension, and no `public/` directory
anywhere in the repository. Every user without Vazirmatn locally installed — essentially
all of them — falls through to a Latin-first system stack, in a product that is Persian-only
by design and has no language switcher.

This is the highest-impact-per-unit-of-work item in the entire backlog: it affects every
Persian character on every screen and undermines every other typographic decision made.

**Blocked on a decision, not on engineering** (#15 in the roadmap): self-host (~100KB+ of
binaries per weight, into the repo and the build) versus a CDN (an external origin with
genuine availability problems for an Iranian audience; Google Fonts specifically is
unreliable in that market).

**Recommendation, carried forward from the audit and endorsed here:** self-host a subset
(Latin + Arabic ranges, weights 400/600/700) via `next/font/local`. Keeps it inside the
build, introduces no external origin, and gets automatic `font-display` handling.

**One consequence to plan for:** the audit's current "no layout shift from web-font swap"
result is only true *because the font never loads*. Shipping it introduces a swap that needs
`font-display: swap` and a metric-matched fallback, or the fix trades one visual problem for
another.

### 2.2 Imagery and media

**IMAGERY · Zero images in the entire product · PRODUCT FEATURE · HIGH · Phase C**

No `<img>`, no `next/image`, no avatars, no cover photos, no portfolio images, no logo mark
(the wordmark is text), no `public/` directory, no placeholder assets. Provider profiles,
search results, and booking cards are entirely text.

For a **beauty marketplace** this is the most consequential product gap after the font.
The category is inherently visual — customers choose a professional by looking at their
work. `GAP-23` already records that V2's portfolio was half-built and must be **redesigned
rather than ported**; this backlog records that the frontend consequence is total, not
partial.

**Hard prerequisite that no document previously named: there is no file-upload or
object-storage capability anywhere in `v3/`** (R31-03). This is not a UI task waiting on
design; it is a UI task waiting on infrastructure that does not exist.

**When it lands, three things must be true from the first commit:** explicit aspect ratios
via `next/image` so the current zero-layout-shift result survives; a public/private access
split (portfolio public, verification evidence never publicly addressable); and no
fabricated imagery of real people.

**Related and cheap: no favicon, no `apple-touch-icon`, no OpenGraph or Twitter metadata.**
`layout.tsx` sets `title` and `description` only, so any link shared into a messaging app —
which is how sharing happens in this market — renders bare. Combined with the absent
`robots` and `sitemap`, this is the frontend half of `GAP-09`. **POLISH, S-sized,
Phase E**, and it is worth doing even before imagery exists.

### 2.3 Missing surfaces

**PRO-UI · No professional-specific frontend · PRODUCT FEATURE · HIGH · Phase B**

`/dashboard` is a shared three-field identity page. There is no professional dashboard,
profile editor, service manager, availability editor, booking list, earnings view, or
analytics view. Nine of fourteen professional capabilities are built and gated on the
backend with no interface at all.

Full endpoint inventory in `V3.1_GAP_RECONCILIATION.md` §4 (PRO-UI). The design brief for
this surface should start from the fact that **the contract is already fixed** — every
route, its ownership resolver, its error shape, and its response envelope are settled and
tested. This is unusually low-risk UI work.

**The one genuinely subtle screen is the availability editor**: bulk slot generation across
a date range with per-day patterns, timezone and DST handling, and a deletion path that has
to reason about slots that are already held or booked. Budget it as the hard one.

**ADMIN-UI · No admin UI · PRODUCT FEATURE · HIGH · Phase A**

Zero admin pages against five fully-gated admin API surfaces. Minimum screen set and the
architecture recommendation (a route group inside `apps/web`, not a second Next.js app) are
in `V3.1_PRODUCT_ROADMAP.md` §8.

**QA-23 · No footer, anywhere · PRODUCT FEATURE · MEDIUM · Phase E**

`AppShell` is `<header>` + `<main>`. Landmarks confirmed live as exactly
`HEADER, NAV, MAIN` — there is no `contentinfo`. Consequences beyond aesthetics: no route
to terms, privacy policy, contact, support, or about from anywhere in the product; nothing
anchoring the trust signals a marketplace that takes payments normally carries; one fewer
landmark for assistive navigation.

**The markup is XS. The content is the blocker** — terms and a privacy policy are legal
artifacts someone must author and approve (#14). Shipping an empty shell, or one linking to
404s, is worse than shipping none. Pair the authoring with the privacy *mechanism*
(GAP-22), since the policy has to describe what the mechanism actually does.

**QA-16r · The homepage is an honest placeholder · PRODUCT FEATURE · MEDIUM · Phase E**

QA-16 removed the Phase 1 scaffold copy that told visitors product pages would be built
later. It did not design a homepage. There is no hero, no value proposition, no category
entry points, no social proof, no imagery — nothing that would make a first-time visitor
understand or trust a beauty marketplace. Depends on C to be worth doing properly.

### 2.4 The component layer — where the recurring bugs come from

**UIKIT · Six primitives, layout mostly inline · POLISH · MEDIUM · Phase G**

Design tokens are genuinely well used: no hardcoded colours or radii were found in any
page. But **almost all layout is inline `style={{}}` objects** — `chipStyle()` in search,
`NAV_LINK_STYLE` in the shell, repeated ad-hoc flex and grid objects everywhere. The token
layer is disciplined; the component layer is thin, so spacing and composition decisions are
re-made per page rather than inherited.

The audit's diagnosis is the important part, and re-verification supports it:

> Five independent empty-state bugs and five independent touch-target bugs are symptoms of
> a thin component layer, not of carelessness.

**Needed:** `TextLink` / `NavLink` (carrying the 44px baseline), `EmptyState` (distinct from
the `ErrorState` that `v3.0.1` already added), `PageHeader`, `Badge`, and a `Dialog` with a
real focus trap.

**TOUCH-CLASS · The 44px baseline is enforced in `Button` and nowhere else · BUG (recurring) · MEDIUM · Phase G**

Five recorded instances of the same bug: 25px nav links (Phase 2), 43px logout (Phase 3),
21px homepage CTA (PHASE5-01), 24px search-result link, 18px payment-result links (QA-13).
None of the fixes regressed — the class simply recurs on every new surface, because 44px
lives inside `Button` and nothing enforces it for a `Link`.

**Building V3.1-B on the current component layer manufactures instances six and seven.**
That is the entire argument for running G concurrently with B rather than after it.

**Dialog / focus management · POLISH · MEDIUM · Phase G**

No dialog, modal, tab, or focus trap exists anywhere in V3. The audit correctly notes this
means the brief's modal-sizing and focus-trap questions have no subject — and that the
**first** modal added will need focus management with no precedent in the codebase to copy.
Phases A (moderation decisions), C (upload), and D (review submission) will each want one.
Build it once, in G, before any of them.

**Visual hierarchy · POLISH · MEDIUM · Phase G**

Every page is `<h1>` at 24px, a muted 14px subtitle, then `Card`s. Legible and consistent,
but flat: there is no size, weight, or colour escalation making a primary action dominant.
`Button`'s `width: '100%'` means the primary CTA and a secondary ghost action are the same
size and shape, differing only in fill. **`Card`'s fixed 24px padding at every breakpoint**
is generous on a 375px screen where content width is already ~327px; section padding does
step correctly via `clamp()`.

### 2.5 Context and information architecture

**No visual distinction between customer, business, and professional contexts · POLISH · MEDIUM · Phase B**

Within the customer surfaces the product does feel like one product — same shell, card
rhythm, and Persian voice. But there is no signal telling a user which *role context* they
are in, and V3.1-B introduces a third. Decide the pattern (a context switcher, a shell
variant, a colour accent) **before** the professional surface ships, not after there are
three undifferentiated stacks.

**`/business` mixes three concerns in one stack · POLISH · LOW · Phase B**

Invitation management, staff management, and business creation are presented as one
undifferentiated column. Worth restructuring while the professional surface establishes the
role-context pattern.

**QA-25 · The business nav link shows to every authenticated user · BUG · LOW · Phase B**

"کسب‌وکار" renders for every signed-in user regardless of business ownership, so most users
click into a create-a-business form they have no use for. **It looks like a one-line
conditional and is not**: a `business` role exists in `CAPABILITIES_BY_ROLE`, but
`identity.users.roles` is never populated beyond `['customer']` (R31-01), so the frontend
has no signal to condition on. Falls out of Phase A for free; listed here so it is not
attempted earlier and hidden by guesswork.

### 2.6 Auth and payment microcopy

**QA-19 · No resend-OTP and no expiry countdown · PRODUCT FEATURE · LOW · Phase E**

After requesting a code the only affordances are the code field and "تغییر شماره موبایل".
The server enforces both a 300s expiry and a resend cooldown; neither is surfaced. A user
whose SMS does not arrive must change their number and change it back — the auth screen's
only real dead end.

Doing it correctly needs the API to return **remaining cooldown seconds** so the button can
count down. The cheap version — a resend button that fails with an unanticipated
`RATE_LIMITED` — is worse than the current dead end, which is exactly why `v3.0.1`
excluded it.

**QA-21 · Cancel and decline look identical · BUG · LOW · Phase F**

The backend deliberately distinguishes `cancelled_by_user` from `declined` — that
distinction was an explicit `GAP-06a` deliverable and the sandbox page offers them as
separate buttons. The result page collapses both into "پرداخت انجام نشد", so a customer who
*chose* to abandon payment is told their payment failed.

Needs `failureCode` threaded through the redirect contract. **Deliberately deferred to
Phase F so the gateway-return contract is settled once, with the real adapter, rather than
changed twice.**

**QA-20 · `current: false` hardcoded · BUG · LOW · Phase E**

`GET /v1/auth/sessions` sets `current: false` on every row, so a user could never tell
which session is theirs. Misleads nobody today because no frontend consumes the endpoint.
Needs a session identifier claim in the JWT — a token-shape change affecting every issued
token — and should ship with the device-management UI rather than alone.

**QA-22 · Label maps fall back to raw English · POLISH (latent) · INFO · Phase D**

`BADGE_LABELS[badge] ?? badge` and equivalents would render `recent_activity` or `over_2m`
into a Persian UI. Verified **not currently reachable**: all five ranking-signal keys and
all four price bands are covered. Latent only — and Phase D adds ranking signals, which is
exactly when a new key could leak. Address it structurally then (a shared enum or a lint
rule), not as a patch now.

### 2.7 Accessibility — what is verified, and what is not

**Verified working and worth protecting:** skip link (measured 1×1 with
`clip: rect(0,0,0,0)`), `:focus-visible` rings on every interactive element, landmark
structure, exactly one `<h1>` per page, labelled controls with `aria-describedby` wiring
both hint and error, `aria-invalid`, `role="alert"` on errors, `role="status"
aria-live="polite"` on loading, combobox ARIA on autocomplete, unread count in the
accessible *name*, a semantic receipt table with `<caption>` and `scope="row"`,
`prefers-reduced-motion` honoured, `aria-busy` on loading buttons, `aria-current` on nav
(added in `v3.0.1`), and 44px targets throughout.

**Not verified — and each is a real gap in the evidence, not a defect claim:**

| # | Item | Why it matters | Phase |
|---|---|---|---|
| 8 | **Colour contrast has never been measured.** The palette is authored in `oklch` with plausible lightness separation, but no ratio has been computed | The most significant unverified accessibility dimension in the product | G — and record the numbers in a test, not a one-off measurement |
| 21 | **Keyboard traversal was never walked end to end** in the authenticated app | The authenticated app is where the forms are | B, once an authenticated runtime exists |
| 22 | **No screen-reader testing** with an actual screen reader | Every ARIA decision above is currently theory | G |
| 23 | **Protected routes were swept unauthenticated only** (`/bookings`, `/notifications`, `/journey`, `/loyalty`, `/waitlist`, `/business`), so they measured their redirect state, not their populated layout | The populated layouts have never been measured at any viewport | B |

Items 21 and 23 share one blocker: the API cannot boot locally (stale
`beauclick_app`/`beauclick_financial_writer` credentials, `pg_hba.conf` requiring
`scram-sha-256`, Docker's daemon not running). **Restoring a bootable local environment is
therefore an accessibility prerequisite, not just a developer convenience** — and it is the
cheapest way to close three unverified items at once.

### 2.8 Informational

**QA-26 · `next dev` invalidates its own `?v=` stylesheet URL under rapid edits**, so the
CSS 404s and every design token silently disappears. Not a product bug — the production
build is content-hashed and correct — but it cost the last audit real time. Mitigation
already landed: the `beauclick-v3-web-prod` launch config, so UI audits run against a
production build by default. **Nothing to fix.**

## 3. What this backlog deliberately does not contain

Reporting UI findings against surfaces that do not exist would be fiction. The following
appear in the audit brief and have **no subject** in V3: AI interface, wishlist, reviews UI,
referrals UI, professional dashboard/profile/services/availability, business
services/bookings/analytics/quotes, service cards as a distinct component, search modal,
admin pages, and any footer. Each is tracked as a product gap in
`V3.1_GAP_RECONCILIATION.md`, and the ones V3.1 will build acquire UI/UX requirements when
their phase begins — not before.

### Contrast, measured

Method matters here. The browser returns `oklch()` **unconverted** from
`getComputedStyle`, so a parser that assumes RGB reads `0.2 0.02 290` as a colour and
produces confident nonsense — the first attempt did exactly that, returned identical
ratios for unrelated pairs, and was discarded. The reported numbers come from painting
each token onto a canvas and reading the pixel back, which forces the browser's own
oklch→sRGB conversion.

**Pass AA:** ink/surface 18.09 · ink/background 17.34 · primary/surface 9.86 ·
surface/primary 9.86 · primary/primary-soft 8.21 · ink-soft/surface 6.57 ·
ink-soft/surface-tint 5.92 · success/success-soft 4.78.

### New item

**26 · Four token pairs below WCAG AA for normal text · BUG · MEDIUM · Phase G**

| Pair | Ratio | Used for |
|---|---|---|
| `error` on `error-soft` | 4.36 | `Alert` error text, error `Badge` |
| `warning` on `warning-soft` | 4.29 | admin context band, warning `Badge` |
| `ink-faint` on `surface` | 3.98 | 12px metadata — ids, timestamps |
| `ink-faint` on `surface-tint` | 3.58 | 12px metadata on tinted cards |

All four render at 12–14px, so "AA for large text" does not apply. **None is a Phase A
regression** — every one predates this phase, and `ink-faint` in particular is used
throughout the customer surfaces. Fixing it means changing design tokens, which affects
every screen in the product; that belongs to Phase G alongside the rest of the component
layer, not to a phase whose scope is operability. Tracked as `R31-11` in the
reconciliation.
