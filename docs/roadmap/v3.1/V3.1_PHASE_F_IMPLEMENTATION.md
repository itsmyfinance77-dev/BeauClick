## 1. The one-paragraph judgement

Phase F's remaining work divides more cleanly than the roadmap could have known
before someone tried it. Roughly two thirds of it — the verification contract,
the failure vocabulary, environment validation, readiness reporting, role
verification, backup and restore, observability, containerisation, the CD
pipeline shape, and the runbooks — needs no vendor, no host, and no credential.
That two thirds is now built, tested, and in several cases *run*. The remaining
third is genuinely external and is not one line closer than it was: no gateway
is selected, no host exists, no OTP has been delivered, no production telemetry
has been received, and no backup of real data has been restored. The most
useful thing this phase produced is not any single feature but the fact that
**four items previously described as "one afternoon once a host exists" are now
one command each** — and the commands are tested, which is how you find out that
they work before the day they matter.

## 2. IMPLEMENTED AND VERIFIED LOCALLY

Everything in this section runs in CI on every build, or was executed by hand
during this phase and is stated as such.

### 2.1 The ambiguous verification outcome (ADR-028)

`VerifyOutcome` was `succeeded | failed`, so an adapter whose gateway call
timed out had to pick one, and both are wrong. `failed` is wrong expensively:
it writes terminal statuses, emits `PaymentFailed` to five consumers, drives an
append-only ledger entry that cannot be withdrawn, and tells a customer whose
card may have been charged that no money moved.

`unknown` is the third state. The caller **writes nothing** for it: the attempt
stays `initiated`, so a later callback still settles the real payment with no
manual repair. That recoverability is asserted, not assumed. A caller-imposed
deadline (`PAYMENT_VERIFY_TIMEOUT_MS`, default 15s) bounds a customer's wait
rather than inheriting the gateway's.

No schema change — `unknown` is the absence of a write.

### 2.2 `QA-21` — the failure reason (closed), and the retry it enabled

The redirect contract carries a `reason` from a **closed** public vocabulary.
The gateway's own code is still stored for support and never published: a
redirect URL is browser history, a referrer header, and whatever analytics the
result page loads, and Iranian gateway codes are frequently free text.

Cancel and decline are now different sentences, which is the whole of QA-21.
`unresolved` gets copy that promises nothing in either direction — the single
most important sentence on that page, because a customer told "no money was
taken" about a payment that may have succeeded will retry and be charged twice.

### 2.2b The design pass, and the retry contract it forced (2026-08-29)

Design source: `origin/design/claude-design` @ `4b40b90`,
`docs/design/phase-f-workspace-snapshot/docs/design/screens/16_CHECKOUT_RESULT.md`.

The design read the shipped page against the shipped backend and found a
**contradiction between the copy and the contract**: the `unresolved` body
promised that any deducted amount would be "به‌صورت خودکار تعیین تکلیف می‌شود".
§8 of this document records that no reconciliation sweep was built, and why. So
the page described a mechanism that does not exist, to a customer who might be
relying on it, about their money. `gateway_error` carried a milder version of
the same fault — an automatic-refund promise for a definitive failure where
nothing was captured. Both corrected; both now point at support instead.

That is the second time in this phase a **claim in prose outlived the code it
described** (the first being `.env.example`'s cookie-validator claim, §2.3).
Worth naming as a pattern: the copy a customer reads is part of the contract,
and nothing was checking it against the contract.

**The retry contract, which the design marked `BACKEND CONTRACT REQUIRED` and
deliberately did not choose.** `isRetryableFailureReason` says four of the eight
public reasons permit a retry; the redirect contract carries no `intentId`, so
the button had nothing to call. The design named two options — put `intentId`
in the redirect, or add an order-scoped lookup — and left the decision here.

Chosen: **`POST /v1/orders/:id/payment/retry`**, order-scoped. An intent id in a
URL is a payment-domain identifier written into browser history, referrer
headers, and every analytics script the result page loads, for nothing the
customer's own order id does not already provide. The browser names the order;
the server resolves the intent from its own records. Full contract in §2.2c.

`expired` stays without a retry, exactly as the design marked it: the slot may
already belong to somebody else, and re-booking is a different question this
platform has no safe path for. That remains open and is NOT closed by this pass.

### 2.2c The retry contract, stated

Refuses unless **all** of these hold, each read from the database and none from
the request:

| # | Check | Why |
|---|---|---|
| 1 | Ownership, via `OrderOwnerResolver` | Same guard every order route uses. A foreign order and a missing one get an identical `NOT_FOUND_OR_NOT_YOURS`, so the route cannot be used to discover which order ids are real |
| 2 | The intent's own `customerId` matches | Redundant with 1 by design — the two reads come from different schemas, so a disagreement fails closed |
| 3 | `order.status === 'pending'` | Paid, refunded, partially refunded, and cancelled orders no longer owe money |
| 4 | Intent not `succeeded` / `cancelled` / `expired`, and its window has not lapsed | `initiate` re-checks all of this; checking here turns a generic refusal into a specific, closed-vocabulary one |
| 5 | **No attempt still `initiated`** | The one that is not obvious — see below |
| 6 | `intent.failureCode` narrows to one of the four retryable public reasons | Derived from the stored provider code. The caller's `reason` parameter is never read |

**Why check 5 exists.** An `unknown` verification writes nothing — that is the
whole of ADR-028 — so after `declined → retry → paid → gateway times out`, the
intent still carries `failure_code = 'declined'` and `status = 'pending'`. A
decision made on the failure code alone would offer to charge that customer a
second time for a payment that may already have taken their money. An open
attempt is the honest signal, and the three situations it covers (at the bank,
abandoned, unresolved) are indistinguishable from here and must be refused
identically. `payment-retry.pg-spec.ts` walks that exact four-step sequence.

**Concurrency** is left to the invariants that already exist rather than a new
lock: `initiate` reuses a live attempt, and `uq_payment_attempts_live_per_intent`
makes a second one impossible at the database level. Three simultaneous retries
produce exactly one chargeable transaction and one redirect URL. A transaction
around the checks would be strictly worse — it would hold a connection across
an HTTP round trip to a bank.

**The response** is `{ redirectUrl }` and nothing else. Refusals carry a reason
from the closed `PAYMENT_RETRY_REFUSALS` set, so no internal state name and no
provider code can reach a browser. Retries are already audited through the
existing path: `initiate` writes `payment.initiated` and emits
`PaymentInitiated`, so no new audit surface was added.

**No new gateway flow.** The retry reuses `PaymentService.initiate`, which is
why the double-charge protections, the expiry check, the attempt reuse, and the
unique-index backstop all apply to it unchanged.

### 2.2d One vocabulary, two runtimes

`@beauclick/payment-contract` is a new dependency-free package holding the
eight public reasons, the six result statuses, the retryability rule, and the
refusal vocabulary. The result page needs all four and was keeping its own copy
of the strings; `services/payment` now re-exports the package and keeps only
the provider-code alias table.

Two policies that must agree while being maintained separately are one policy
plus a bug waiting for a release — a reason the page hides that the server
permits, or worse, one the page offers that the server refuses. Sharing the
rule removes the drift. It does **not** move the decision: the server derives
eligibility from its own stored failure code and refuses regardless of what the
page believed, which is asserted by pointing a retry at an `amount_mismatch`
order while claiming `reason=declined` in the query string, the body, and both.

### 2.3 Production environment validation

`validateEnv` checked three variables for presence. Presence is the weakest
property a production configuration has, and every failure that matters passes
it. Now refused, all at once rather than one per deploy, with **no message ever
echoing a value**:

- the code's own development fallback secret, verbatim;
- `PAYMENT_ENVIRONMENT=sandbox` on a production host — a sandbox presented as
  production, arriving through configuration rather than code;
- `CORS_ALLOWED_ORIGINS=*` alongside `credentials: true`;
- plaintext public URLs, loopback origins, origins carrying a path;
- one secret serving two purposes;
- a half-configured object store, a missing search cluster, a leftover
  `DEV_QA_LOGIN`, a disabled outbox sweep.

`SECRET_CONTRACT` names every secret the application reads and what an attacker
gets by learning it — data rather than prose, because a list in a document
drifts from the code that reads it.

`NODE_ENV` is compared **exactly**. Every gate in the codebase tests the literal
`'production'`, so normalising would have let `NODE_ENV=Production` pass
validation with the sandbox gateway, the container-disk media driver, and the
in-memory search engine all still enabled.

### 2.4 Readiness reporting (ADR-028)

`GET /health/ready`, with `not_configured` / `simulated` / `configured` /
`reachable` / `unreachable`, plus `productionVerified` on a separate axis
sourced from `EXTERNAL_VERIFICATION_LEDGER`. Every row is `false` and a test
asserts it; **no code path can set one true.**

Public and rate-limit exempt, because an orchestrator's probe carries no
session — so the output is enums, booleans, and gap ids only, asserted by a
test that serialises the report and searches it for the process's real
configuration. The configuration problem list is withheld in production: it
names variables, origins, and drivers, which is a configuration map.

### 2.5 PostgreSQL role verification — `pnpm verify:roles`

44 checks: schema and table ownership, non-superuser, the ledger's append-only
grants, the application role's total exclusion from `financial`, the audit
log's append-only grants, `PHASE4-03`'s `CREATE ON SCHEMA public`, and the
default privileges covering tables no migration has written yet.

**Needs no superuser**, which is what makes it usable against a managed
provider. Every check is a catalog read plus `has_table_privilege(role, oid,
priv)`; addressing tables by OID rather than by name is load-bearing, because
the name form needs USAGE from the caller and the application role
deliberately has none on `financial`.

CI runs the **command**, not the functions inside it — including a negative
case that produces real failures and asserts a non-zero exit, and a
cannot-connect case that must also not be silently zero.

### 2.6 Backup and restore — `pnpm backup`, `pnpm restore:rehearse`

A dump plus a manifest (sha256, byte length, server version, applied
migrations, per-table row counts). The rehearsal dumps, verifies the manifest
**before** restoring, restores into a database it creates rather than one it
overwrites, and compares counts and schema version.

Then the check that justifies the whole thing: **it re-runs the role contract
against the restored database.** The append-only guarantee is a role contract,
not a column constraint — a restore that returns every row and drops the grants
produces a database where the financial writer can `UPDATE ledger_entries`, and
every count matches, every query works, every smoke test passes.

Executed locally: 71 tables, 37 migrations, 44/44 role checks on the restored
copy. Runs in CI on every build.

### 2.7 Observability

- **Redaction first**, because a log aggregator is a second copy of whatever
  reaches it. Two rules: by key, and by value shape for the free text no
  key-based rule can reach.
- **Structured JSON logging**, correlation-tagged, stack traces on one line,
  installed at `NestFactory.create` so the framework's own boot lines go
  through it.
- **Prometheus text exposition** at `GET /metrics`. Implementing an open FORMAT
  is not writing a vendor adapter from documentation. Cardinality bounded:
  route template not path, status class not code, hard series ceiling that
  reports what it refused. Requires a bearer token and answers **404** without
  one — the worst outcome of a forgotten variable should be a missing
  dashboard, not an open one.
- **An error-reporter port** with a logging default that says it transmits
  nothing, and a configurable HTTP reporter that never throws, never waits, and
  never retries — verified against a real local HTTP server that refuses,
  errors, and hangs.

`beauclick_payment_verifications_total{outcome="unresolved"}` is the metric
worth alerting on: it counts payments whose result nobody knows, and it is
invisible in every other signal.

## 7. TOPOLOGY-DEPENDENT

### `THROTTLE-STORE` — deliberately NOT implemented

Throttler storage is in-memory per process, which is **correct** at
single-instance scale and silently wrong the moment a second instance exists:
the effective limit multiplies by instance count.

The correct fix is a shared Redis store. It was not built, because building it
would require deciding that production runs more than one API instance — and
that is downstream of the `HOSTING` decision, which does not exist. Inventing
the topology to justify the code is exactly the class of thing this phase is
forbidden from doing.

What was done instead: the fact is **reported**. `/health/ready` carries a
`throttle_store` row in the `simulated` state, blocked by `THROTTLE-STORE`, so
an operator reading the readiness endpoint on a multi-instance deployment can
see the problem rather than deducing it from a rate limit that seems too
generous.

  guessing at them.

  unsafe without a machine-readable backward-compatibility marker on
  migrations.
- **A web container image.** `apps/web` has no `output: standalone`; the API is
  the deployable the CD pipeline shape needed to be proven against.

## 9. Bugs discovered and fixed

Six, all found by tests or by running the artifact rather than by review.

### `BUG-F-01` — a failure code could return a function into the customer's address bar

`REASON_ALIASES[code]` over an object literal resolves `constructor`,
`toString`, and `hasOwnProperty` off `Object.prototype` and returns a FUNCTION
as though it were a reason — which `URLSearchParams` stringifies, publishing a
chunk of the runtime's source into the redirect. Exactly the leak the closed set
exists to prevent, arriving through the lookup rather than the table. Now a
`Map`, which has no prototype chain.

Found by `payment-failure.spec.ts`.

### `BUG-F-02` — a long gateway failure code aborted the callback transaction

`payment_attempts.failure_code` is `varchar(60)` and PostgreSQL does not
truncate, it raises `22001`. Inside the callback's transaction. So an adapter
returning a longer message — a free-text Persian bank message, which several
Iranian gateways return — served the customer a 500 on the failure path, where
they are already having a bad time. Adapter strings are now fitted at the
boundary; the provider REFERENCE is refused loudly instead, because a truncated
one is a payment nothing can ever reconcile.

Found by `payment-verification-contract.pg-spec.ts`.

### `BUG-F-03` — every 4xx was invisible to metrics

HTTP metrics started as an interceptor. Nest runs guards **before**
interceptors, so 401, 403, 404, and 429 never reached it, and an unmatched
route never enters the pipeline at all. The error-rate dashboard would have
read zero during exactly the incidents it exists to surface. It is middleware
now — the only layer that sees them.

Found by `observability.pg-spec.ts`.

### `BUG-F-04` — the metrics middleware hung every request

It never called `next()`. That does not fail loudly; it hangs the entire
application forever with no error anywhere. Twelve tests timed out on a
`GET /health`.

Found by `observability.pg-spec.ts`, within minutes of being written.

### `BUG-F-05` — the exception filter threw while handling an exception

The new error-reporting hook assumed an HTTP `ArgumentsHost`. A filter that
throws produces an unhandled rejection and **no response at all**, turning a
recoverable 500 into a dropped request.

Found by the pre-existing `beauclick-exception.filter.spec.ts`, whose host
double implements `getResponse` and nothing else.

### `BUG-F-06` — `pnpm build` produced output that cannot start

`apps/api/tsconfig.json` redeclared `paths` as a **subset** — twelve of
twenty-six packages. Everything absent resolved through `node_modules` to each
package's own `src/index.ts`, which works for `ts-node` and every test runner
and silently breaks `tsc -p`: **TypeScript does not emit files it reached
through `node_modules`.** `dist/` had been missing `libs/audit`, `libs/media`,
`libs/subject-data`, `libs/event-contracts`, and `libs/testing` entirely.

A green build, for as long as nobody ran its output. Found by running the
container, which died on `Cannot find module '/app/libs/audit/src/
admin-audit-log'`. The config now inherits, which removes the class rather than
lengthening the list.

### `BUG-F-07` — a new path mapping would have killed the container

`infra/docker/tsconfig.runtime.json` is GENERATED from `tsconfig.base.json`'s
path table, and nothing regenerates it. Adding `@beauclick/payment-contract`
therefore left the container's runtime resolver without it: typecheck passed,
lint passed, every test passed, the image BUILT, and the process would have died
at startup on `Cannot find module '@beauclick/payment-contract'`.

Found by rebuilding and starting the image rather than by any check that exists.
Regenerated, and the container re-verified: it starts, serves `/api/health`, and
answers the new retry route with a 401 for an unauthenticated caller.

The same class as `BUG-F-06` — a build that succeeds and produces output that
cannot run — and the second time in this phase that only executing the artifact
in the shape it actually runs in would have caught it.

Two further defects in the Dockerfile itself — a prod-prune silently skipped by
`|| true`, and a module-resolution root that would have broken
`services/payment` in production and nowhere else — are recorded in that file
and in the commit message; they never reached a committed artifact in a broken
state.

## 12. What this phase deliberately did not do

- **Write a named gateway adapter from documentation.** An unexercised adapter
  is a liability rather than an asset, because it looks finished. The port,
  the contract, the failure taxonomy, the deadline, and the tests are the half
  that can be right without a vendor; the protocol is the half that cannot.
- **Bind the Sentry SDK.** It would settle a vendor question this phase may not
  settle and would not close `OPS-04` anyway, which needs a DSN, a deployment,
  and a real error in a real dashboard.
- **Implement Redis-backed throttling.** See §7.
- **Weaken the two-condition sandbox gate.** Untouched, and now refused twice:
  the provider gate stops a sandbox taking real money, and environment
  validation stops a deployment that thinks it can from starting at all.
- **Close any external gap.** Every one is still open, in §4 and §11.
- **Create a tag or a release.**
- **Begin final production frontend implementation.** The frontend changes are
  scoped to `/checkout/result` and its login return path, implementing an
  approved design against surfaces that already existed. No new screen, no new
  component, no new design token.
- **Build a safe re-booking path for `expired`.** The design marks it
  `BACKEND CONTRACT REQUIRED` and it stays open: the slot may already belong to
  somebody else, and a "book it again" flow is a booking question, not a
  payment one. Inventing one would be inventing product semantics.
- **Touch `design/claude-design`.**
