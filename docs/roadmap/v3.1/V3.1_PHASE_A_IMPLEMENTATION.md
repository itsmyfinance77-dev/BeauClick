# V3.1 Phase A — Operability Foundation

**Baseline at start:** `HEAD` = `origin/master` = `69239ce` (Task 1 complete).
`v3.0.0` (`cfecfdf`) and `v3.0.1` (`68d3d5e`) untouched. No historical tag touched. No
`v3.1.0` tag created. V2 / WordPress / WooCommerce untouched.

**Scope:** dynamic roles and capabilities, a least-privileged platform operator with a
documented one-time bootstrap, the professional verification workflow, a persistent
append-only admin audit log with boot-time structural enforcement, an eight-screen admin
route group, phone-conflict resolution, and search click-through metrics. Nothing from
Phases C, D, E, or F was started.

---

## 1. What was actually broken

Three findings from the V3.1 reconciliation, and they compound:

- **`R31-01`** — `AccountResolverService` wrote `roles: ['customer']` at account creation
  and **no code path anywhere ever wrote that column again**. `bc_manage_platform` was
  therefore ungrantable, and all five `/v1/admin/*` surfaces — platform analytics,
  cross-party financial totals, settlement creation and reversal, loyalty policy,
  notification status, search reindex — were unreachable by any account the application
  could produce. The platform could not be operated at all.
- **`R31-02`** — `ProviderService.transitionVerification()` was a complete, CAS-hardened,
  event-emitting state machine whose only callers were four lines in a spec file. Every
  professional was `unverified` permanently, so the `verified` badge, the `verifiedOnly`
  filter, and `RankingConfig.WEIGHT_VERIFIED` were all permanently inert.
- **`GAP-02-V3`** — audit logging was structured-logger-based. A log line is not a record
  anyone can query, and a mutation whose log line is lost succeeds anyway.

The sequencing that mattered: Phase A creates the platform's **first privileged
principal**, so the audit enforcement had to land in the same phase rather than after it.

## 2. Dynamic roles and capabilities

`identity.roles`, `identity.capabilities`, `identity.role_capabilities`,
`identity.user_roles`. The seed is the exact contents of `CAPABILITIES_BY_ROLE` at
migration time — the constant becomes the seed's source rather than a second authority.

**Nothing about how authorization works changed.** Every guard still checks a capability
NAME, exactly as the Phase 1 docblock promised: *"upgrading to dynamic roles/capabilities
later changes only where this map's data comes from, not how any guard/controller checks
it."* Only `RoleService.resolveAccess()` replaced `capabilitiesForRoles()` as the source.

**Expand, not contract (ADR-016).** `identity.users.roles` remains and is kept in sync
during this window. Dropping a column in the same migration that introduces its
replacement is the deploy-ordering hazard the discipline exists to prevent; a later
migration may drop it once nothing reads it.

Account creation now writes the user row and its default role grant in **one
transaction**, so an account cannot exist with no role.

### One deliberate widening, recorded rather than slipped in

`platform_operator` gains `bc_moderate_verification`, which the Phase 1 static map did not
give it. Phase A's brief requires an operator to decide verifications. The alternative —
granting the bootstrap account both `platform_operator` and `moderator` — would give the
first privileged account `bc_moderate_reviews`, authority over a domain that does not
exist yet. This is the narrower of the two options, which is what
`V3_SECURITY_MODEL.md` §9 asks for.

## 3. The escalation rules, and the deadlock the tests caught

Enforced in `RoleService`, never in a controller and never in the frontend:

1. Granting requires `bc_manage_platform` (the guard).
2. **A caller may only grant a role whose capabilities are a SUBSET of their own.**
3. `administrator` is never grantable through the application at all, even by an
   administrator — only through the documented bootstrap.
4. No self-grant of a privileged role, ever.

Rule 2's first draft was narrower: *"may only grant a role you yourself hold."* It
**deadlocked**. `moderator` holds `bc_moderate_reviews`, which `platform_operator`
deliberately does not, so no operator could ever grant it — and a moderator has no
`bc_manage_platform` and so cannot reach the endpoint at all. The role would have been
permanently ungrantable, which is the same class of bug as `R31-01` itself.

**Caught by the test suite, not by review.** Under the subset rule the hierarchy is
coherent: an administrator's capability set contains a moderator's, so an administrator
can appoint one; a platform_operator cannot, because they genuinely lack authority over a
domain they are not responsible for. That refusal is the rule working, and both directions
are asserted.

## 4. The platform operator and its bootstrap

`database/scripts/grant-platform-operator.ts`.

**Why a script and not a route.** The first privileged account cannot be created by a
privileged account. The options were: seed a superuser (rejected — a permanent full-authority
account with a password somebody wrote once is the most-attacked thing a deployment can
own, and §9 says default to the narrowest tier); an unauthenticated claim-ownership
endpoint (rejected — a race with the internet on every fresh deploy, during the window
nobody is watching); or **require authority the application itself does not have**.

Database credentials were chosen. Someone holding them can already do anything; asking
them to prove it is not a new trust assumption, it is the existing one made explicit.

**Single-use by design.** The script refuses to run if any account already holds
`platform_operator` or `administrator`, checked inside the transaction so two simultaneous
bootstraps cannot both see zero. `--force` exists for one real situation — every operator
account lost — and requires `--reason`, which is recorded.

**Even the first grant is audited.** The row is written with `actor_user_id = NULL` and
`actor_label = 'bootstrap'`, and the audit-log screen marks those entries visibly so an
operator can tell which rows predate any accountable actor.

It grants authority; it does not mint identities. The operator signs in through the
ordinary OTP flow first.

```bash
DATABASE_URL=postgres://... pnpm ts-node database/scripts/grant-platform-operator.ts \
  --phone +989121110001 --reason "initial operator, approved by <name> on <date>"
```

## 5. Session invalidation — the window, stated exactly

Capabilities are baked into the access token at issue time, so a naive implementation
would leave a revoked operator fully privileged for up to one access-token TTL
(15 minutes by default).

**For ordinary capabilities that is the behaviour**, and the window is one token TTL: a
grant or revocation takes effect at the next `issuePair()`, which happens on login and on
every refresh.

**For privileged capabilities it is immediate.** `CapabilityGuard` re-reads the role
assignment from the database when the required capability is in `PRIVILEGED_CAPABILITIES`,
through a port bound by the composition root (`libs/auth` may not import a `services/*`
package — ADR-011). An operator whose authority was revoked a second ago is refused on
their next request even holding a valid token.

The cost is one indexed lookup per request **to a privileged route** — the admin surface
and nothing else. It fails closed: a verifier that throws denies. If no verifier is bound
(a test module booting one service in isolation), the guard is exactly as strict as it was
before the re-check existed, never weaker.

`GET /v1/me` also resolves live rather than echoing the token, so a revocation removes the
admin surface from the UI at the next page load.

## 6. The persistent audit log

`admin.admin_audit_log`, owned by `beauclick_admin_audit_owner` — a role the application
never connects as. The application holds **INSERT + SELECT and nothing else**. Because it
is not the owner it cannot grant itself back UPDATE. Same reasoning as ADR-009/ADR-017 for
the ledger, same script shape (`database/scripts/admin-audit-roles.sql`), because a second
mechanism for the same guarantee would be a second thing to get wrong.

Unlike `financial`, no second connection pool is needed: INSERT + SELECT is the entire
access pattern, and sharing the main pool is what lets an audit row commit **in the same
transaction as the mutation it records**. `financial` needs a separate pool precisely
because the application role cannot even SELECT there.

Proven against the real database:

```
INSERT  -> ok
UPDATE  -> ERROR: permission denied for table admin_audit_log
DELETE  -> ERROR: permission denied for table admin_audit_log
```

### Transactional, and where it honestly cannot be

`AdminAuditService.record()` takes an `EntityManager`. If the audit insert fails, the
caller's transaction fails with it — an administrative mutation that cannot be recorded
does not happen. The three Phase A mutations (role grant/revoke, verification decision,
phone-conflict resolution) all have this property.

Five pre-existing admin mutations **cannot**, for physical reasons, and they declare it:

| Route | Why not transactional |
|---|---|
| `POST /v1/admin/finance/settlements` | `financial` is a separate DataSource as the append-only writer role (ADR-017). No shared transaction exists. The authoritative record is `financial.settlement_batches`, itself append-only and already carrying the actor. |
| `POST /v1/admin/finance/settlements/:id/reverse` | Same boundary. |
| `POST /v1/admin/search/reindex` | Writes to OpenSearch. No PostgreSQL transaction spans an external index. |
| `POST /v1/admin/search/rebuild-projection` | Same. |
| `POST /v1/admin/notifications/retry-due` | Dispatches to external channels. |

`@AuditAction(action, { transactional: false, because })` makes that a declaration with a
stated reason rather than a silent difference, and `because` is required — the decorator
throws at decoration time without it. All five still write their audit row, after the
action; the row follows rather than accompanies, and a crash in between leaves an action
with no record. That is disclosed rather than designed around, because writing the row
first would leave a record of an action that never happened.

## 7. Structural enforcement

`assertPrivilegedMutationsAreAudited(app)` runs in `main.ts` after init and in the test
factory. A privileged mutation declaring neither `@AuditAction` nor `@AuditExempt`
**prevents the application from starting**, naming the offender.

Read through `DiscoveryService` + `MetadataScanner` — Nest's own supported API — over the
controllers Nest actually instantiated, using the **same metadata key `CapabilityGuard`
reads**. There is no second inventory of admin routes to keep in sync, which would be the
original bug one level up.

An earlier draft walked Express's private `_router.stack`. It was replaced because when
that breaks, it breaks by finding **nothing** — a check that silently passes reads as a
guarantee and is worse than no check.

**So the property is proven in both directions.** `libs/audit/src/audit-enforcement.spec.ts`
(9 cases) asserts a declared mutation IS seen, an undeclared one DOES throw with an
actionable message, exemptions are accepted with their reason, and reads / non-privileged
mutations / ungated mutations are correctly ignored. Additionally verified by deliberate
violation during this phase: removing one declaration from `SearchAdminController.reindex`
produced

```
Privileged mutation(s) registered without an audit declaration.
  SearchAdminController.reindex  (bc_manage_platform)
```

and the declaration was restored.

**Reads are deliberately not audited.** A GET listing settlements changes nothing, and
auditing every read would bury the mutations in noise — including burying them under
people looking at the audit log.

## 8. Verification workflow

The state machine was **not redesigned**. `provider.verification_requests` adds the
QUEUE it never had — who asked, when, who decided, why — and `VerificationService` calls
the existing `transitionVerification()`, which still owns every state and every legal
transition.

- `POST /v1/verification/submit` — session-derived; there is no professional parameter, so
  submitting on someone else's behalf is not a request this API can express.
- `GET /v1/verification/me` — `null` means "never submitted", which is an answer.
- `GET /v1/admin/verification/queue`, `POST /v1/admin/verification/:id/decide` — gated on
  `bc_moderate_verification`, not `bc_manage_platform`.

Transitions used, all pre-existing: `unverified → pending` (and `rejected → pending`, a
resubmission), `pending → verified`, `pending → rejected`. `verified → suspended/revoked`
exists in the machine and is deliberately not exposed — a different operational action with
different consequences, out of Phase A's scope.

Two concurrency guards: a partial unique index on `(professional_id) WHERE status='pending'`
makes a second open request unrepresentable, and the decision compare-and-swaps on the
**request** as well as the professional, so two moderators deciding simultaneously produce
one decision and one audit row rather than a trail naming the wrong person.

`transitionVerification()` gained an optional `EntityManager` so it can join the caller's
transaction. Behaviour is otherwise identical — same CAS, same assertion, same single
event. Without it the status change would commit independently of the audit row, which is
exactly the shape GAP-02-V3 exists to remove.

**Evidence is deliberately absent.** Phase C introduces object storage; V3 has no
file-upload capability of any kind (`R31-03`). Inventing an evidence-URL column now would
sit empty or invite a fabricated path. The queue says so on screen rather than showing an
empty attachment area.

## 9. Phone-conflict resolution (GAP-20)

`identity.phone_conflicts` has collected rows since Phase 1 with `resolved_at`
**write-never**. V2 had the same gap (`AUTH-10`).

**What resolution means, stated on the screen as well as in the code:** it records that a
human looked. It does not merge accounts or touch either identity.
`V3_SECURITY_MODEL.md` §1's rule is "never silently merge identities on ambiguity", and a
button that merged them would be that silent merge with a slower trigger.

Idempotent by compare-and-swap (`resolved_at IS NULL` in the UPDATE's own WHERE), so two
operators clicking simultaneously produce exactly one resolution and exactly one audit row.
An already-resolved conflict returns unchanged and writes **no second audit row** —
re-recording a no-op as an action is how an audit trail stops being reliable.

The queue shows the phone (the whole subject of the conflict) and the other account's id,
and does not join the user table — that would turn a narrow operational queue into a
general-purpose lookup of arbitrary accounts.

## 10. Search quality metrics

**Zero-result rate already existed.** `platformMetrics` has carried `emptyResultRate`
since Phase 3. Rebuilding it would have been exactly the duplication the brief forbids, so
only click-through was added:

`searchSourcedViews` / `clickThroughRate` = `ProviderProfileViewed` with
`dimensions->>'source' = 'search'`, over `SearchPerformed`. Both already exist as
contracts; `source` is on `ProviderProfileViewed` for precisely this reason, its own note
calling it *"the distinction that makes conversion meaningful rather than a raw ratio"*.

**No raw query text is involved anywhere** — `SearchPerformed` has no field that could
carry one, by construction.

Classified `correlation_derived`, not `event_derived`, and the screen shows the server's
own caveat: numerator and denominator are different event types, so one search yielding
three views produces a rate above 100%. That is a true statement about engagement and a
false one about "what fraction of searches led somewhere", and saying so beats letting a
reader assume the friendlier reading.

## 11. Admin frontend

Eight screens in a route group inside `apps/web` — not a second Next.js app. Same decision
and reasoning as `/pro`: one design system, one auth implementation, one deploy, and the
real authorization is server-side regardless of which bundle asked.
`V3_FRONTEND_ARCHITECTURE.md` §10 left this open; `V3.1_PRODUCT_ROADMAP.md` §8 settles it
and says revisit past ~15 screens. It is eight.

```
/admin                  queues first, then platform figures
/admin/verification     review queue, decide with a required reason
/admin/users            role grant/revoke by exact phone
/admin/audit-log        filterable, paginated, read-only
/admin/settlements      platform totals, party lookup, record a payout
/admin/search           index health + quality metrics + two recovery actions
/admin/notifications    channel truthfulness + dead letters + retry
/admin/phone-conflicts  review queue
/admin/loyalty          GAP-10 policy visibility, read-only
```

`AdminShell` reuses the `ProShell` pattern deliberately and uses a **different colour**
deliberately: a professional acting in the wrong context edits their own catalogue; an
operator acting in the wrong context settles someone else's money. The band carries the
mode badge, who you are acting as, **your actual capabilities**, the mode's nav with
`aria-current`, and a permanent way out.

Two screens are read-only on purpose. **Loyalty** shows GAP-10's unresolved values but has
no edit form — turning them into a text box would let an operator set the platform's
economics from a screen with no approval trail; GAP-10 asks for a sign-off pass, not an
input. **Settlement reversal** is not offered from a list: it exists on the API and is
genuinely dangerous, and a button next to every row is how it gets clicked by accident.

## 12. Security

The frontend gate is a **courtesy, not a control**, and both the code and the tests say
so. `AdminGuard` explains a refusal so a customer landing on `/admin` does not see a page
of failed requests; `CapabilityGuard` is what refuses the request.

| # | Case | Result |
|---|---|---|
| 1 | Customer → admin endpoint | 403 |
| 2 | Professional → admin endpoint | 403 |
| 3 | Platform operator → route outside their capability | 403 |
| 4 | Platform operator → grant `administrator` | 403 (never grantable via API) |
| 5 | Customer → role grant | 403 |
| 6 | Forged target user id | 404, generic shape |
| 7 | Self-escalation | 403 |
| 8 | **Revoked role → next request** | 403 **immediately**, holding a valid token |
| 9 | Audit record modified | `permission denied` from PostgreSQL |
| 10 | Admin mutation without audit declaration | **boot/test failure**, offender named |
| 11 | Verification submitted for another professional | not expressible — no parameter |
| 12 | Invalid verification transition | refused by the existing state machine |
| 13 | Phone-conflict resolution by unauthorized user | 403 |

The actor is always the verified session. There is no actor field on any DTO, so
attributing an action to somebody else is not something a check could fail to catch — it
is unrepresentable.

### Colour contrast - measured for the first time, and it found something

The UI/UX audit recorded contrast as the most significant unverified accessibility
dimension. It is now measured, by painting each token onto a canvas and reading the pixel
back. That method matters: the browser returns `oklch()` **unconverted** from
`getComputedStyle`, so a naive parser reads `0.2 0.02 290` as RGB and produces confident
nonsense. The first attempt here did exactly that, returned identical ratios for unrelated
pairs, and was discarded rather than reported.

**Pass AA:** ink/surface **18.09**, ink/background **17.34**, primary/surface **9.86**,
surface/primary **9.86**, primary/primary-soft **8.21**, ink-soft/surface **6.57**,
ink-soft/surface-tint **5.92**, success/success-soft **4.78**.

**Below AA for normal text** (>=3 but <4.5, i.e. large-text only) - a **real finding**,
recorded rather than fixed here because changing a design token affects every customer
screen and belongs to Phase G, which owns the component layer:

| Pair | Ratio | Where it is used |
|---|---|---|
| `error` on `error-soft` | **4.36** | `Alert` error text, error `Badge` |
| `warning` on `warning-soft` | **4.29** | admin context band, warning `Badge` |
| `ink-faint` on `surface` | **3.98** | 12px metadata (ids, timestamps) |
| `ink-faint` on `surface-tint` | **3.58** | 12px metadata on tinted cards |

All four are used at 12-14px, i.e. normal text, so "AA for large text" does not rescue
them. **None is a Phase A regression** - every one predates this phase.

## 15. Known limitations

- **No verification evidence upload.** Phase C. The queue states this rather than showing
  an empty attachment area.
- **`administrator` is bootstrap-only.** Deliberate, and it means a deployment wanting one
  needs database access. Recorded as the intended friction, not an oversight.
- **The non-transactional audit boundary** (§6) is real for five routes. Their primary
  records are append-only elsewhere, but a crash between action and audit row leaves an
  action unrecorded.
- **`identity.users.roles` still exists** as a synced denormalized column. Contracting it
  is a later migration.
- **Ordinary capability revocation still takes up to one token TTL.** Only privileged
  capabilities are re-checked live; extending that to every capability would put a DB
  lookup on every request for a materially smaller benefit.
- **Settlement reversal has no UI.** API-only until a settlement-history screen exists.
- **The audit log has no export.** Reading is paginated and filtered; bulk extraction is
  not offered.
- **Four design-token pairs are below WCAG AA for normal text** (see 14a). Pre-existing,
  now measured, deferred to Phase G with the numbers recorded.

### One deviation from the roadmap's Phase A sketch

`V3.1_PRODUCT_ROADMAP.md` section 15 anticipated `RoleGranted` / `RoleRevoked` v1 **event
contracts** feeding analytics. They were **not** built. The audit log already records every
grant and revocation with actor, before-state, after-state and reason, transactionally -
adding domain events would have produced a second, weaker record of the same facts for a
consumer (analytics) that has no question it currently needs them to answer. If a real
analytics need appears, the events are additive and the audit rows are not thrown away.
Recorded as a deliberate deviation rather than an omission.
