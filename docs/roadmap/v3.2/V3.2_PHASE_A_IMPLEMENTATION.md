# V3.2-A — AI Assistant Foundation: Implementation Report

**Milestone:** deterministic sandbox only. **No real AI vendor, SDK, credential, external call, production-provider claim, or customer frontend was built, and none is authorized by this phase.**

**Baseline:** `86c32f7e780d6081d387352809f0e9c45957fa48` on `master`, verified equal to `origin/master` before any work, with a clean worktree apart from the untracked `start-beauclick.vbs` (unmodified, still untracked, never staged).

**Decisions this phase implements:** `V32-DEC-001` … `V32-DEC-009`, closed by the product owner on 2026-08-29 and recorded in `V3.2_DECISION_REGISTER.md` §A.

**Architecture:** ADR-029 (AI domain, provider port, deterministic fallback, honest provider state) and ADR-030 (the AI threat model). Both were committed **before** any implementation, so the code is reviewable against a fixed boundary rather than alongside one still being drawn.

---

## 1. What was built, in one paragraph

A bounded `ai` module owning an `ai` schema of six tables; a provider-neutral port with a registry that refuses to guess and fails closed; one registered provider, `deterministic`, which narrates the real catalogue, needs no credential, makes no network call, and states in its own reply that it is not a language model; a typed context boundary of exactly four ratified sources with no field able to hold prose; input screening that runs before the provider is invoked; strict output-schema validation followed by independent re-verification of every recommended identifier against the authoritative provider tables; a one-time recorded consent; a daily quota enforced in PostgreSQL atomically with the message insert; a self-scoped customer API on which no route accepts an owner id; two lifecycle events carrying counts and enums and no text; an `ai_provider` readiness row reporting `simulated` with `productionVerified` permanently false; and full subject-data export and erasure.

## 3. Architecture and ADR summary

**ADR-029 — the domain.** `ai` is a bounded module tagged `scope:ai`, added to the closed `ServiceName` contract and to the Nx boundary matrix on the same terms as every other domain: it may depend on `scope:shared` and nothing else, enforced by lint. It contains no search implementation, no ranking, no authorization system, no second recommendation engine, and no mutation authority. Everything it needs from another domain arrives through one of two typed ports bound in the composition root — the only place ADR-011 permits a cross-domain read.

The provider is a port with a registry modelled on `PaymentProviderRegistry`, including the two behaviours that look like paranoia in a registry holding one entry: it refuses to pick a default when more than one provider is registered, and it fails closed rather than substituting. The deterministic provider is a **registered provider with its own key**, never an implicit fallback reached for when something else breaks — the `F-03` reconciliation.

**ADR-030 — the threat model.** Nine threats, each with a control and each with a named test: prompt injection, context exfiltration, hallucinated identifiers, malformed provider output, cost and quota abuse, leakage through logs/metrics/events/analytics/readiness, provider failure and retry storms, privileged reads, and subject-data obligations turned into a leak. It amends `V3_SECURITY_MODEL.md` §5 from prose into mechanism.

## 4. Schema and retention

Six tables in the `ai` schema, created by `database/migrations/ai/20260829400001_create_ai_schema.sql`, verified applied and verified idempotent on re-run.

| Table | Holds | Disposition |
|---|---|---|
| `ai.conversations` | Bounded sessions: status, closure reason, message count, last activity | `subject_data` |
| `ai.messages` | Customer and assistant text, sequence, provider state | `subject_data` |
| `ai.recommendations` | Re-verified catalogue targets, snapshotted public name, click | `subject_data` |
| `ai.assistant_consents` | One acceptance per customer, with its contract key | `subject_data` |
| `ai.usage_daily` | Per-customer, per-Tehran-day accepted count and provider split | `subject_data` |
| `ai.outbox_events` | Transactional outbox | `retained` |

**Three schema choices are load-bearing rather than decorative.**

**Ownership is a foreign key, not a convention.** `conversations` carries `UNIQUE (id, user_id)`, and `messages` and `recommendations` reference it compositely. A row whose owner disagrees with its parent's is *unwritable* — not merely absent from today's queries. This is proved directly: a raw `INSERT` attempting it is rejected by `fk_ai_messages_conversation`.

**Deletion cascades.** `V32-DEC-003` requires destruction rather than a flag, and a cascade makes it atomic with the parent's removal instead of a second statement that can be forgotten or fail alone. There is no `deleted_at`, `is_deleted`, `archived_at`, or `hidden_at` column anywhere in the schema — asserted against `information_schema`, so a soft delete has nowhere to be recorded even if somebody wanted one.

**No provider payload is stored as domain truth.** No prompt, no raw response, no vendor envelope. What is stored is the assistant's user-facing Persian text and the validated recommendations.

**Retention behaviour.** Inactivity closure is applied **on read and on send**, from the injected clock, not only by the sweep — because a sweep can be disabled (`DISABLE_BACKGROUND_SWEEPS` exists and every suite sets it), can fall behind, and can be down for the twenty minutes that matter. If closure lived only in the sweep, the 24-hour bound would be a claim about the sweep's uptime rather than about the product, and it would be untested, because the suites proving it run with the timer off. The sweep exists so `status` is also true for anything reading the table directly. Retention measures age from `last_activity_at`, not `closed_at`: a conversation that closed on day 2 and one that closed on day 29 because the sweep was down should be destroyed together, since the customer's last interaction with both was equally old.

## 5. Provider and fallback semantics

One registered provider: `deterministic`.

- Produces schema-valid Persian assembled from the typed context and nothing else.
- Narrates only already-public, already-curated catalogue data. It generates no claims.
- Byte-for-byte deterministic: no clock read, no random number, catalogue order preserved. It does not re-rank — there is exactly one ranking implementation in this platform.
- States in **every** reply that it is a local assistant and not a language model. That sentence lives in the reply body, not in the interface, where a restyle could hide it.
- Needs no credential, opens no socket, costs nothing.
- Holds no repository, `EntityManager`, service, or HTTP client — so there is no collaborator through which `V32-DEC-004`'s prohibition on mutation could be violated. Its entire input is the request it is handed, and the context carries no user id.
- Obeys every control identically to any other provider: consent, quota, input screening, output validation, re-verification.

**Failure semantics.** A provider that throws, times out, or returns malformed output produces one Persian refusal (`assistant_unavailable`), writes no assistant message and no recommendation, and leaks no provider-internal text. **There is no retry** — not one, not with backoff. **There is no silent substitution**: the deterministic provider serves when it is the *selected* provider and at no other time, because a user cannot distinguish a degraded answer from a real one.

**Honest state.** `ai_provider` joins `DEPENDENCIES` with an `EXTERNAL_VERIFICATION_LEDGER` row (`gap: AI-PROVIDER`, `verified: false`) and `required: false`. The state is computed from the *resolved* provider, so a deployment naming an unregistered vendor reports `not_configured` rather than `configured`. `productionVerified` stays false and no code path can change it — asserted after a real successful exchange, which is the strongest available statement that a working provider does not advance the ledger.

## 6. The context allow-list, exactly

**Included** (`V32-DEC-005`), as three keys on one closed type whose key set is asserted against a literal:

- `journey` — `specialtyIds`, `cityId`, `budgetToman`. Three structured fields, no string field of any kind.
- `candidates` — public professional summaries: id, display name, city id and name, specialty names, verified flag, min and max price, rating average, review count.
- `services` — public service summaries: id, professional id, name, price, duration.

**Structurally excluded**, with no port returning them and no type able to hold them: Journey `notes` and goal titles; review comments and professional replies; CRM notes; internal chat messages; moderation reasons; verification evidence; direct identifiers; financial figures; professional and tenant-private analytics; arbitrary database queries.

**Excluded although public:** a professional's `bio`. A public string authored by one party and fed into a prompt on behalf of another is an injection surface with no compensating benefit — the assistant does not need a biography to say a professional exists, is verified, works in this city, and charges this much.

**The context carries no user id.** A provider has no use for one and every reason not to hold one: it cannot look anything up with it, cannot be asked to reveal it, and cannot leak it into a completion that then gets stored.

**Re-verification reads the authoritative tables, not the search projection.** This is the most consequential detail in the file. The projection is eventually consistent, so a professional suspended thirty seconds ago is still in the index — and re-verifying there would confirm exactly the record the platform has just decided must not be shown. Discovery is fast and eventually consistent; the gate is strictly consistent. A recommendation survives only if the record currently exists, is currently `verified`, and is not soft-deleted; a service additionally requires its professional to still be showable.

## 7. Consent and quota

**Consent.** One row per customer, keyed on the customer. No version column and no withdrawal column — their absence is the decision, because a versioned withdrawable trail is the platform-wide system scheduled at V3.3-E. `ON CONFLICT DO NOTHING`, not `DO UPDATE`: a user who taps twice must not have their original acceptance time rewritten, because that timestamp is the evidence. The acceptance route declares **no request body at all**, so there is no parameter through which a consent owner could arrive. An acceptance recorded against a different `contract_key` is not treated as consent to this one.

**Quota.** Twenty accepted customer messages per user per Tehran calendar day, incremented in the **same transaction** as the message insert, by a single conditional `INSERT … ON CONFLICT DO UPDATE … WHERE used < limit RETURNING`. There is no read-then-write. The HTTP throttler still runs as abuse control but is *not* what makes twenty mean twenty: its storage is in-memory per process, so its effective limit multiplies by instance count, and that topology question (`THROTTLE-STORE`) is unresolved.

The deterministic provider is counted too — zero external cost is not a reason to exempt a path, since the retention and export obligations are identical and a quota that only exists on the expensive path is a quota nobody has tested.

**Refused requests consume nothing.** A rejected, invalid, unauthorized, or injection-blocked request leaves the counter untouched and writes no row. Otherwise anybody holding a token — including one stolen briefly — could destroy a victim's day with twenty junk requests, and a client bug would be indistinguishable from an attack.

The refusal carries a closed browser-safe reason plus the **exact reset instant** at the Tehran calendar boundary, as an absolute timestamp rather than a duration: a duration is stale by the time it renders, and a client counting down to a moment it computed in its own timezone counts down to the wrong one.

## 8. API, events, readiness

**API** — all under `bc_use_ai_assistant`, all self-scoped:

```
GET    /v1/me/ai/consent
POST   /v1/me/ai/consent                          (no body)
POST   /v1/me/ai/conversations
GET    /v1/me/ai/conversations                    (cursor-paginated)
GET    /v1/me/ai/conversations/:id
POST   /v1/me/ai/conversations/:id/messages
DELETE /v1/me/ai/conversations/:id
POST   /v1/me/ai/recommendations/:id/click
```

No route accepts an owner, customer, party, or user id — asserted mechanically over the real route table, which also proves no AI route exists outside `/v1/me/` and no route pairs an admin/operator segment with an AI one. A foreign conversation and a nonexistent one produce **byte-identical** refusals; delete and click answer 204 regardless, for the same reason from the other direction. Anything else is a membership oracle.

Pagination is a keyset cursor over `(last_activity_at, id)`, opaque to the client. An offset would silently skip a row whenever the retention sweep destroyed one between pages.

**Browser-safe contracts** live in `@beauclick/ai-contract` — zero dependencies, no framework, no TypeORM — so the page and the server share one definition of the provider-state vocabulary, the refusal vocabulary, the conversation and message enums, and the size, quota, and retention limits. The provider *key* is stored and never published; the provider *state* is published.

**Events.** `AIConversationStarted` v1 and `AIMessageExchanged` v1, both carrying ids, counts, enums, a length, and timestamps. **No field in either schema can hold prose**, asserted by walking the zod schema and rejecting any string field that is not an enum, a uuid, or a datetime — with a negative control proving the detector detects. A third event was considered and rejected: the recommendation click has no consumer, and emitting an event nothing reads would be publishing because a table changed.

**Analytics** reuses the existing fact table and the existing generic ingestion handler, so there is no bespoke AI consumer and no second place an AI payload is read. `subjectType: 'customer'` — an existing member of the closed vocabulary, so no migration alters that CHECK constraint.

**Readiness** emits enums, booleans, counts, and a gap id only.

## 9. Security and adversarial evidence

Every item below is a passing test, not a claim.

- An injection attempt is refused **before the provider is invoked** — proved with a spy that records zero calls, which is a stronger statement than a 400 status, because a 400 could equally have come from a provider that saw the text.
- A refused message is **not persisted**, and consumes no quota.
- Screening survives zero-width padding, right-to-left overrides, Arabic letter forms, arbitrary whitespace, and case — because a filter defeated by a ZWNJ is decoration, and ZWNJ is how Persian half-spaces are written.
- Injection and private-data refusals reach the browser as **one** reason; the distinction is kept server-side for an operator's counter, because telling a prober which technique was detected tells them how to rephrase.
- A natural-language request for another tenant's figures returns none of theirs, not even an id or a name.
- Journey `notes` and goal titles are absent from the assembled context at any depth, including fragments.
- The context's exact key set is asserted against an independently written literal.
- Hallucinated, suspended, unverified, and soft-deleted targets are all dropped; a response of entirely invalid ids stores a reply with zero recommendations rather than failing.
- The catalogue's display name is used, never one a provider supplied — the completion schema has no field for one.
- A provider returning an `actions` array is rejected outright rather than having the unknown key silently dropped, keeping `V32-DEC-004` structural.
- A full exchange is driven through the real stack and its distinctive marker text is searched for — and absent from — the outbox payloads, the analytics facts, and the readiness response, while present in `ai.messages`, where it belongs.
- No provider-internal text reaches a client on failure.
- Twenty concurrent submissions against a limit of twenty produce exactly twenty acceptances and no internal errors.

## 10. Subject data, export, erasure

`ai` registers a `SubjectDataContract` claiming all six tables. Coverage is proved twice: the claim list is compared against what `pg_tables` actually reports, and `evaluateCoverage` is run with the AI contract **removed**, which must report all six tables unclaimed — that is what stops the application booting, and a test asserting only the passing case would not distinguish a working check from one that always returns "fine".

**Export** returns the complete readable conversation, customer messages and assistant replies alike, ordered by conversation then sequence — the order the customer read them in, not a flat timestamp ordering that interleaves concurrent conversations into one incoherent thread. Each message carries its provider state, so a reader of their own export can tell a deterministic reply from a model's. Consent and daily usage are exported too. A customer who never used the assistant gets three empty sections rather than nothing.

**Erasure deletes rather than anonymizes**, and `retained` is empty. Every other module with a two-party fact reports something there; an AI conversation has exactly one human party, and `V32-DEC-007` states there is no counterpart-retention exception. Erasure runs inside the caller's transaction and rolls back cleanly, leaving the subject fully intact rather than half erased.

## 12. Bugs found

Four, three of them mine and one pre-existing. All are fixed and all now have regression tests.

> **Correction recorded 2026-09-05 (bug #86).** A fifth defect escaped this
> phase and is recorded below as **5**, rather than by editing the original text
> above, which stands as it was written. The count in this paragraph is the
> phase's own count at the time; it was four then and is five now.

**1. `CapabilityGuard` silently ignored controller-level `@RequireCapability` — pre-existing, security-relevant.** The guard read `context.getHandler()` only. Every existing controller happened to decorate each route individually, so it worked by coincidence. A capability written on the *controller* was silently ignored: the reflector found nothing on the handler, `canActivate` returned `true` on its first line, and every route on that controller became reachable by any logged-in user regardless of role — with nothing failing and nothing logged. Found when `AiController` used the class-level form and a **professional** was served the customer assistant surface with a 200. Fixed with `getAllAndOverride([handler, class])`, keeping the more specific declaration winning. No existing controller used the class-level form, so the fix adds enforcement and cannot remove any: no existing route changes behaviour, confirmed by the full suite.

**2. Persian screening patterns were written in pre-canonical form and matched nothing.** Screening runs on a canonicalised copy in which `آ` has already become `ا`; three patterns containing `آ`, and one using `\b` after a Persian letter (JavaScript's `\b` is ASCII-based and recognises no boundary after `ک`), were correct-looking Persian regular expressions that could never fire. A dead pattern is the worst failure a filter can have: it passes review, reads as coverage, and does nothing. Fixed, and a mechanical hygiene guard now asserts over both pattern lists that none contains a folded character, uppercase, or an ASCII word boundary after a non-ASCII letter.

**3. Concurrent sends in one conversation collided on the message sequence.** Two defects, found by the twenty-six-way concurrency case. The reserving transaction read `message_count` without a lock, so concurrent sends computed the same `sequence` and the losers died on a unique violation — a 500 where a queued 201 belonged. Locking the conversation row fixed that half; the second half was subtler. The reply is written in a *separate* transaction (deliberately, so a slow provider does not pin a connection), and it reused the count captured by the first — stale the moment another send committed. Fixed by re-deriving the sequence under the row lock in **both** transactions. The quota was already correct throughout, because the counter and the insert shared a transaction and a failed insert rolled both back — but "correct after an error the user sees" is not correct.

**4. The send response fabricated recommendation ids.** It returned synthesised `${messageId}:${index}` strings instead of the persisted rows, so `POST /recommendations/:id/click` answered 400 for every recommendation the API had just handed out. Fixed by returning the persisted entities.

**5. The retained-conversation cap was never serialised against concurrent inserts — found 2026-09-05, fixed under bug #86.**
`AiConversationService.create()` credited `SELECT ... FOR UPDATE` on the
customer's rows with closing the race, and both the service docblock and the
`ai-lifecycle-privacy` case said so. It does not. A row lock covers the rows the
statement found and says nothing about the ABSENCE of a twentieth row, and under
`READ COMMITTED` a blocked `SELECT ... FOR UPDATE` re-checks only the rows it is
waiting on — it never discovers rows another transaction inserted meanwhile. Five
concurrent creates therefore each saw nineteen, each found `19 >= 20` false, and
each inserted, leaving twenty-four retained conversations against a ratified cap
of twenty.

It survived this phase because the single-shot concurrency case passed on almost
every run; it failed once, on CI run `33953016131` (failed attempt, job
`101271169256`), with `Expected: 1 / Received: 5`. **A diagnostic rerun passed,
and that was not evidence of correctness** — the source still contained no
insert-serialising mechanism of any kind.

Fixed with a transaction-scoped, per-user advisory lock —
`pg_advisory_xact_lock(0x61_69_63_6e, hashtext(userId))`, namespace `aicn`,
distinct from `WishlistService`'s `wish` and asserted so structurally — taken
before stale closure, the count, the eviction and the insert. `FOR UPDATE` is
kept for the row that may be DELETED, and its comment no longer claims to
serialise inserts. `V32-DEC-002` is unchanged: the cap, the eviction rule and the
refusal vocabulary are exactly as ratified, and only their enforcement changed.

The regression evidence is deliberately not a single race: six repeated rounds,
plus a deterministic case in which an outside transaction holds the same key and
the create must block until release, plus proof that rollback frees the lock and
that a different user is never coupled to it.

## 14. What did NOT happen

Stated explicitly because each is a thing a reader might otherwise assume from a green build.

- **No real AI provider, vendor adapter, SDK dependency, credential, fake credential, model identifier, or external network call.** The registered key set is asserted to be exactly `['deterministic']`.
- **No claim of provider-sandbox or production verification.** `ai_provider.productionVerified` is `false` and no code path can set it true.
- **No professional mode** — no capability, no table, no route (`V32-DEC-001`).
- **No operator or admin route reading AI conversation content**, no impersonation, no moderation queue (`V32-DEC-009`).
- **No customer frontend.** Claude Design synchronisation against the real API is the next required step.
- **No internal chat code** or any other V3.2 phase.
- **No release tag.**
- **No modification to `start-beauclick.vbs`** — still untracked and byte-identical.
- **No V3.1 blocker closed, narrowed, or absorbed.** `HOSTING`, `HOSTING_GRANTS`, `GAP-06b`, `GAP-11`, `OPS-04`, and `THROTTLE-STORE` are untouched. `AI-PROVIDER` is a new open gap, not a closed one.
- **No final Persian legal or disclosure copy.** The deterministic provider's honesty sentence is an engineering statement about what produced a paragraph, not a legal disclosure.
