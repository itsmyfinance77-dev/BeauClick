# V3.2+ Product Roadmap

**Status:** OWNER-DIRECTED PLANNING — scope recorded 2026-08-29. No V3.2 code, migration,
release, or tag is created by this document.

**Entry condition:** V3.1 reaches `IMPLEMENTATION COMPLETE / SANDBOX READY`. Production
enablement may continue in parallel, but no V3.2 feature may weaken or bypass V3.1's
External Enablement Gate.

**Purpose:** turn the former V3.2+ deferral bucket into an ordered product programme while
keeping unresolved product decisions, vendor dependencies, and evidence-gated scale work
visible rather than silently settling them in implementation.

## 2. Product and architecture constraints

1. The repository and accepted ADRs remain the source of truth.
2. No V3.2 feature may create a second authorization, pricing, financial, search, media,
   notification, or analytics engine where V3 already has one.
3. Ownership is derived from the authenticated session, never a client-supplied user,
   professional, business, conversation, or party id.
4. AI and chat are separate domains. They may share UI primitives and notification/media
   ports, but human messages must not be stored as AI conversations or automatically sent
   to an LLM.
5. Free text is PII-adjacent by default. Review text, Journey notes, CRM notes, and human
   chat messages are excluded from AI context unless a later explicit, narrow, consented
   contract says otherwise.
6. Provider-specific code waits for an actual provider decision and test account. A local
   HTTP server or rule-based fallback proves an interface, not external delivery.
7. Every new data-owning table must register with the Phase E subject-data contract before
   the application may boot.
8. Every new event uses the existing transactional outbox and versioned event catalogue.
9. V3.2 inherits the evidence vocabulary from `V3.1_EXTERNAL_ENABLEMENT_STRATEGY.md`:
   local, provider-sandbox, and production verification remain distinct.

## 3. V3.2-A — AI Assistant Foundation

**Goal:** safe, useful customer and professional assistants that can run locally with an
honest deterministic fallback and can later use a real LLM provider without changing domain
or security boundaries.

**Scope:**

- `ai` schema and module, conversation/message model, and an explicit decision on single
  thread versus conversation history (`GAP-12`).
- Customer and professional modes with separate capabilities and tenant scopes.
- Session-derived authorization followed by curated-context assembly; no raw database or
  arbitrary-query access for a provider.
- Typed context ports to Journey and other approved domains. Free-text exclusions enforced
  by types and adversarial tests, not prompt wording.
- Provider registry, deterministic rule-based fallback, timeouts, safe failure states, and
  provider-health reporting that never claims a fallback is a live LLM.
- System constraints, input length and injection controls, output-schema validation, and
  independent re-verification of every model-recommended entity id against real data.
- Usage quotas, cost accounting, rate limits, analytics without raw prompt retention, and
  operator-visible health/usage surfaces.
- Persian-first customer and professional assistant UI designed through Claude Design before
  production frontend implementation.

**External gate:** hosting-region/provider reachability, provider selection, credentials,
and one end-to-end provider-sandbox/live verification.

**Definition of Done — sandbox milestone:** both modes work end to end through the real app
with deterministic fallback; cross-tenant and prompt-injection tests pass; every output is
validated; missing credentials fail honestly; no external-provider claim is made.

### 3.1 Status — DELIVERED to the sandbox milestone, 2026-08-29

Implemented against ADR-029 and ADR-030, with `V32-DEC-001` … `V32-DEC-009` closed by the
owner. The full report is `V3.2_PHASE_A_IMPLEMENTATION.md`.

The Definition of Done above is met with **one scope change the owner made, not a shortfall**:

- **"Both modes" is now one mode.** `V32-DEC-001` decided customer-only for the first release
  and deferred professional mode entirely — no `bc_use_professional_ai`, no professional
  conversation table, no professional route. That is sequencing the adversarial test surface,
  not cutting scope: professional mode reads settlement and analytics facts and is the
  strictest tenant-isolation surface in the platform. When it is approved it gets its own table
  keyed on the party, never a `scope` column on the customer table.

Everything else in the scope list landed, with two clarifications worth recording because a
reader could otherwise assume more or less than was built:

- **"Deterministic rule-based fallback" is a registered PROVIDER, not a fallback.** It has its
  own key, is selected explicitly, and is never reached for when something else breaks — a
  provider failure produces an honest refusal instead. That is the `F-03` reconciliation, and
  it is the difference between a user knowing what answered them and not.
- **The Persian-first assistant UI was NOT built**, as the scope list itself requires: Claude
  Design synchronises against the real API first. This phase delivers the API it will be
  designed against.

**The external gate is unchanged and narrowed.** Hosting, provider selection, credentials, and
reachability all remain open, and `V32-DEC-008` adds one more: the platform-wide monetary spend
ceiling is deferred, and **a real provider must not be enabled while it is undecided.**

## 4. V3.2-B — Internal Chat Foundation

**Goal:** privacy-bound, abuse-resistant human messaging inside BeauClick without coupling
human conversation data to the AI provider.

**Product decisions required before schema implementation:**

- permitted participants: customer↔professional, customer↔business, staff groups,
  platform support, or a subset;
- when a booking or commercial relationship is required to start a conversation;
- retention/deletion policy and what account erasure does to the other participant's copy;
- attachment types, limits, and access lifetime;
- blocking, reporting, moderation, escalation, and support access;
- delivery expectations: polling, SSE, WebSocket, push, read receipts, typing indicators,
  and offline behaviour.

**Engineering scope after those decisions:**

- conversation, participant, message, delivery/read-state, block/report, and moderation
  contracts with database-enforced tenant boundaries.
- Versioned pagination, unread counts, notification integration, idempotent send, ordering,
  retry, and duplicate-delivery safety.
- Attachment reuse through the media boundary with private access class; no public object
  URLs and no duplicated upload engine.
- Subject-data export/erasure registration, audit rules for privileged moderation, retention
  sweep, abuse throttling, and adversarial cross-tenant tests.
- Modern RTL inbox, thread, composer, attachment, empty/offline/error, block/report, and
  moderator states in the design package and frontend.

**Non-goal:** human messages are not AI context by default. Any future AI summarization or
reply assistance is a separate consent, privacy, retention, and output-validation decision.

### 4.1 Status — decisions closed 2026-08-30; externally-independent backend milestone delivered

`V32-DEC-010` … `V32-DEC-015` are closed. Implemented against ADR-031 (counterparty derivation,
eligibility, send window) and ADR-032 (privacy, abuse, moderation). Full report:
`V3.2_PHASE_B_IMPLEMENTATION.md`.

**Four places the delivered scope differs from the prose above**, each an owner decision rather
than a shortfall:

- **"Attachment types, limits, and access lifetime" is not answered — attachments are out
  entirely.** No table, no contract field, no event field, no media purpose, no placeholder. The
  scope list's "attachment reuse through the media boundary" is deferred with
  `CHAT-ATTACHMENT-STORAGE`, and building it against local disk would have produced a feature
  that works in development and silently loses files in production.
- **The participant matrix is narrower than "customer↔professional, customer↔business" implies.**
  The customer never chooses; the counterparty is derived from the immutable historical seller
  snapshot on the booking's order. Business-inbox access is the owner and active managers only.
- **Delivery expectations are settled as polling plus in-app notification.** No SSE, WebSocket,
  push, typing, presence, or delivery receipt. Read state and unread counts are in.
- **The "modern RTL inbox, thread, composer…" frontend is NOT built.** Claude Design
  synchronises against the fixed backend and browser contract first.

**Also out, and worth stating because the prose above does not:** group conversations, named-staff
conversations, platform-support conversations, message editing, and participant-initiated message
deletion.

## 5. V3.2-C — Retention: Referral and Wishlist

### Referral

- Invite/link/code lifecycle and attribution rules.
- Qualification from a real `BookingCompleted` or another explicitly approved event.
- Loyalty integration using the existing idempotent ledger.
- Fraud, self-referral, duplicate-device/account, cancellation/refund, expiry, and replay
  rules decided and tested before rewards can move.
- `pointsReferralQualified` requires an owner-approved business value; zero must remain an
  honest disabled state rather than a silent no-op.

### Wishlist

- Explicit product decision on saveable targets: professionals, services, portfolio items,
  or an approved subset.
- Private per-customer collection, stable pagination, idempotent add/remove, deleted-target
  behaviour, and subject-data export/erasure registration.
- Search/profile integration and useful empty states without creating a second discovery
  or recommendation engine.

**Definition of Done:** a referral can qualify exactly once under an approved rule and a
wishlist survives normal target changes without leaking another customer's collection.

### 5.1 Status — COMPLETE 2026-09-02

All V3.2-C decisions through `V32-DEC-036` are closed. Wishlist, referral attribution,
qualification, two-sided reward, full-refund reversal, the adversarial suite, and both design
surfaces have been delivered. The final measured scope is **59/59 Story Points**. Reward values
remain honestly disabled at **0/0**; platform-sent referral channels, approved public copy, and a
public business-profile capability remain explicitly outside this milestone rather than being
claimed as delivered.

**Six places the approved scope differs from the prose above**, each an owner decision rather than
a shortfall:

- **"Professionals, services, portfolio items, or an approved subset" is settled at professionals
  and services.** Portfolio items are out because a portfolio item id is not stable across an
  ordinary remove-and-re-add. Businesses are out because **no public business route exists
  anywhere** and businesses have no search document — saving one would need a
  public-business-profile capability that is scoped nowhere.
- **"Deleted-target behaviour" is answered against the states the schema actually has.** There is
  no `is_published` or `is_hidden` column on either provider table. Unavailable means soft-deleted,
  or the owning professional `suspended`/`revoked`; merely `unverified` does **not** count, because
  ordinary search still returns those professionals and a stricter rule would make the wishlist
  contradict the page the customer saved from.
- **"Search/profile integration" carries no discovery effect at all.** The wishlist emits no event,
  no notification, no analytics fact, no popularity count, and no ranking signal, and `wishlist` is
  therefore not added to `ServiceName`.
- **"Fraud, self-referral, duplicate-device/account … rules" ships without device signals.** No
  device, IP, browser, or fingerprint identity signal is collected. The bounded-exposure control is
  a transactional cap of **10 qualified referrals per referrer per Tehran calendar month**, and the
  erase-and-re-register gap is recorded as accepted rather than claimed closed.
- **"Cancellation/refund" narrows to refund only.** `LEGAL_TRANSITIONS` makes `completed` terminal,
  so a qualifying booking can never be cancelled; only a **full** refund of its order reverses.
- **`pointsReferralQualified` becomes two values and two ledger reasons, both at 0.** One reason
  cannot idempotently pay two people against one referral id.

**Also settled, and worth stating because the prose above does not:** one list only with no named
collections; no display snapshots on the saved row; no manual-review queue, appeal workflow, or
override route; `ReferralAttributed` is deliberately **not** defined, because it has no consumer;
and the referral share channel is copy-code, copy-link, and native share as **contract and design
only**, since this milestone builds no production frontend.

**One correction to a previously recorded blocker.** Phase F blocker 15 (cancellation and refund
policy) decides *when* a refund is granted. It does **not** block referral from reacting to a full
refund already authoritatively recorded, so the referral reversal work is **buildable and not
externally blocked**. `V3.2_EXTERNAL_DEPENDENCY_LEDGER.md` row 15 is corrected accordingly.

### 5.2 Story #8 — Wishlist contract, persistence, API, privacy lifecycle: DELIVERED 2026-08-30

Implemented against **ADR-033**, committed before the schema as V3.2-A and V3.2-B both did.

**What shipped.** A `wishlist` module owning a `wishlist` schema of exactly **one table**;
`@beauclick/wishlist-contract`, the fourth zero-dependency browser-safe package;
`POST`/`GET`/`DELETE` under `/api/v1/me/wishlist/items`, authenticated and session-scoped with no
new capability; and the subject-data claim, export, and hard-delete erasure.

**Three properties worth naming, because each is a decision rather than a default:**

- **The cap is enforced under a transaction-scoped advisory lock**, not by a counter row and not
  by a preceding count. Both obvious implementations overshoot: a `SELECT count(*)` then `INSERT`
  is `GAP-04` exactly, and a single `INSERT … SELECT … WHERE (SELECT count(*)) < 500` is *also*
  wrong, because under `READ COMMITTED` each transaction evaluates the subquery against a snapshot
  taken before any sibling's insert is visible. The counter-row shape used by `ai.usage_daily` and
  `chat.send_counters` was rejected here specifically: those limit a *rate*, where the counter is
  the state, whereas here the rows are the state and a counter would shadow them, need a decrement
  on every remove and on erasure, and be able to drift.
- **Add-time validation reads the authoritative `provider` tables, never the search projection**,
  and deliberately does **not** require `verified` — ordinary search returns unverified
  professionals, so refusing to save one would contradict the page the customer is saving from.
- **The tombstone is a property of what does not happen.** No foreign key out of the schema, no
  cascade, no sweep, no soft-delete column, and no filter on target state — asserted against
  `pg_constraint` and `information_schema` so a later migration has to come and say why.

**Not built, and absent rather than stubbed:** the target-state projection and saved-state
hydration (Story #9); any frontend or design artifact (Story #10); every referral table, route,
event and ADR (Stories #11 onward); any domain event, outbox table, `ServiceName` entry,
notification, analytics fact, popularity count, ranking signal, sweep scheduler, or display
snapshot. Businesses and portfolio items remain out as saveable targets, and the missing
public-business-profile capability is recorded as unscheduled in the capability catalog.

### 5.3 Story #9 — Wishlist discovery integration and target-state projection: DELIVERED 2026-08-31

Implemented against **ADR-034**, which is the half ADR-033 §4 and §6 deferred. It revisits no
owner decision: ownership, the target set, the tombstone rule, the cap, and the erasure model are
unchanged, and **no search visibility policy was touched**.

**What shipped.** `WishlistItemView` gained one field, `state: 'available' | 'unavailable'`, computed
on every read; `saved: boolean | null` was added to `GET /v1/search/providers`,
`GET /v1/providers`, `GET /v1/providers/:id`, and `GET /v1/providers/:id/services`. Both additive —
no key was removed or renamed. **No migration**: the saved-state read is served by the existing
`uq_wishlist_saved_items_user_target`, and the availability read is by primary key.

**Four properties worth naming, because each is a decision rather than a default:**

- **The Story #8 port was absorbed, not extended.** `isSaveable(manager, target)` became
  `availableTargets(manager, targets)`, exactly as ADR-033 §4 said should happen if #9 needed a
  broader one. `save` now calls the batch with a single-element array. Keeping both would have been
  two implementations of `V32-DEC-021`, free to drift.
- **Availability is read from the authoritative `provider` tables and the projection is never
  consulted.** Proved in both directions: a professional suspended without a reindex reads
  `unavailable` while the stale document still says `verified` and search still returns them; a
  professional spuriously dropped from the index reads `available` anyway.
- **Deleted, suspended, and revoked render as one value with no cause**, asserted by
  whole-response comparison rather than field by field. The absence is structural — the port returns
  a set of keys, not a map of reasons, so no value in the system could carry a cause.
- **Saved state is hydrated after the search, never indexed into it.** One document per professional
  is shared by every customer, so a per-customer field there would mean either an unbounded document
  count or a per-customer filter on a shared document. Hydrating afterwards also means a save can
  never become a ranking signal, which the suite checks by comparing a signed-in caller's result
  order against an anonymous one's.

**Query evidence.** A page of forty saved items costs **two** target queries and **one** saved-state
query; a page of one costs one and one. Pinned at exact counts, and verified non-vacuous — with
`availableTargets` temporarily rewritten as a loop, the same case costs 60.

**Not built, and absent rather than stubbed:** any frontend or design artifact (Story #10); every
referral table, route, event and ADR (Stories #11 onward); saved state on the nested `services`
array inside a search result (refused on the batching argument, ADR-034 §8); and — still — any
domain event, outbox table, `ServiceName` entry, notification, analytics fact, popularity count,
ranking signal, or display snapshot. The temptation is real for the first time in this story,
because the platform now *computes* that a target went away; it is a computation discarded at the
end of the response, not a fact anything is told about.

### 5.4 Story #27 — Referral attribution claim lifecycle: DELIVERED 2026-08-31

Implemented against **ADR-036**, committed before the schema as every V3.2 story has done. It
follows Story #11 (the referral module, schema, code generation and share contract, delivered
2026-08-31 against ADR-035), and revisits none of it: the code format, the share channel, the
invite link, and `referral_codes`' own privacy disposition are unchanged.

**Why this was its own five-point story.** The platform has **no signup route and no new-account
signal.** `POST /v1/auth/verify-otp` is `@Public()` and is simultaneously login and registration;
`AccountResolverService.resolveOrCreate(phone)` creates the row, and `LoginResult` carries no
`isNewUser` flag. A referral code therefore cannot be attached "at signup" without widening a
public unauthenticated route to accept a bearer credential — which is why Issue #11 was split
rather than re-pointed.

**What shipped.** `POST /api/v1/me/referral/claim`, authenticated, with the referee resolved from
the session and the code as the only client-controlled input. Two tables — `referral.referrals`
and `referral.claim_attempts` — and one migration. `@beauclick/referral-contract` gained three
ratified limits, one refusal code, and two closed shapes, still with zero runtime dependencies.

**Six properties, each a decision rather than a default:**

- **"Attributed once, ever" is a unique index and nothing else.** There is no application check in
  front of `UNIQUE (referee_user_id)` that "really" enforces it. Two concurrent claims both pass
  every eligibility read — under `READ COMMITTED` neither transaction sees the other's uncommitted
  row — and the constraint decides which wins; the loser reads `23505` **by constraint name** and
  returns the collapsed refusal.
- **Self-referral is unrepresentable, proved through raw SQL.** `CHECK (referrer_user_id <>
  referee_user_id)`. The service refuses it earlier so a caller gets the same answer as every other
  refusal, but the guarantee is the constraint, and the suite proves it by an `INSERT` that
  bypasses the service entirely.
- **Attribution is immutable, enforced by the repository's first database trigger.** `V32-DEC-019`
  requires it and names no mechanism. The platform's existing one — `REVOKE UPDATE` plus a separate
  owner role (ADR-017) — is unavailable because `referral` is application-owned and the tombstone
  below needs the app role to `UPDATE` this very table; a column-level grant would leave the owner
  one statement from re-granting itself, which is ADR-017's own argument against an app-owned
  ledger. A `BEFORE UPDATE` trigger fires for the owner too and distinguishes the four frozen
  columns from the two writable ones.
- **The claim throttle is PostgreSQL, not the HTTP throttler.** Ten attempts per authenticated
  caller per hour, charged by one conditional `INSERT … ON CONFLICT DO UPDATE … WHERE
  attempt_count < 10 RETURNING`. `BeauClickThrottlerGuard`'s storage is per-process, so its
  effective limit multiplies by instance count while `THROTTLE-STORE` is unresolved. Twenty
  concurrent requests yield exactly ten charged.
- **One refusal, and the mechanism is a constructor signature.**
  `ReferralClaimRefusedException` takes **no arguments**, so there is no per-call-site value that
  could differ between the six cases `V32-DEC-019` enumerates. The suite compares **complete
  response bodies**, not status codes — a status-only assertion passes while a `details.reason`
  leaks the branch.
- **Both eligibility facts are read through narrow ports, inside the claim's transaction.**
  `ReferralIdentityPort` over `identity.users.created_at` and `ReferralBookingPort` over
  `booking.bookings`, declared by `referral` and bound in the composition root (ADR-011). Neither
  has a default implementation: a permissive stub would pass every test written against the
  referral module alone while silently disabling two of the six rules in production.

**The two boundaries, to the millisecond.** Account age is **≤ 30 days, inclusive** — an account
created exactly 30 days ago still claims — and the pending expiry is `attributed_at` **+ 90 days**
as an absolute UTC duration, both computed from an injected clock and both sides of each boundary
tested frozen. Deliberately **not** a Tehran calendar boundary: `V32-DEC-019`'s referrer cap *is*
per Tehran calendar month and belongs to Story #12, and the two must not be confused.

**Privacy: the first `retained` table this module owns.** `V32-DEC-019` ratifies it —
`referral.referrals` is retained **with the erased side's identity tombstoned**, because the row is
what explains a retained loyalty entry the *other* party still holds. `referral.claim_attempts` is
`subject_data` and deleted, exactly as `chat.send_counters` is treated. The tombstone reuses the
platform's shared `tombstoneFor` and invents no mechanism. Export shapes are asymmetric per the
decision: a referrer's carries no referee identity, and a referee's carries **no referrer code** —
structurally, because the table stores the code's id and never the string.

**Three semantics `V32-DEC-019` left implicit, resolved from its own reasoning rather than chosen**
(ADR-036 §6, §11): every request consumes an attempt including a refused one, because
`V32-DEC-034` prices this exact number as a **guess rate** and makes it the stated reason the code
is ten characters rather than eight; a successful claim consumes one like any other; and a spent
limit returns **429** rather than the collapsed refusal, because exhaustion is in neither the
decision's six-case list nor Issue #27's, and it reveals only how many requests the caller
themselves made.

**One bug found, and it was the adversarial suite that found it.** The claim DTO originally
validated the code's shape with `@Matches`. The platform's `ValidationException` serialises
class-validator's `ValidationError`, which carries the submitted `value` — so a malformed code came
back in the response body. The realistic trigger is not an attacker but a customer typing their
inviter's **real code in lowercase**: malformed, because the shape check is deliberately
case-sensitive, and one `toUpperCase()` from the live credential, in a payload that reaches
whatever logs client errors. `V32-DEC-033` keeps a referral code out of exception messages. The
check moved into the service, where a malformed code becomes the ordinary collapsed refusal — which
also made the route *more* indistinguishable and stopped malformed probes being free.

**Not built, and absent rather than stubbed:** `ReferralAttributed` is still **not defined and not
emitted**, and the reason is unchanged — it has no consumer, and Story #12 qualifies on
`BookingCompleted` (`V32-DEC-018`), not on an attribution event. There is no `referral.outbox_events`
table, no `reward_grants`, no `referrer_counters`, no monthly cap, no reward value, no
qualification or reversal state, no manual-review or appeal path, no device/IP/browser/fingerprint
signal, no notification, no analytics fact, no metric, and no frontend or design artifact
(Stories #12, #28, #13, #14).

### 5.5 Story #12 — Referral qualification and independent two-sided loyalty reward: DELIVERED 2026-09-01

Implemented against **ADR-037**, committed before the schema as every V3.2 story has done. It
continues Story #27 and revisits none of it. **This is the first referral story that crosses a
ledger**, and most of what follows is a consequence of taking that seriously.

**What shipped.** `BookingCompleted` v1 is consumed and qualifies a pending referral exactly once;
`referral.referrals` gains `status`, `qualified_at` and `qualifying_booking_id`; three new tables
(`reward_grants`, `referrer_counters`, and the module's first `outbox_events`); two ledger reasons
and two independent configured values; and `ReferralQualified` v1, notified in-app to both parties.

**Three things Story #12 needed already existed and were already correct**, which is worth
recording because it changed the shape of the work: `LoyaltyLedgerService.award(input, manager)`
already accepted a caller's `EntityManager`; it already returned early at zero **without inserting
a row or consuming the idempotency slot**, with a docblock naming `pointsReferralQualified` as the
reason; and `returningRows`/`affectedAny` already existed as the fix for the `[rows, rowCount]`
trap, having been written after that shape caused two separately-diagnosed bugs.

**`BookingCompleted` v1 was already sufficient**, so **no lookup port over `booking` was
declared**. It carries `customerId` — the referee — and `bookingId`. The absence is a finding
rather than an omission: a port here would have been a seam nothing crossed.

**Seven properties, each a decision rather than a default:**

- **Only `BookingCompleted` qualifies, and the refusals are structural.** There is exactly one
  caller of `qualify`. Nothing polls the booking table, nothing reads `OrderPaid`, and no route can
  trigger a qualification. `V32-DEC-018` calls the `OrderPaid` refusal the sharpest: money moves
  *before* delivery and can be refunded within minutes.
- **The compare-and-swap is the only guard**, on `status = 'pending' AND expires_at > now` with a
  **strict** expiry comparison, and the affected-row count read through `returningRows` — never
  `result.length`, which is always 2 for an `UPDATE … RETURNING` and is how a CAS silently stops
  observing its own loss. Everything else lives inside the success branch, so a replay, an expired
  referral, and a never-referred customer all cost one `UPDATE` affecting zero rows.
- **The status, the instant and the qualifying booking move in ONE statement**, and
  `ck_referrals_qualification_complete` makes any other combination unwritable — so a crash between
  "marked qualified" and "recorded which booking" is unrepresentable rather than merely unlikely.
- **Both grants are always written**, whatever either side's outcome. `V32-DEC-019`'s owner
  correction is explicit: an invited customer must never lose their own reward because of somebody
  else's activity, so at the cap the referral still qualifies, the referrer is marked `capped`, and
  **the referee is still paid**.
- **Zero is honestly disabled, and it is guarded twice.** A zero side does not call the ledger at
  all, and the ledger would refuse anyway — so **no row is written and no idempotency slot is
  consumed**, and a later approved figure remains awardable against the same referral id. That last
  clause is the whole point: a zero row would occupy the slot permanently and the eventual real
  award would be silently deduplicated away.
- **The cap is one conditional statement**, the third use of the shape after `chat.send_counters`
  and `referral.claim_attempts`. It is a module constant rather than an environment variable: the
  reward *values* are configuration because `V32-DEC-016` expects the business to set them, but the
  *cap* is an abuse control the same decision fixes at a number.
- **The financial role boundary is preserved by not being touched.** `loyalty.points_entries` is
  owned by `beauclick_app`; `financial.ledger_entries` is a different object owned by
  `beauclick_financial_owner`. The ledger's `reason` column is `VARCHAR(64)` with **no CHECK
  constraint**, so two new reasons needed **no loyalty migration at all**, and the referral
  migration contains zero `GRANT`, `REVOKE` or `ALTER OWNER` statements.

**Two ledger reasons, and why one would be a bug.** The ledger's idempotency is
`UNIQUE (reference_type, reference_id, reason)`, so a single shared reason would make the two
people's rewards for one referral id collide in the same slot — the second would silently never
happen. The reference is `('referral', <referral id>)`, never the booking id, because the guarantee
is *one reward per referral per side*. The suite proves both directions: two reasons pay two
people, and a deliberately shared reason deduplicates the second away.

**The pre-existing single `referral_qualified` reason was removed**, not left beside the pair. It
was the exact shape `V32-DEC-016` forbids and was **structurally unwritable** — its configured
value was 0 and `award()` returns before the `INSERT`, verified as zero rows — so removing it
destroyed no history while removing the forbidden shape from reach. The **false V2 history claim**
in `loyalty.config.ts` is corrected in the same commit, which `V32-DEC-016` assigns to *"the
implementation phase, not this governance record."*

**Configuration refuses to boot on a malformed reward value, in every environment.** A silent
fallback would turn `-5`, `1.5` or `abc` into **0** — and 0 is a *decided* value here, so the
misconfiguration would be indistinguishable from a correct deployment that had deliberately
disabled rewards, while the operator who set it believed a reward was live.

✅ **One parameter no closed decision pinned precisely — flagged rather than assumed, and now
ratified.** `V32-DEC-019` says *"Tehran calendar month"*, and that admits two readings whose
windows differ by about three weeks: the **Gregorian** month evaluated in `Asia/Tehran`, or the
**Solar Hijri (Jalali)** month, Iran's official calendar, which this repository fully supports and
which `persian-utils` says the platform uses *"never Gregorian"* for user-facing dates. `ai`'s
`tehranCalendarDay` precedent does **not** settle it — for a *day* the two calendars are the same
window and only the label differs, so the question a *month* asks had never been exercised.

Story #12 shipped the **Gregorian-in-Tehran** reading and flagged it for ratification, the course
`ADR-035` §3 took with the code format before the owner ratified it as `V32-DEC-034`. **The owner
ratified the Solar Hijri month on 2026-09-01 as `V32-DEC-035`**, so the flagged reading was wrong
and was corrected the same day — see §5.6. The correction landed while **both reward values were
still 0**, which is the only moment at which a payout window can be re-cut for free.

**Two bugs found, neither by reading code.** The referral outbox table invented `dispatched_at`
where `OutboxEventEntityBase` declares `published_at`, and omitted `attempts` and `last_error`; it
migrated cleanly, compiled, and passed typecheck, lint and the fast suite, because TypeORM builds
its `SELECT` from the *entity*. Only executing against a real table caught it. And the mutation
pass found that both zero-value tests were observing the **ledger's** guard rather than the
domain's — ADR-037 §8 claims two *independent* reasons the slot stays free, and only one was
observed; a port-spy case was added rather than the assertion weakened.

**Not built, and absent rather than stubbed:** everything in Story #28 — no refund consumer, no
`OrderRefunded` handling, no order-lookup port, no negative ledger row, no clawback, no
below-zero balance, no lifetime-earned or tier reversal, and no `ReferralReversed`. Also no
`ReferralRewarded`, `ReferralCapped` or `ReferralExpired` (states and non-facts, with no consumer);
no manual review, appeal or administrator override; no device, IP, browser or fingerprint signal;
no second points ledger, referral balance, direct balance write, cash payout or promo code; no
SMS, email, push or external provider; and no frontend or design artifact (Stories #13, #14).

The single thing this story does for Story #28 is persist `qualifying_booking_id`, so the reversal
story can identify the qualifying order without guessing or scanning historical events. **That is a
column, not a behaviour**, and nothing in this story reads it.

### 5.6 Story #12 correction — the referral cap's calendar is Solar Hijri: RATIFIED AND CORRECTED 2026-09-01

A narrowly scoped correction to the already-closed Story #12, implementing **`V32-DEC-035`**. Story
#12's outcome, story points, and closed state are unchanged; nothing else about the cap is
reopened.

**What was wrong.** §5.5 shipped the cap bucketed by the **Gregorian** year-month evaluated in
`Asia/Tehran`, and said so — `ADR-037` §7 recorded it as *"an engineering interpretation of an
owner phrase, not a ratified parameter"* and flagged it. `V32-DEC-019` says *"10 qualified
referrals per referrer per **Tehran calendar month**"* without naming a calendar, and the two
candidate readings put a referrer's allowance reset roughly **three weeks apart, every month**.

**What the owner decided.** The **Solar Hijri (Jalali) month**, each period beginning at **00:00
`Asia/Tehran`** on the first day of the Jalali month. The persisted key stays `YYYY-MM` with ASCII
digits and a zero-padded month, but the year and month are now **Jalali** values — `1405-06` rather
than `2026-09`. A Gregorian month evaluated in Tehran is explicitly **not** the policy.

**Why the flag was right to exist.** The `ai` module's `tehranCalendarDay` looks like a precedent
for Gregorian-in-Tehran, and is not one: for a **day**, the two calendars are the *same window* and
only the label differs. The question a **month** asks had therefore never been exercised anywhere
in the codebase, and Story #12 inherited an interpretation nobody had chosen. Flagging it is what
produced the decision.

**The implementation, and what it deliberately does not add.** The period key is now
`toJalali(...)` applied to `wallClockIn(instant, 'Asia/Tehran')` — this repository's own
`@beauclick/persian-utils`, the single Jalali implementation the whole platform already uses. **No
new external dependency**: `toJalali` is pure arithmetic on a 2820-year cycle routed through Julian
Day Numbers, already verified against the 1979-02-11 ↔ 1357-11-22 reference point, and it does not
depend on the container's ICU build for calendar correctness — which an `Intl` `ca-persian`
formatter would have. Three concerns stay separate: instants are UTC, the timezone is IANA
`Asia/Tehran` read through `formatToParts`, and the calendar is arithmetic that knows nothing about
zones.

**No migration, and that is evidence rather than convenience.**
`referral.referrer_counters.period` is `VARCHAR(7)` under `^[0-9]{4}-(0[1-9]|1[0-2])$`, which
`1405-06` satisfies unchanged. No row can exist under the old reading: the table arrived in the
migration merged as `597c88d` on 2026-09-01, **no release tag contains it**, the CD pipeline has
never run — its own header records that it *"cannot deploy anything, because there is nowhere to
deploy to"* while `HOSTING` is unresolved — and the only database that has ever held it is a
development scratch database, verified empty. There is no cutover, no mixed-calendar period, and no
user data to rewrite. The migration's column comment is corrected in place because it describes a
policy rather than a schema, and it has never been applied to any environment that outlives a test
run.

**What did not change:** the limit of **10**, the per-referrer scope, the absence of a lifetime
cap, the single conditional `INSERT … ON CONFLICT … WHERE count < limit RETURNING`, the transaction
boundary, replay and concurrency behaviour, the independence of the two reward sides at the cap,
the qualification trigger, the reversal boundary, the notification policy, and **both reward values,
which remain 0**.

**Evidence.** Boundary tests at Nowruz 1405 (00:00 Tehran on 2026-03-21 = 20:30 UTC on 03-20), at a
31-day month roll (1 Mehr 1405), at a 30-day month roll (1 Azar 1405), across Esfand in both a leap
(1403) and a non-leap (1404) Persian year, and the two decisive pairs: a **Gregorian** month change
inside one Jalali month does **not** reset the cap, and a **Jalali** month change inside one
Gregorian month **does**. Non-vacuity is proved by substituting the old Gregorian helper and
watching the Jalali boundary tests fail.

### 5.7 Story #28 — Referral full-refund reversal and loyalty clawback: DELIVERED 2026-09-01

Implemented against **ADR-038**, committed before the schema. It completes the referral lifecycle:
Story #27 made the relationship, Story #12 made it pay, and this makes it *unpay* when the service
was refunded. `V32-DEC-018` splits the two directions in one sentence — **booking is the
qualification authority, payment is the reversal authority** — and neither moved.

**What shipped.** `OrderRefunded` v1 is consumed; a **full** refund of the qualifying booking's
order moves the referral `qualified → reversed` by one compare-and-swap and claws both sides back
through **new negative rows** in the existing append-only loyalty ledger, under two new distinct
reasons. `referral.referrals` gains `reversed_at` and `reversal_order_id`; a new
`referral.reward_reversals` table records what each side actually gave back; `ReferralReversed` v1
is emitted through the outbox and notified in-app to both parties. **No loyalty, financial, role or
grant object was touched** — the points ledger's `points` column was already signed and
`lifetimeEarned()` already summed positive rows only, so two of the hardest requirements needed no
code at all.

**Three findings from reading the code changed the design**, and each is worth recording:

- **`reward_grants.points` is the configured BASE, not what was credited.** `award()` applies the
  recipient's membership multiplier on top of it, so clawing back the grant's figure would
  under-reverse every referral belonging to a customer holding a bonus-points benefit, by an amount
  that grows with the benefit and that nothing would ever report. The **grant decides whether** a
  side reverses — only it can tell `disabled_zero` from `capped` — and the **ledger row decides how
  much**. Neither is current configuration, which is the property `V32-DEC-017` protects, and the
  two are cross-checked rather than trusted.
- **`duplicate_charge` cannot reach the reversal path at all.** `RefundCompletedCommerceHandler`
  returns before calling `recordRefund`, and that handler is `recordRefund`'s only production
  caller — so a duplicate charge never moves an order's status and never produces an
  `OrderRefunded`. The exclusion is **structural**, so the order-lookup port has no
  duplicate-charge field: a guard that can never fire reads, to the next author, as though the
  danger were being handled somewhere. It is proved end to end instead.
- **The relay makes refund-before-qualification ordinary.** Outbox sources drain independently with
  no cross-source ordering, and a failed handler is retried on an arbitrarily later sweep. A naive
  reversal handler loses that case: it finds a `pending` referral and the qualification that
  follows leaves an active reward on a fully refunded order — `V32-DEC-017`'s free-points loop,
  reintroduced by delivery order alone. Fixed with the **same authoritative read at the other end**,
  and the residual race closed with a `FOR SHARE` lock on the order row. **No new retry or
  reconciliation mechanism**, which the story made a condition.

**What did not change:** both reward values, which remain **0**; the monthly cap of 10 and its
Solar Hijri period; the qualification trigger; the notification policy; and
`referral.referrer_counters`, which this story deliberately does not touch — see below.

**One question shipped OPEN and was closed the same day — `V32-DEC-036`.** Whether a reversal
returns the referrer's monthly cap slot was settled by no closed decision, and `ADR-037` said so in
as many words. Story #28 took the **null action** — the counter untouched — and recorded the
question rather than settling it under cover of implementing it. See §5.8.

### 5.8 `V32-DEC-036` closure — a reversal does not return the cap slot: RATIFIED 2026-09-01

The owner ratified alternative **(a)** on 2026-09-01: **the slot stays spent.** The cap counts
*qualifications the platform successfully processed*, not *rewards that survived a refund*.

**The reason is the abuse boundary.** Returning the slot makes qualification/refund **cycling**
possible — a referrer colluding with invitees who book and refund could reuse one slot indefinitely
— and `V32-DEC-019` calls the monthly cap the *bounded-exposure control* for an erase-and-re-register
gap it accepts knowingly. A cap that a refund can refund would bound nothing. The cost is accepted
knowingly in the other direction too: a referrer whose invitee is refunded through no fault of their
own loses a slot they earned nothing from.

**The rule does not vary by period.** A refund landing in a **later** Jalali month neither reaches
back to decrement the earlier counter nor creates or adjusts a row in the current one. Option (c) —
returning the slot only within the same period — was refused for making a referrer's remaining
allowance depend on *when the refund happened* rather than on what they did.

**No production line changed**, and the audit that preceded the closure is why.
`referral.referrer_counters` appears nowhere in the reversal service, the reversal handlers, either
adapter, the ledger, or the reversal migration — so the shipped code already matched (a) exactly.
That is the outcome the flag-rather-than-assume discipline is for: the null action turned out to be
the ratified behaviour, and ratifying it cost nothing.

**What the closure did add is a proof.** Before it, the only thing standing behind "the counter is
untouched" was a **source-text** assertion in the fast suite — the reversal service does not contain
the string `referrer_counters`. That proves the code does not *mention* a table; it cannot prove a
*row survived*. The real-PostgreSQL suite now asserts the counter row is **byte-identical after a
reversal** — period, count, and PostgreSQL's own `xmin` — in both the same and a later Jalali month,
and that no row appears in the later period.

**`xmin` rather than `updated_at`, and a mutation probe is why.** `updated_at` was the obvious
instrument and is the wrong one: it is a TypeORM `@UpdateDateColumn` set by *application code*, and
its `DEFAULT now()` fires only on INSERT. The cap counter is written by raw SQL — it has to be,
because the cap is one conditional statement — so a raw `UPDATE` leaves `updated_at` untouched. An
assertion on it would have passed while the row underneath was being rewritten, and the probe that
wrote the row without changing its value proved exactly that. `xmin` is the transaction id of the
current row version, so **any** write produces a new one.

Four probes establish non-vacuity: an unguarded decrement (refused outright by
`ck_referrer_counters_count_positive` at a count of 1 — the database already forbids the crudest
form of the rejected reading), a guarded decrement that does succeed, a row delete, a same-value
touch, and a cross-period insert. Each kills at least three of the four cases.

Closed **before either reward value becomes non-zero**, on exactly the reasoning that closed
`V32-DEC-035` before then. Both values remain **0**.
