# V3.2+ Product Roadmap

**Status:** OWNER-DIRECTED PLANNING — scope recorded 2026-08-29. No V3.2 code, migration,
release, or tag is created by this document.

**Entry condition:** V3.1 reaches `IMPLEMENTATION COMPLETE / SANDBOX READY`. Production
enablement may continue in parallel, but no V3.2 feature may weaken or bypass V3.1's
External Enablement Gate.

**Purpose:** turn the former V3.2+ deferral bucket into an ordered product programme while
keeping unresolved product decisions, vendor dependencies, and evidence-gated scale work
visible rather than silently settling them in implementation.

---

## 1. Scope now recorded for V3.2+

| Capability | Current V3 state | V3.2+ disposition |
|---|---|---|
| AI assistants | Capability flag and curated Journey seam only; no AI domain | Core V3.2 |

| Referral | No domain; booking-completion and loyalty seams exist | Core V3.2 |

| Calendar sync/live recurrence | No integration or recurrence engine | Provider and product-decision gate |
| Kafka, ClickHouse, shared Redis | No evidence requiring them today | Evidence-gated only |

The roadmap also retains smaller deferred improvements in §9. Inclusion here means tracked
and ordered; it does not mean every optional item is approved for immediate implementation.

## 2. Product and architecture constraints

1. The repository and accepted ADRs remain the source of truth.
2. No V3.2 feature may create a second authorization, pricing, financial, search, media,
   notification, or analytics engine where V3 already has one.
3. Ownership is derived from the authenticated session, never a client-supplied user,
   professional, business, conversation, or party id.
4. AI and chat are separate domains. They may share UI primitives and notification/media
   ports, but human messages must not be stored as AI conversations or automatically sent
   to an LLM.
5. Free text is PII-adjacent by default. Review text, Journey notes, CRM notes, and human
   chat messages are excluded from AI context unless a later explicit, narrow, consented
   contract says otherwise.
6. Provider-specific code waits for an actual provider decision and test account. A local
   HTTP server or rule-based fallback proves an interface, not external delivery.
7. Every new data-owning table must register with the Phase E subject-data contract before
   the application may boot.
8. Every new event uses the existing transactional outbox and versioned event catalogue.
9. V3.2 inherits the evidence vocabulary from `V3.1_EXTERNAL_ENABLEMENT_STRATEGY.md`:
   local, provider-sandbox, and production verification remain distinct.

## 3. V3.2-A — AI Assistant Foundation

**Goal:** safe, useful customer and professional assistants that can run locally with an
honest deterministic fallback and can later use a real LLM provider without changing domain
or security boundaries.

**Scope:**

- `ai` schema and module, conversation/message model, and an explicit decision on single
  thread versus conversation history (`GAP-12`).
- Customer and professional modes with separate capabilities and tenant scopes.
- Session-derived authorization followed by curated-context assembly; no raw database or
  arbitrary-query access for a provider.
- Typed context ports to Journey and other approved domains. Free-text exclusions enforced
  by types and adversarial tests, not prompt wording.
- Provider registry, deterministic rule-based fallback, timeouts, safe failure states, and
  provider-health reporting that never claims a fallback is a live LLM.
- System constraints, input length and injection controls, output-schema validation, and
  independent re-verification of every model-recommended entity id against real data.
- Usage quotas, cost accounting, rate limits, analytics without raw prompt retention, and
  operator-visible health/usage surfaces.
- Persian-first customer and professional assistant UI designed through Claude Design before
  production frontend implementation.

**External gate:** hosting-region/provider reachability, provider selection, credentials,
and one end-to-end provider-sandbox/live verification.

**Definition of Done — sandbox milestone:** both modes work end to end through the real app
with deterministic fallback; cross-tenant and prompt-injection tests pass; every output is
validated; missing credentials fail honestly; no external-provider claim is made.

## 4. V3.2-B — Internal Chat Foundation

**Goal:** privacy-bound, abuse-resistant human messaging inside BeauClick without coupling
human conversation data to the AI provider.

**Product decisions required before schema implementation:**

- permitted participants: customer↔professional, customer↔business, staff groups,
  platform support, or a subset;
- when a booking or commercial relationship is required to start a conversation;
- retention/deletion policy and what account erasure does to the other participant's copy;
- attachment types, limits, and access lifetime;
- blocking, reporting, moderation, escalation, and support access;
- delivery expectations: polling, SSE, WebSocket, push, read receipts, typing indicators,
  and offline behaviour.

**Engineering scope after those decisions:**

- conversation, participant, message, delivery/read-state, block/report, and moderation
  contracts with database-enforced tenant boundaries.
- Versioned pagination, unread counts, notification integration, idempotent send, ordering,
  retry, and duplicate-delivery safety.
- Attachment reuse through the media boundary with private access class; no public object
  URLs and no duplicated upload engine.
- Subject-data export/erasure registration, audit rules for privileged moderation, retention
  sweep, abuse throttling, and adversarial cross-tenant tests.
- Modern RTL inbox, thread, composer, attachment, empty/offline/error, block/report, and
  moderator states in the design package and frontend.

**Non-goal:** human messages are not AI context by default. Any future AI summarization or
reply assistance is a separate consent, privacy, retention, and output-validation decision.

## 5. V3.2-C — Retention: Referral and Wishlist

### Referral

- Invite/link/code lifecycle and attribution rules.
- Qualification from a real `BookingCompleted` or another explicitly approved event.
- Loyalty integration using the existing idempotent ledger.
- Fraud, self-referral, duplicate-device/account, cancellation/refund, expiry, and replay
  rules decided and tested before rewards can move.
- `pointsReferralQualified` requires an owner-approved business value; zero must remain an
  honest disabled state rather than a silent no-op.

### Wishlist

- Explicit product decision on saveable targets: professionals, services, portfolio items,
  or an approved subset.
- Private per-customer collection, stable pagination, idempotent add/remove, deleted-target
  behaviour, and subject-data export/erasure registration.
- Search/profile integration and useful empty states without creating a second discovery
  or recommendation engine.

**Definition of Done:** a referral can qualify exactly once under an approved rule and a
wishlist survives normal target changes without leaking another customer's collection.

## 6. V3.2-D — Professional Growth: CRM and Delegation

**Scope:** a scalable CRM surface over existing customer, booking, notification, journey,
and analytics facts; professional notes and follow-up workflows; and the unresolved
delegation model for an independent professional.

**Constraints:**

- Do not port V2's unbatched in-memory search/filter/pagination.
- CRM notes are tenant-private PII, excluded from AI context and analytics facts by
  construction.
- Decide owner-only versus staff access by data class. Financial and AI-conversation data
  keep their stricter existing boundaries.
- Reuse notification and analytics engines; do not create a parallel campaign sender or
  metrics calculator inside CRM.

**Product decisions:** allowed staff roles, note retention, export/erasure treatment,
follow-up types, consent requirements, and whether a solo professional may delegate access.

## 7. V3.2-E — Commercial Expansion: B2B Quotes and Campaigns

Both capabilities require an explicit owner decision that they belong in BeauClick V3
before implementation begins.

### B2B quotes

- Quote parties, catalogue ownership, tier pricing, validity, negotiation, acceptance,
  conversion to order/payment, cancellation, tax/invoice requirements, and authorization.
- Reuse Commerce, Payment, Financial, and Business party boundaries.

### Campaigns and promotions

- Campaign eligibility, schedules, budgets, usage caps, per-customer limits, stacking,
  cancellation/refund effects, and auditability.
- Add rules to the existing pricing chain; never calculate a second total beside it.
- Database-enforced or transactional concurrency for usage caps; no read-then-write quota.

---

## 8. V3.2-F — Financial and Scheduling Automation

### Automated payout/disbursement

- Additive to the existing append-only, idempotent settlement model.
- Requires selected banking rails, payout policy, KYC/beneficiary rules, failure/retry and
  reversal handling, reconciliation, operator approval thresholds, and real evidence.
- No automatic movement of money before the owner approves policy and the External
  Enablement Gate has real banking credentials.

### Calendar sync and live recurrence

- Decide supported providers, one-way versus two-way sync, source of truth, recurrence,
  timezone/DST, conflicts, cancellations, privacy, and revocation behaviour.
- Reuse Booking availability; do not create a second calendar of bookable inventory.

---

## 9. V3.2-G — Evidence-Gated Scale and Deferred Improvements

These items are not sequential delivery commitments. Each needs evidence and a written
decision before implementation:

- Shared Redis throttling if production is multi-instance.
- Kafka only if outbox throughput or independent deployment evidence exceeds the modular
  monolith's current transport.
- ClickHouse only if analytics volume/query evidence exceeds PostgreSQL/OpenSearch needs.
- ML ranking only after sufficient labelled interaction data exists; hand-weighted ranking
  remains the explainable baseline.
- Availability-aware search after production usage proves the benefit and freshness model.
- Image derivatives/thumbnails after a sync-versus-async media pipeline decision.
- Portfolio reordering.
- Review editing and customer-initiated review reporting.
- Ranking-weight administration.
- Per-category privacy controls and consent audit trail.
- Screen-reader software pass and other explicitly deferred QA evidence.

Native mobile apps, Kubernetes, multi-region deployment, advanced realtime features, and
full accounting are not automatically included in V3.2. They require separate evidence and
owner approval.

## 10. Recommended execution order

```text
V3.1 IMPLEMENTATION COMPLETE / SANDBOX READY
  -> V3.2 discovery + owner decisions for AI conversation model and Chat participants
  -> V3.2-A AI Assistant Foundation
  -> V3.2-B Internal Chat Foundation
  -> V3.2-C Referral + Wishlist
  -> V3.2-D CRM + Delegation
  -> owner gates for B2B and Campaigns
  -> V3.2-E B2B Quotes + Campaigns, if approved
  -> V3.2-F Payout + Calendar, as external rails/providers become available
  -> V3.2-G items only on evidence
```

AI, Chat, Referral, and Wishlist are the V3.2 core. Later phases remain conditional where
the requirement itself or the external rail is not yet approved.

## 11. Required discovery before the first V3.2 implementation prompt

Before code is written, reconcile this roadmap against the final V3.1 repository and create:

1. AI conversation-cardinality decision.
2. AI provider/reachability and cost envelope.
3. Chat participant/eligibility matrix.
4. Chat retention, erasure, moderation, and attachment policy.
5. Referral qualification and reward policy.
6. Wishlist target decision.
7. CRM staff-access and retention policy.
8. Explicit yes/no decisions for B2B quotes and campaigns.
9. Payout and calendar external dependency ledger.

No implementation agent may silently answer those product questions because a convenient
schema or library suggests an answer.
