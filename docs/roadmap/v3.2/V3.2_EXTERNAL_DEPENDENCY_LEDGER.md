# V3.2 External Dependency Ledger

**Status:** OPEN LEDGER. Nothing in this document closes any dependency. No provider is
selected, no credential is held, no vendor is named as chosen, and no external gap is closed
by the V3.2 Phase 0 discovery commit.

**Purpose:** one place that separates *what engineering can build locally* from *what needs a
vendor, a credential, a host, or real evidence* — and states the exact condition that unblocks
each. It exists so a V3.2 implementation phase cannot mistake a working local stand-in for a
working integration, which `V3.2_PLUS_CAPABILITY_CATALOG.md` §9 lists as `RETIRED` behaviour.

---

## 1. The three levels of proof, inherited unchanged

V3.2 inherits the evidence vocabulary of `V3.1_EXTERNAL_ENABLEMENT_STRATEGY.md` and the
readiness model of `ADR-028`. The three levels are not interchangeable and a claim at one level
is never evidence at another.

| Level | What it proves | What it does not prove |
|---|---|---|
| **Local capability** | The interface, the failure taxonomy, the timeouts, the validation, and the tests are right. A deterministic stand-in serves. | That any external service exists, is reachable, or behaves as documented. |
| **Provider sandbox** | The real protocol, the real field semantics, the real error codes, and the real network failure modes, against the vendor's own sandbox. | That production credentials work, or that anything has happened with real money, a real phone, or a real customer. |
| **Production verified** | One real end-to-end transaction on the real host, recorded by a person holding the evidence. | Nothing further; this is the terminal level. |

The mechanical expression of this already exists in code:
`v3/apps/api/src/health/readiness.ts` reports a `ReadinessState`
(`not_configured` · `simulated` · `configured` · `reachable` · `unreachable`) and carries
`productionVerified` as a **separate axis** sourced from `EXTERNAL_VERIFICATION_LEDGER`.
**No probe may set `productionVerified` true.** V3.2 adds rows to that ledger; it does not add
a second status model.

## 3. New dependencies introduced by V3.2

### 3.1 `AI-PROVIDER` — LLM provider selection and reachability

| Field | Statement |
|---|---|
| **Type** | BUSINESS DECISION + CREDENTIAL + LIVE CHECK |
| **Blocked by** | Phase F blocker **1** (hosting / region). This is a hard ordering, not a preference: whether a given provider's API is reachable at all depends on where the application runs. |
| **What engineering can build with no external dependency** | Everything except the vendor adapter. The provider port and registry; the deterministic provider registered under its own key; context assembly; input guards; output-schema validation; independent re-verification of every recommended id; timeouts, retry, and circuit behaviour; quotas and cost accounting; the `ai_provider` readiness row; the full real-PostgreSQL and adversarial suite. This is the entire V3.2-A sandbox milestone. |
| **What must wait** | Any named vendor adapter, any SDK dependency, any model identifier in configuration defaults, and every claim that a real model has answered anything. |
| **Local capability proof** | Both assistant modes working end to end through the real application on the deterministic provider; cross-tenant and prompt-injection suites passing; every output validated; a missing credential producing an honest state. |
| **Provider sandbox proof** | One real completion from the selected provider's own endpoint, with its real error codes and its real timeout behaviour exercised — including a refusal, a truncation, and a malformed structured output. |
| **Production verified proof** | One real customer conversation served by the real provider on the real host, within the approved cost envelope. |
| **Exact unblock condition** | The owner records (i) the hosting region, (ii) the selected provider, and (iii) an approved cost ceiling; a credential is held as a deployment secret; and one sandbox completion is observed. |
| **Anti-pattern this row exists to prevent** | Writing a vendor adapter from documentation. Phase F §12 records why it refused to do this for the payment gateway: an unexercised adapter is a liability rather than an asset, because it looks finished. |

### 3.2 `CHAT-ATTACHMENT-STORAGE` — private object storage for chat attachments

| Field | Statement |
|---|---|
| **Type** | VENDOR + CREDENTIAL |
| **Blocked by** | Phase F blocker **13**, and blocker **1** upstream of it. |
| **What engineering can build now** | The whole attachment path against the existing local storage driver: a new media purpose at access class `protected` with its own byte cap and per-user quota; a `canView` implementation checking live conversation participation; expiring download URLs (already five minutes); the non-participant refusal tests. |
| **What must wait** | Any claim that attachments are durably stored, and any production enablement of the feature. Files written by the local driver disappear with the container. |
| **Exact unblock condition** | Blocker 13 closes — an Iran-reachable S3-compatible bucket holding real uploads with verified retention. |

### 3.3 `CHAT-PUSH` — push notification delivery for messages

| Field | Statement |
|---|---|
| **Type** | VENDOR + CREDENTIAL + PRODUCT |
| **Blocked by** | The absence of a mobile or PWA surface (V3.4-A) and a push provider decision (V3.3-B). |
| **What engineering can build now** | In-app notification delivery through the existing notification module and outbox, plus unread counts. This is sufficient for a polling-transport first release. |
| **What must wait** | Push tokens, token lifecycle, and any claim that a message reaches a closed application. |
| **Exact unblock condition** | A mobile or PWA surface exists **and** a push provider is selected and credentialed. Both are outside V3.2. |

### 3.4 `PAYOUT-RAIL` — automated disbursement

| Field | Statement |
|---|---|
| **Type** | BUSINESS DECISION + LEGAL + VENDOR + CREDENTIAL + LIVE CHECK |
| **Blocked by** | `V32-DEC-028` (payout policy), Phase F blockers **1**, **2**, **3**, **5**, **9**, and **15**. |
| **What engineering can build now** | Nothing beyond provider-neutral interfaces, and even those are premature: the settlement ledger is append-only and idempotent and already records batches, items, and reversals. Adding a payout port before the rail is chosen would encode assumptions about beneficiary identity, batching, and failure semantics that the eventual rail may contradict. |
| **What must wait** | Everything else. `V3.2_PRODUCT_ROADMAP.md` §8: no automatic movement of money before the owner approves policy and the External Enablement Gate has real banking credentials. |
| **Required owner policies** | Payout schedule; approval thresholds; beneficiary and KYC rules; failure, retry, and reversal handling; reconciliation ownership; who may authorize an exception. |
| **Exact unblock condition** | All of: a stated payout policy; a selected banking rail; real credentials; one full lifecycle against that rail's sandbox including a failed payout and a reversal; and one controlled real disbursement on the real host. |
| **Proof required before any production claim** | A real disbursement reconciled against a real ledger entry, recorded by a person. No probe, no sandbox run, and no green test suite may set this. |

### 3.5 `CALENDAR-PROVIDER` — external calendar sync

| Field | Statement |
|---|---|
| **Type** | BUSINESS DECISION + VENDOR + CREDENTIAL |
| **Blocked by** | `V32-DEC-029` (direction and source of truth), and blocker **1** for provider reachability. |
| **What engineering can build now** | Under the recommended one-way-export answer: a stable, authenticated, read-only feed of a professional's own confirmed bookings, derived from Booking. That is `BUILDABLE` and needs no vendor. |
| **What must wait** | Any import of external busy time, any two-way sync, any OAuth integration with a named calendar provider, any recurrence engine, and every consequence that follows — conflict resolution, timezone and DST handling, revocation, and privacy of external event titles. |
| **Exact unblock condition** | The owner records the direction and the source of truth; if anything other than one-way export is chosen, a provider is selected and an OAuth application is registered and credentialed. |
| **Boundary that does not move** | Booking remains the only source of bookable inventory. `V3.2_PRODUCT_ROADMAP.md` §8 forbids a second calendar of inventory under every alternative. |

### 3.6 `REFERRAL-SHARE-CHANNEL` — how an invite actually reaches somebody

| Field | Statement |
|---|---|
| **Type** | EXTERNAL, conditional |
| **Blocked by** | Phase F blockers **6** and **7** *only if* invites are sent by SMS from the platform. |
| **What engineering can build now** | The entire referral capability, if the invite mechanism is an in-product code and a copyable link that the referrer shares themselves. No external dependency at all. |
| **What must wait** | Platform-sent SMS or email invites, and any funnel attribution that depends on them. |
| **Exact unblock condition** | Only applicable if the owner requires platform-sent invites. Otherwise **not a dependency** — this row exists so that an implementation phase does not invent one. |

## 4. What V3.2 can deliver with zero external dependencies

Stated positively, because the ledger above reads as a wall of blockers and most of V3.2 is not
blocked by any of them.

| Capability | Externally blocked? | Note |
|---|---|---|
| V3.2-A AI Assistant, to the sandbox milestone | **No** | Deterministic provider only. Both modes, full context boundary, full adversarial suite, honest readiness reporting. Only the real-provider claim is gated. |
| V3.2-B Internal Chat, without attachments | **No** | Polling transport, in-app notification, unread counts, blocking, reporting, moderation. |
| V3.2-B chat attachments | **Yes**, blocker 13 | Buildable and testable locally; not production-claimable. |
| V3.2-C Referral | **No**, unless platform-sent invites are required | See §3.6. |
| V3.2-C Wishlist | **No** | The smallest fully unblocked capability in the programme. |
| V3.2-D CRM and delegation | **No** | Blocked only by owner decisions, not by any vendor. |
| V3.2-E B2B and campaigns | **Owner-gated**, then payment-gated for B2B order settlement | Campaigns alone are not payment-gated. |
| V3.2-F payout | **Yes**, comprehensively | See §3.4. |
| V3.2-F calendar | **Partly** | One-way export is unblocked; anything else is not. |

**The honest summary:** after the owner decisions in `V3.2_DECISION_REGISTER.md` §H are made,
**V3.2-A (sandbox milestone), V3.2-B (less attachments), V3.2-C, and V3.2-D can be delivered in
full without a single new vendor, credential, or host.** Only V3.2-E's approval and V3.2-F's
rails sit outside engineering's reach.

## 5. Rules for maintaining this ledger

1. A row moves from blocked to unblocked only when its **exact unblock condition** is met, and
   the person who met it records how.
2. `EXTERNAL_VERIFICATION_LEDGER` in `v3/apps/api/src/health/readiness.ts` is the machine-readable
   half of this document. A new V3.2 dependency that a deployment can be misled about — the AI
   provider is the clear case — gets a row there, and the two must agree.
3. A local stand-in is never evidence of an external capability. A green test suite is evidence
   about the code.
4. A dependency is never closed by an engineering commit alone. Every row above ends in a
   person's statement, a credential, or an observed real transaction.
