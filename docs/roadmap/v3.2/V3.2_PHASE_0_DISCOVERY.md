# V3.2 Phase 0 — Repository Audit and Discovery

**Status:** DISCOVERY ONLY. No V3.2 implementation, schema, migration, route, provider
selection, release tag, or external-gap closure is produced by this document or by the
commit that carries it.

**Baseline audited:** `226b14a441f1dfc1c4ee42b9831e51232d5ee14b`, verified equal to
`origin/master` before the audit began. The worktree carried no change other than the
untracked `start-beauclick.vbs`, which is preserved. `design/claude-design` was not merged
and not touched.

**What this document is.** An evidence-backed statement of what the repository already
decides, what it does not decide, and what cannot be decided by engineering at all. Every
finding below is classified. Recommendations are labelled as recommendations; they are not
approvals, and an owner decision is recorded in `V3.2_DECISION_REGISTER.md` rather than
settled here.

**Classification vocabulary** (used throughout, per the Phase 0 brief):

| Tag | Meaning |
|---|---|
| `FIXED` | `FIXED SAFETY/ARCHITECTURE CONSTRAINT` — already decided by code, an ADR, or an accepted security rule. Not reopenable by a V3.2 implementation phase. |
| `OWNER` | `OWNER PRODUCT DECISION REQUIRED` — only the owner may settle it. |
| `EXTERNAL` | `EXTERNAL DEPENDENCY` — needs a vendor, credential, host, or region decision. |
| `EVIDENCE` | `EVIDENCE-GATED` — needs measured production evidence before it may be built. |
| `DISCOVERY` | `ENGINEERING DISCOVERY` — a fact this audit established about the repository. |
| `BUILDABLE` | `IMPLEMENTABLE WITHOUT EXTERNAL DEPENDENCIES` — engineering can complete it locally once the owner decisions it depends on are made. |
| `NON-GOAL` | `EXPLICIT NON-GOAL` — deliberately out of scope. |

## 1. Method and coverage

The audit read every document named in the Phase 0 brief and then searched the repository
directly rather than trusting any roadmap's summary of it. Concretely:

- every migration under `v3/database/migrations/` (37 files, 16 schema directories,
  **70 tables**, of which 12 are per-schema `outbox_events`);
- every module under `v3/services/` (14) and `v3/libs/` (11), plus `v3/apps/api` and
  `v3/apps/web`;
- every registered event contract (`v3/libs/event-contracts/src/catalog/`, 10 domain files,
  **62 contracts**);
- every subject-data contract (16);
- the V2 WordPress tree under `wordpress/wp-content/plugins/` and the V2 SPA under `app/src/`,
  because four V3.2 capabilities have real V2 implementations that the V3 planning documents
  either do not classify or describe inaccurately.

Where a roadmap claim and the repository disagreed, the repository won and the disagreement
is recorded in §6.

### 2.3 Cross-cutting mechanisms that constrain every V3.2 phase

These are `FIXED`. A V3.2 phase does not get to choose whether to satisfy them; they are
enforced at boot, at emit time, at lint time, or by the database.

**Subject-data coverage fails the boot** (`v3/libs/subject-data/src/coverage.ts`, ADR-027).
The universe is `pg_tables`, not an entity list. Every table in every non-system schema must
be claimed by **exactly one** module contract as `subject_data`, `retained` (with a reason),
or `no_subject_data` (with a reason). A table nobody claimed stops the application from
starting; so does a claim for a table that no longer exists, a table claimed twice, and a
`no_subject_data` claim on a table carrying a subject-shaped column (`user_id`,
`customer_id`, `owner_id`, `actor_id`, `subject_id`, `phone`, `email`, or any `*_by` /
`*_user_id` suffix). Every AI, chat, referral, and wishlist table must therefore arrive with
its disposition and its export/erasure behaviour already decided — which is why several
entries in the decision register are blocking rather than advisory.

**One producer per event, one schema per event, versions are immutable**
(`v3/libs/event-contracts/src/`). `ServiceName` is a closed union of the 14 existing
services; a new domain that emits an event must be added to it. A payload change is a new
version, never an edit. Emitting an event no contract declares throws.

**One pricing path** (`v3/services/commerce/src/pricing/pricing.types.ts`). Every rule
implements `PricingRule`; `subtotalToman` is immutable across the evaluation so percentage
rules never compound; the itemised result is stored on the order. A campaign or B2B tier is
a rule added to this chain — never a second total computed beside it.

**Ownership is resolved, never supplied** (`v3/libs/ownership/`, `V3_SECURITY_MODEL.md` §3).
Every tenant-scoped read takes a session-resolved id. `MetricsService.forProvider` and
`MyFinanceService.*` are the reference shapes: there is no method that accepts a list of
parties, so a controller cannot widen the scope by passing the wrong argument.

**Audit logging is structurally enforced** (`v3/libs/audit/src/audit-enforcement.ts`). A
mutation-capable controller that does not record an audit action fails registration.

**Readiness distinguishes real from simulated** (`v3/apps/api/src/health/readiness.ts`).
`ReadinessState` is `not_configured | simulated | configured | reachable | unreachable`;
`productionVerified` is a separate axis sourced from `EXTERNAL_VERIFICATION_LEDGER` and
**no probe may set it true**. `DEPENDENCIES` is a closed list of 8. This is the vocabulary
V3.2-A's provider-health requirement asks for, and it already exists.

**Media has two access classes, not three** (`v3/libs/media/src/`). `MediaAccessClass` is
`'public' | 'protected'`. `MEDIA_POLICY` covers four purposes: `portfolio`, `avatar`,
`cover`, `verification_evidence` — each with a byte cap, a per-user quota, and pixel bounds.
`MediaService.resolveProtectedDownload(mediaId, token, canView)` takes an authorization
callback and re-checks it against live data on every request. `media.abuse_reports` plus
`POST /v1/media/:id/report`, `GET /v1/media/reports`, and `POST /v1/media/reports/:id/decide`
already exist under `bc_moderate_media`.

**Throttling is single-instance and in-memory.** `@nestjs/throttler` with exactly one
throttler, deliberately (`throttlerOptionsFromEnv`). `THROTTLE-STORE` stays open pending the
deployment instance count. Any V3.2 quota that must hold across instances inherits this gap.

## 4. V2 evidence the V3 planning documents do not carry

Four V3.2 capabilities have complete, tested V2 implementations in this repository. They are
not portable, and this section does not propose porting them. They are cited because they are
the only real evidence available about behaviour, abuse surface, and scale — and because two
of them contradict what a V3 document says about them (§6).

### 4.1 Internal chat — `wordpress/wp-content/plugins/beauclick-chat`

- **Model:** `bc_conversations(type, participant_a_id, participant_b_id, last_message_at)`
  with `UNIQUE(participant_a_id, participant_b_id, type)` in canonical (smaller id, larger id)
  order, so the same pair resolves to one row regardless of who starts. Exactly two
  participants. A `type` of `ai` was reserved for reuse by the AI plugin and deliberately
  never taken up (§4.2).
- **Messages:** `bc_messages(conversation_id, sender_id, body, created_at, read_at)`.
- **Transport:** polling. `ChatPanel.tsx` polls the conversation list every **15 s** and the
  open thread every **4 s**. The service's own docblock states the reason: PHP-FPM does not
  hold long-lived connections cheaply and a single-city launch does not need sub-second
  delivery. A `message_sent` action is fired on every insert as the seam a future realtime
  relay would subscribe to, with no listener attached.
- **Abuse control:** 20 messages per sender per minute, via a transient.
- **Authorization:** `bc_send_message` to start; participant-or-`bc_view_all_conversations`
  to read. Support holds `bc_view_all_conversations` and deliberately **not**
  `bc_send_message`.
- **Privacy:** export returns **only the subject's own authored messages**, explicitly
  matching the CRM-notes boundary and the privacy policy's own wording that a conversation
  stays between the customer and that professional. Conversations and messages are
  **retained, never deleted**, on account erasure, because the counterpart has a legitimate
  ongoing interest.
- **What V2 never had:** any eligibility rule. `start_or_get` rejects only self-conversation
  and non-positive ids — any logged-in holder of `bc_send_message` could open a thread with
  any user id. Also absent: attachments, blocking, reporting, a moderation queue, retention
  sweep, typing and presence, and per-participant read state (`read_at` is a per-message
  column, correct for two participants and wrong for three).

`DISCOVERY` — the missing eligibility rule is the single most important piece of V2 chat
evidence. It is a harassment and user-enumeration surface, and it is why the participant
matrix in `V32-DEC-010` is blocking rather than advisory.

### 4.2 AI assistant — `wordpress/wp-content/plugins/beauclick-ai`

- **Cardinality:** `bc_ai_conversations` carries `UNIQUE KEY user_id` — one ongoing customer
  conversation per user, with an accumulated `ai_context` blob. This is `GAP-12`.
- **Professional mode:** a *separate* table pair keyed `UNIQUE(provider_id)`, with `user_id`
  stored but not the identity key. The migration's docblock states both reasons: the
  customer table's `UNIQUE(user_id)` makes coexistence impossible for a professional who is
  also a customer, and conflating the two would leak a professional's own shopping history
  into a business-data prompt. It also deliberately carries **no cached context column** —
  a professional's numbers are rebuilt fresh every turn so "your revenue right now" can never
  read a stale snapshot.
- **Provider boundary:** a `chat(history, context)` port; the factory returns a real provider
  only when both the provider name and the API key are set, and otherwise returns the
  rule-based provider.
- **Input guard:** a 1000-character cap and six literal injection phrases (five English, one
  Persian), checked before the provider is invoked.
- **Safety guard:** 13 Persian medical-signal phrases, deliberately narrow so ordinary
  skincare vocabulary does not trigger it. Its own docblock records that the guard runs on
  the rule-based path and that the LLM path carries the same principle only as a system-prompt
  instruction, because an external model's output cannot be verified locally.
- **Output validation:** every model-claimed recommendation id is re-checked against a real
  row before anything is persisted or rendered.

### 4.3 Referral — `wordpress/wp-content/plugins/beauclick-referral`

- `bc_referral_codes` with `UNIQUE(user_id)` and `UNIQUE(code)`; `bc_referrals` with
  `UNIQUE(referee_user_id)` — a person can be referred exactly once, enforced by the database.
- Status lifecycle: pending, qualified, rewarded.
- **Qualification:** first genuinely completed booking **or** first completed shop/B2B order,
  whichever happens first. Registration alone never qualifies. Both triggers are domain
  events, never client input.
- **Reward:** give-one-get-one — flat points to **both** sides (50 and 50 by default),
  awarded through the loyalty ledger under **two distinct reasons**,
  `referral_referrer_reward` and `referral_referee_reward`, each idempotent on
  `(reference_type = 'referral', reference_id = the referral id, reason)`.
- Self-referral is prevented at attribution; attribution only ever fires for a genuinely new
  account.
- **What V2 never had:** expiry, and any reversal on cancellation or refund. A referral that
  qualified on a booking later refunded stayed rewarded.

### 4.4 CRM, campaigns, B2B

- **CRM** (`beauclick-booking/src/Crm/`): `bc_crm_notes(provider_id, customer_id,
  author_user_id, note VARCHAR(2000))`. Access control is on `provider_id` — the party —
  with `author_user_id` kept for display and audit only. Aggregation is a small fixed number
  of bulk `GROUP BY` queries; **search, filter, and pagination then happen in PHP over the
  fetched set**, justified explicitly by "low hundreds, not millions, of bookings per
  provider". `V3_MIGRATION_MATRIX.md` classifies this `REFACTOR` and names the scale ceiling.
  The CRM view also composes a **chat conversation summary**, which is a real coupling between
  V3.2-B and V3.2-D.
- **Campaigns** (`beauclick-campaigns`): `usage_limit_total` and `usage_limit_per_customer`
  with `starts_at`/`ends_at`; usage rows are applied or released. `record_usage()` is an
  insert-ignore under `UNIQUE(booking_id)`, and the code's own comment records `GAP-04`: the
  usage-count check runs well before the insert, so concurrent checkouts can overshoot both
  caps. That is exactly the "no read-then-write quota" rule the V3.2 roadmap states.
- **B2B** (`beauclick-b2b`): `bc_business_accounts(approval_status)`, `bc_b2b_price_tiers`,
  `bc_quotes(status, expires_at)`. A working tier-pricing engine and a quote lifecycle exist.
  `PRODUCT_GAP_REGISTER.md` records that B2B quote orders were a pricing path no discount
  could reach — one of the three defects that motivated V3's single pricing chain.

`NON-GOAL` — none of §4 is a port. `V3_MIGRATION_MATRIX.md` classifies the reusable parts as
patterns and business rules, and classifies the implementations themselves as throwaway.

## 5. Architecture findings

**`F-01` `DISCOVERY` / `OWNER` — the customer AI capability is granted and empty.**
`bc_use_ai_assistant` exists in `identity.capabilities`, is granted to the `customer` role in
both the migration and `CAPABILITIES_BY_ROLE`, and gates nothing. There is no corresponding
professional capability: `V3_API_CONTRACTS.md` names `bc_use_professional_ai`, which does not
exist anywhere in the codebase. V3.2-A must add it, and adding a capability is an
authorization decision, not a mechanical step.

**`F-02` `DISCOVERY` / `FIXED` — the platform already promises customers that their Journey
notes never reach an AI assistant.** `v3/apps/web/app/journey/page.tsx:168` carries that
sentence, in Persian, about a product surface that does not exist. Today the promise is
vacuously true and structurally guaranteed by `JourneyAiContext` having no string field. The
moment V3.2-A ships, it becomes a live customer-facing contract. Phase F recorded twice that
prose outlived its implementation; this is the mirror case — prose that precedes it — and it
must be treated as a binding constraint on the AI context contract, not as copy to revisit.

**`F-03` `DISCOVERY` — a deterministic AI fallback is in direct tension with the fail-closed
provider rule, and the tension resolves only by making the fallback an explicitly selected
provider.** `PaymentProviderRegistry` refuses to substitute a provider silently, because
silently substituting a payment gateway charges a customer through a channel nobody chose.
V2's AI factory did the opposite: it fell back to the rule-based provider whenever
configuration was incomplete. `V3_SECURITY_MODEL.md` §6 blesses the fallback for AI
specifically, on the condition that it is clearly labelled and honest. The reconciliation is:
the fallback is a **registered provider with its own key**, selected by configuration like any
other, and the readiness surface reports `simulated` for it. What must not exist is an
implicit fallback triggered by a missing credential at request time, because that is the shape
that lets a deployment believe it has an LLM when it does not.

**`F-04` `DISCOVERY` / `FIXED` — the loyalty ledger's idempotency key makes a single
`referral_qualified` reason insufficient for a two-sided reward.** The unique index is
`(reference_type, reference_id, reason)`. V2 awarded both sides of one referral under two
distinct reasons for exactly this arithmetic. If the owner approves any two-sided reward,
`LOYALTY_REASONS` needs two referral reasons, not one, and `pointsReferralQualified` needs to
become two values. Recorded as `V32-DEC-016`.

**`F-05` `DISCOVERY` — `search` is a read model, not a recommendation engine, and V3.2-A must
not become one.** `services/search` owns no relational system of record; its ranking is a
hand-weighted, explainable formula (`services/search/src/ranking/ranking.ts`), and
`V3.2_PLUS_CAPABILITY_CATALOG.md` keeps ML ranking at V3.4-D behind labelled-data evidence.
An AI assistant that recommends professionals must resolve candidates through the search
service or `getProviderSummary` and re-verify every returned id, not compute its own ordering.

**`F-06` `DISCOVERY` — chat has no home in the current module graph, and the two candidate
owners are both wrong.** `V3_DOMAIN_BOUNDARIES.md` does not mention chat at all. Folding it
into `notification` would merge the delivery authority with a content system of record;
folding it into `booking` would tie message retention to booking lifecycle and put PII-bearing
free text inside the module that owns availability concurrency. A `chat` module owning a
`chat` schema, consuming booking facts through a port and emitting a notification request, is
the only placement consistent with ADR-011. This requires adding `chat` to `ServiceName`.

**`F-07` `DISCOVERY` — per-message `read_at` does not survive a third participant.** V2's
unread count is "not sent by me and not yet read". It is correct for two participants and
silently wrong for a group: one participant reading a message clears it for everyone. If the
approved participant matrix ever includes a staff group, read state must be a per-participant
watermark (a `last_read_message_id` on the participant row), not a column on the message. This
is cheap to get right at schema time and expensive afterwards, so the participant decision
(`V32-DEC-010`) must precede the schema even if the first release ships only pairs.

**`F-08` `DISCOVERY` / `FIXED` — every new table costs a subject-data claim, and for chat the
claim is a genuine product decision.** V2 retained conversations and messages on erasure and
exported only the subject's own words. Under ADR-027 that maps to `retained` **with a stated
reason** — and the reason is a policy statement about the counterpart's interest, which
engineering may not write on the owner's behalf. See `V32-DEC-013`.

**`F-09` `DISCOVERY` — the media policy has no chat purpose and no private class.**
Attachments need a new media purpose with its own quota and byte cap, at access class
`protected`, and a `canView` implementation that checks conversation participation live. The
roadmap's phrase "private access class" does not correspond to anything in the code; the
existing class is `protected`, and it already re-authorizes on every request.

**`F-10` `DISCOVERY` — quotas for AI would be the platform's first cross-instance counter.**
Throttling today is in-memory and single-instance by deliberate choice, with `THROTTLE-STORE`
open pending the instance count. An AI usage quota or cost cap that must hold globally
inherits that gap. A per-user daily quota stored in PostgreSQL alongside the conversation
avoids it entirely and is the recommendation in `V32-DEC-008`.

**`F-11` `DISCOVERY` / `EXTERNAL` — AI reachability is already gated on the standing hosting
decision.** `V3.1_PHASE_F_IMPLEMENTATION.md` §5 lists AI reachability among what the
domestic-versus-international hosting decision gates. This is not a new V3.2 dependency; it is
blocker #1 carried forward, and it is the reason V3.2-A cannot reach a provider-sandbox
milestone on engineering effort alone.

## 6. Stale, incomplete, or incorrect claims found

**`S-01` — `v3/services/loyalty/src/loyalty.config.ts` misstates the V2 referral precedent.
Material.** The comment reads: "No V2 precedent — referral rewards existed but split a
configured pool rather than awarding flat points." V2 awarded **flat points to both sides**
(50 and 50 by default), through the loyalty ledger, under two distinct reasons. There was no
pool and no split. The consequence is not cosmetic: the comment justifies a single
`referralQualified` reason, and a single reason cannot idempotently award two people for one
referral id under `UNIQUE(reference_type, reference_id, reason)`. See `F-04`. **The correction
is recorded here; the code is not edited by this documentation-only phase.**

**`S-02` — `V3.2_PRODUCT_ROADMAP.md` §1 says wishlist and CRM have "no domain" without noting
that the Phase 0 blueprint already assigned them owners.** `V3_DOMAIN_BOUNDARIES.md` places
`wishlist_items` in the `provider` schema and `crm_notes` in the `booking` schema. Both
statements are true — nothing is implemented — but a V3.2 implementation phase reading only
the roadmap would treat ownership as an open question when a blueprint answer exists. The
blueprint answer is a *proposal*, not an approval, and §8 re-opens both on the merits. A
cross-reference has been added to the roadmap.

**`S-03` — `V3_DOMAIN_BOUNDARIES.md` is a Phase 0 blueprint and has drifted from the built
system in at least five places.** Waitlist is its own `waitlist` schema and module, not
`booking.waitlist_entries`. Business is its own `business` schema and module, not
`provider.business_staff`. `media` is a first-class library with its own schema and is not
mentioned in the document at all. `privacy` owns `data_requests` **and** `export_payloads`,
not a single table. `booking.booking_reschedules` does not exist. None of this invalidates the
document's ownership *rules*, which V3 follows closely; it does mean the table lists must not
be read as the current schema.

**`S-04` — the V3 migration matrix never classified internal chat.** `V3_MIGRATION_MATRIX.md`
has sections for Booking, Referral, CRM, AI, Search, Frontend and more; chat appears only in
one Frontend row about feature components. `V3_MIGRATION_PLAN.md` lists chat under "rebuild
from business rules", and `V3.2_PRODUCT_ROADMAP.md` describes chat as mentioned in the older
migration plan but absent from V3 implementation. All three are accurate as far as they go,
and together they understate the position: a complete V2 chat plugin with a schema, a REST
controller, two test suites, and a polling SPA panel exists in this repository and was never
given a classification row. §4.1 supplies the evidence that was missing.

**`S-05` — `GAP-09`'s frontend half is still open and the audit confirms it.**
`v3/apps/web/app/layout.tsx` sets only `title` and `description`. There is no favicon, no
apple-touch-icon, and no OpenGraph or Twitter metadata anywhere in `apps/web`. Carried forward
unchanged (§10).

**`S-06` — the two Phase F blocker numberings differ.** `V3.1_PHASE_F_IMPLEMENTATION.md` §11
numbers legal content as **16** and font delivery as **17**; `V3.1_PRODUCT_ROADMAP.md` and
`V3.1_UIUX_BACKLOG.md` refer to the same two items as **#14** and **#15**. Both sets are live
in the documentation. `V3.2_EXTERNAL_DEPENDENCY_LEDGER.md` cites the Phase F numbering and
records the alias, so a future reader is not chasing two ledgers.

**No stale claim was found in `V3_SECURITY_MODEL.md`, ADR-027, `V3_EVENT_CATALOG.md`, or
`V3.1_GAP_RECONCILIATION.md`.** Every AI and chat statement in the security model matches what

## 7. V3.2-A — AI Assistant Foundation: decision dossier

Full decision cards are in `V3.2_DECISION_REGISTER.md` (`V32-DEC-001` through `V32-DEC-009`).
This section states the evidence and the boundary.

### 7.1 Product model

| Question | Status | Evidence and position |
|---|---|---|
| Customer assistant, professional assistant, or both | `OWNER` `V32-DEC-001` | Both are specified (`V3_DOMAIN_BOUNDARIES.md` §ai) and both existed in V2. Only the customer capability exists in V3. Recommendation: **customer mode first, professional mode second**, because customer mode reads only Journey plus the public catalogue, while professional mode reads settlement and analytics facts and therefore carries the strictest tenant-isolation surface in the platform. |
| Conversation cardinality | `OWNER` `V32-DEC-002` | `GAP-12`. V2 used one thread per user, keyed `UNIQUE(user_id)`, and the professional table repeated the pattern on `provider_id`. `V3_MIGRATION_MATRIX.md` says revisit, do not re-adopt. **Recommendation: bounded sessions** — see §7.2. |
| Naming, history, archive, delete | `OWNER` `V32-DEC-003` | Follows cardinality. A single persistent thread makes naming meaningless; multiple conversations make it necessary. |
| Supported first-release outcomes | `OWNER` `V32-DEC-004` | Recommendation: answer a discovery question, and surface up to N re-verified professionals or services with a reason. Nothing else. |
| Prohibited outcomes | `FIXED` | The assistant may **recommend only**. It may not create, modify, or cancel a booking; move or refund money; change identity, privacy, consent, or moderation state; write a review; or mutate any business record. `V3.2_PRODUCT_ROADMAP.md` §11 V3.4-C and `V3_SECURITY_MODEL.md` §5 both state this. Any future action-taking assistant is a V3.4-C decision with its own consent and confirmation design. |
| Confirmation that mutations need an independently authorized user action | `FIXED` | Confirmed. Every mutation route in V3 resolves ownership from the session and is capability-gated and audit-enforced; an AI-suggested action reaching one of them is indistinguishable from the user performing it, which is the requirement. |

**Recommended conversation-cardinality model — `OWNER PRODUCT DECISION REQUIRED`.**
**Bounded sessions**: many conversations per user, each with a server-set inactivity horizon
after which it is closed and read-only, and a hard cap on retained conversations per user.

The reasoning, stated so the owner can reject it on the merits:

- *One persistent thread* (V2) is the cheapest and is what `GAP-12` warns against re-adopting.
  Its real defect is not usability: an unbounded accumulating context blob is an unbounded
  prompt, an unbounded cost, an unbounded retention obligation, and an unbounded
  prompt-injection surface, because text a user typed six months ago is still being replayed
  to the provider today.
- *Unbounded conversation history* is the most familiar product shape and the most expensive
  privacy commitment. Every conversation is free text the subject authored, which ADR-027
  requires to be destroyed on erasure and exported on request, and the volume is unbounded.
- *Bounded sessions* keep the useful part of history (a user can find last week's
  conversation) while making retention, cost, and prompt size finite by construction rather
  than by a sweep that has to be remembered. It also matches the professional mode's
  already-correct rule that business numbers are rebuilt fresh each turn and never carried
  in a cached blob.

### 7.2 Context and privacy

**Allow-listed context sources — recommended, `OWNER` for the final list (`V32-DEC-005`).**

| Source | Method | What may cross | What must not |
|---|---|---|---|
| `journey` | `inferAiDefaults(userId)` | `specialtyIds`, `cityId`, `budgetToman` | `notes`, goal titles, timeline entries — structurally impossible today, and `F-02` makes the exclusion a customer-facing promise |
| `provider` | a `getProviderSummary`-shaped port | Already-public catalogue facts for candidate professionals and services | Verification evidence, internal notes, contact details |
| `search` | the existing search service | Candidate ids and their public summaries | Nothing else; the assistant does not rank |
| `analytics` (professional mode only) | `MetricsService.forProvider` | Pre-aggregated metrics with their `kind` and `note` | Any other party's figures; there is no method that returns them |
| `financial` (professional mode only) | `MyFinanceService.mySummary(sessionUserId)` | The caller's own settlement summary | Any caller-supplied party; the method does not accept one |

**Fields that must remain excluded — `FIXED`.** Journey `notes` and goal titles; review comment
text and professional reply text; moderator reasons; CRM notes; every human chat message;
verification evidence; phone numbers and any other direct identifier. `V3_SECURITY_MODEL.md`
§5 requires these to be "deliberately excluded from the context entirely, not merely
access-controlled within it", and `V3.2_PLUS_CAPABILITY_CATALOG.md` §9 lists automatic use of
them as `RETIRED`.

**The enforcement mechanism must be types, not prompt wording — `FIXED`.**
`JourneyAiContext` is the pattern: no string field exists, so adding one is a visible,
reviewable act. Every new context port must be shaped the same way, and the adversarial test
must assert the *key set*, as `journey-privacy.pg-spec.ts` already does.

**Consent — `OWNER` `V32-DEC-006`.** Whether using the assistant requires an explicit,
recorded consent, or whether the capability grant plus in-product disclosure suffices, is a
product and legal question. `V3.2_PLUS_CAPABILITY_CATALOG.md` puts a versioned consent audit
trail at V3.3-E, so a consent requirement decided now would either need a narrow bespoke
record or would pull that item forward.

**Retention, deletion, and subject data — `OWNER` `V32-DEC-007`, then `BUILDABLE`.** Every AI
table must register a Phase E disposition before the application can boot. AI messages are
free text the subject authored, so ADR-027's rule points at `subject_data` and destruction on
erasure — unlike chat, there is no counterpart with an interest. Export must include the
subject's own messages; whether it includes the assistant's replies is a decision (they are
not the subject's words, but they are about the subject).

**Analytics without raw prompts — `BUILDABLE`.** The analytics fact table already refuses
free text by construction (allow-listed dimensions), and V2's recommendation-event model —
shown, then clicked — is the right shape: it measures usefulness without retaining what anyone
typed.

**Support and admin access — `OWNER` `V32-DEC-009`.** V2 chat gave support a
read-all capability. For AI conversations the equivalent is a much stronger read: an AI thread
can contain a customer's stated beauty concerns. `V3.2_PLUS_CAPABILITY_CATALOG.md` places
least-privilege support access at V3.3-E and prohibits impersonation. Recommendation: **no
privileged read of AI conversation content in the first release.** Operators get counts,
health, and cost — never content.

### 7.3 Safety and the provider boundary

All `BUILDABLE` except where marked.

- **Deterministic local fallback** — a registered provider with its own key, never an implicit
  substitution (`F-03`). It narrates only real, already-curated data.
- **Provider-neutral port** — one interface, one registry, modelled on
  `PaymentProviderRegistry`, including its refusal to pick a default when more than one
  provider is registered.
- **Provider selection and regional reachability** — `EXTERNAL`, gated on the hosting decision
  (`F-11`). See the dependency ledger.
- **Prompt-injection controls** — input checked *before* the provider is invoked, per
  `V3_SECURITY_MODEL.md` §5. V2's six-phrase list is a starting point that needs re-auditing,
  not mechanical porting; the phrase list is a mitigation, and the real controls are the
  curated context (the model has nothing to leak) and output validation.
- **Input and output size limits** — a hard character cap on input; a hard cap on output
  tokens and on the number of recommendations accepted from one response.
- **Structured output validation** — the response must parse against a schema before anything
  is persisted or rendered. `zod` is already the platform's schema tool
  (`libs/event-contracts`).
- **Independent re-verification of every recommended entity id** — `FIXED`.
  `V3_SECURITY_MODEL.md` §5 states the calling code, not the adapter, is the trust boundary.
  Re-verify existence, visibility, and every claim the model made about the entity.
- **Timeout, retry, and failure behaviour** — an explicit per-request deadline; at most one
  retry on a transport error and none on a model error; a circuit that opens after repeated
  failures and reports `unreachable` rather than silently falling back to the deterministic
  provider mid-conversation, because a user cannot tell those two answers apart.
- **Quotas, rate limits, cost accounting, abuse** — `OWNER` for the numbers (`V32-DEC-008`),
  `BUILDABLE` for the mechanism. Recommendation: a per-user daily counter in PostgreSQL,
  incremented in the same transaction as the message insert, so the cap is not a read-then-write
  race and does not depend on the unresolved `THROTTLE-STORE` topology (`F-10`, `GAP-04`).
- **Health and readiness vocabulary** — add one `ai_provider` dependency to `DEPENDENCIES` with
  its own `EXTERNAL_VERIFICATION_LEDGER` row. `simulated` means the deterministic fallback is
  serving; `configured` means credentials exist but nothing was probed; `productionVerified`
  stays false until a person records real evidence. `required: false` — an unavailable
  assistant must not take an instance out of rotation.
- **Secrets and redaction** — the API key is a deployment secret, never in Git, and
  `env.validation.spec.ts`'s rule that no message may echo a secret value extends to it. Prompts
  and completions must not reach logs; `libs/observability`'s redaction discipline applies.

### 7.4 Architecture

- **Module and schema:** a new `ai` module owning an `ai` schema. Add `ai` to `ServiceName`.
- **Minimal table model alternatives** — the shape follows `V32-DEC-002`:
  - *one thread per user*: `ai_conversations(UNIQUE user_id)`, `ai_messages`,
    `ai_recommendation_events` — three tables, V2's shape, the model `GAP-12` warns against;
  - *bounded sessions* (recommended): the same three tables with the unique key removed, a
    `status` and `last_activity_at` on the conversation, and a per-user retained-conversation
    cap enforced on create;
  - *full history*: the same three tables with no bound, plus a retention sweep that must then
    be built, tested, and remembered.
  Professional mode is a **separate conversation table keyed on the party**, not a `scope`
  column on the customer table — V2's own migration records why, and the reason (a
  professional is also a customer) is equally true in V3.
- **Event contracts:** at most `AIConversationCreated` v1 and `AIMessageSent` v1, carrying ids
  and counts and **no message body**, matching the notification domain's existing discipline
  that message bodies stay out of every emitted event.
- **APIs:** `GET/POST /v1/ai/messages` under `bc_use_ai_assistant`;
  `GET/POST /v1/ai/professional/messages` under a new `bc_use_professional_ai`;
  `POST /v1/ai/recommendations/{id}/click`. No route accepts a party id.
- **Browser-safe contracts:** a shared package like `@beauclick/payment-contract` so the page
  and the server share one vocabulary for provider states and refusal reasons, with the server
  refusing regardless of what the page believed.
- **No raw database or arbitrary-query access for a provider** — `FIXED`, `RETIRED` in the
  capability catalog.
- **No second search, recommendation, analytics, notification, or authorization engine** —
  `FIXED` (`F-05`).
- **Required ADRs:** one for the AI domain boundary, provider port, and fallback semantics
  (the `F-03` reconciliation); one amending the threat model for prompt injection, output
  validation, and cost abuse. Both are prerequisites for the implementation phase, not
  deliverables of it.
- **Test strategy:** real-PostgreSQL suites in the established `*.pg-spec.ts` shape. The
  mandatory adversarial set: a forged party id in every professional-mode surface proven to
  have zero effect; a natural-language request for another tenant's data proven to return
  nothing of theirs; a hallucinated entity id proven to be dropped; an injection attempt
  proven to be refused before the provider is called; a context-key-set assertion for every
  context port; and a proof that a missing credential yields an honest state rather than a
  silent fallback claiming to be an LLM.

### 8.1 Participants and eligibility

Each pairing is evaluated separately, as the brief requires. **The matrix below is a
recommendation and is not approved.**

| Pairing | Recommendation | Reasoning |
|---|---|---|
| customer to professional | **In**, gated on a real booking relationship | The only pairing with an unambiguous product need and a natural eligibility signal. V2 shipped it with no gate at all (§4.1); that is the defect to avoid. |
| customer to business | **In**, same gate | `business` is a first-class module with staff. The counterpart is the business party, not a named individual. |
| customer to a specific staff member | **Out of first release** | Requires the staff role matrix that is itself unresolved at V3.3-C, and exposes an individual employee's identity to customers — a decision with real consequences that nothing in the repository has made. |
| business or staff group conversations | **Out of first release** | Needs per-participant read state (`F-07`), group membership lifecycle, and a leave/remove model. Nothing forces it now. |
| platform support | **Out of first release, with the seam kept** | V2 gave support a read-all capability but deliberately no send capability. Recommendation: keep the read-for-moderation seam, do not build a support inbox. |
| conversation requiring an existing booking | **Yes for the first release** | It is the strongest available abuse control and it costs nothing: booking already knows the relationship. |
| conversation allowed before booking | `OWNER` `V32-DEC-011` | This is a genuine commercial trade-off. Pre-booking questions plainly drive bookings; allowing them also opens messaging to any customer against any professional, which is precisely V2's harassment surface. |
| post-booking access duration | `OWNER` `V32-DEC-012` | Recommendation: the conversation stays readable indefinitely and becomes send-disabled a fixed period after the last booking ends. Read and write are separate questions and should be decided separately. |

### 8.2 Privacy, retention, and moderation

| Question | Status | Position |
|---|---|---|
| Message ownership and participant access | `FIXED` | A message belongs to its conversation; access is participation, resolved from the session through `libs/ownership`, never a supplied conversation or party id. |

V2 retained both sides and exported only the subject's own words, reasoning that the counterpart has a legitimate ongoing interest — the same reasoning it applied to CRM notes. ADR-027 requires the disposition and a stated reason at boot. **Engineering must not choose this.** |
| Retention period | `OWNER` `V32-DEC-013` | V2 had none. A period implies a sweep; `phase3-sweep.scheduler.ts` already exists to host one. |

| Blocking | `OWNER` `V32-DEC-014` | Recommendation: **in**, as the minimum viable counterweight to any pre-booking messaging. If pre-booking messaging is refused, blocking may be deferred. |
| Reporting | `OWNER` `V32-DEC-014` | Recommendation: **in**, mirroring `media.abuse_reports` rather than inventing a second report model. |
| Moderation queue | `OWNER` `V32-DEC-014` | Recommendation: reuse the existing moderator capability shape; a new `bc_moderate_chat` capability, not a widening of `bc_moderate_media`. |
| Privileged support access | `OWNER` `V32-DEC-015` | Recommendation: reported threads only, never arbitrary browsing, always audit-logged. Impersonation stays `RETIRED`. |
| Immutable audit | `FIXED` | `libs/audit` enforcement applies to every moderation mutation automatically. |
| Abuse throttling | `BUILDABLE` | V2's 20 per minute is a defensible starting figure; the V3 equivalent is a per-sender counter in the same transaction as the insert, for the `F-10` reason. |
| Attachment access and expiry | `OWNER` for policy, `BUILDABLE` for mechanism | A new media purpose at `protected` with its own quota and byte cap; `canView` checks live participation; download URLs already expire in five minutes (`F-09`). |

**`FIXED` — human chat is not AI context.** `V3.2_PRODUCT_ROADMAP.md` §4 states it as a
non-goal, and `V3.2_PLUS_CAPABILITY_CATALOG.md` §9 lists automatic use of human chat as AI
context as `RETIRED`. Any future summarization is a V3.4-C decision with its own consent,
retention, and validation design. The structural enforcement is that no chat context port
exists and none may be added without amending this rule.

### 8.3 Delivery model

| Option | Assessment |
|---|---|
| Polling | **Recommended for the first release.** It is what V2 shipped and what its own docblock justified; it needs no new infrastructure, no sticky sessions, and no connection budget; and it is the only option whose behaviour under the unresolved deployment topology is already known. |
| SSE | `EVIDENCE`. One long-lived connection per open thread per instance. No evidence of need exists, and the instance count is itself unresolved (`THROTTLE-STORE`). |
| WebSocket | `EVIDENCE`. `V3.2_PLUS_CAPABILITY_CATALOG.md` places realtime transport at V3.4-C behind measured need. Nothing in the repository measures it. |
| Push notifications | `EXTERNAL`. Requires a mobile or PWA surface and a provider; V3.3-B and V3.4-A. |
| Offline behaviour | Recommendation: a failed send stays visible as unsent and is retried by the user, never silently dropped and never auto-resent on reconnect without the idempotency key below. |
| Unread counts | `BUILDABLE`. Reuse the `UnreadProvider` pattern, including pushing the server's post-action count rather than decrementing locally. |
| Delivery and read receipts | Recommendation: **read state yes, delivery receipts no.** Read state is needed for unread counts anyway; a delivery receipt under polling means "the recipient's browser polled", which is not what a reader would understand it to mean. |
| Typing and presence | `EVIDENCE`, V3.4-C. Both require a transport that does not exist and leak activity information nobody has decided to publish. |
| Ordering | `BUILDABLE`. Order by a monotonic server-assigned sequence within the conversation, never by client timestamp. |
| Pagination | `BUILDABLE`. Keyset pagination on that sequence — V2 used offset and had to fix an unbounded list twice. |
| Idempotent send | `BUILDABLE`. A client-supplied idempotency key unique per conversation, so a retried POST returns the original message rather than creating a second one. `booking.idempotency_keys` is the existing precedent. |
| Duplicate delivery | `BUILDABLE`. The outbox is at-least-once; the notification idempotency key already covers the notification side. |
| Reconnect and retry | `BUILDABLE` under polling: a poll that fails is simply retried on the next tick, which is why polling is the recommendation while the topology is unknown. |

### 8.4 Architecture

- **Domain:** a new `chat` module owning a `chat` schema (`F-06`). Add `chat` to `ServiceName`.
- **Minimal model:** `conversations`, `conversation_participants`, `messages`,
  `message_attachments`, `blocks`, `reports`. Read state lives on the participant row as a
  watermark, not on the message (`F-07`), even if the first release ships only pairs.
- **Constraints PostgreSQL can enforce:** a unique participant pair per conversation kind;
  a unique `(conversation_id, sequence)`; a unique `(conversation_id, sender_id,
  idempotency_key)`; a unique `(blocker_id, blocked_id)`; a foreign key from every attachment
  to a media object; and a check that a participant row's user appears exactly once per
  conversation.
- **Attachments:** private media reuse only. No public object URL, no second upload engine
  (`F-09`).
- **Notification integration:** emit a notification request; never call a channel directly.
  A new `chat` notification category is required, and it must be opt-outable — it is not
  operationally mandatory the way a booking confirmation is.
- **Events:** `ConversationStarted` v1 and `MessageSent` v1, carrying ids and counts and
  **never a message body**.
- **Moderation boundary:** a moderator may read a reported thread and act on it; a moderator
  may not send, may not browse unreported conversations, and every action is audit-logged.
- **API surface:** `GET/POST /v1/chat/conversations`,
  `GET/POST /v1/chat/conversations/{id}/messages`,
  `POST /v1/chat/conversations/{id}/read`, `POST /v1/chat/blocks`, `POST /v1/chat/reports`,
  and capability-gated moderation routes.
- **Adversarial and concurrency tests:** a non-participant proven to read nothing; a forged
  conversation id proven indistinguishable from a missing one; two concurrent
  start-conversation requests proven to produce one row; a retried send proven to produce one
  message; a blocked sender proven to be refused; an attachment proven unreadable by a
  non-participant even with a valid-looking token; and a cross-tenant sweep in the shape the
  security model §4 requires.
- **Explicit non-goals:** group chat, typing, presence, streaming, message editing, message
  deletion by a participant, voice or video, AI summarization, and any support-initiated
  outbound conversation.

## 12. Recommended delivery order

This refines `V3.2_PRODUCT_ROADMAP.md` §12 with what the audit found. It does not change the
programme boundaries.

1. **Owner decision round 1** — `V32-DEC-001` through `V32-DEC-009` (AI) and `V32-DEC-010`
   through `V32-DEC-015` (chat). Nothing engineering does in the meantime is wasted, because
   the ports and the fallback are shared by every alternative.
2. **V3.2-A AI Assistant Foundation**, to the sandbox milestone, with the deterministic
   provider only. `BUILDABLE` in full without any external dependency; the external gate binds
   only the real-provider claim.
3. **V3.2-B Internal Chat Foundation**. Independent of V3.2-A and could equally run first;
   sequenced second only because AI has a live capability and two live seams already, and chat
   has none.
4. **V3.2-C Referral and Wishlist**, after `V32-DEC-016` through `V32-DEC-021`. Wishlist is the
   smallest genuinely complete capability in the programme and is a reasonable candidate to
   pull forward if an early, low-risk delivery is wanted.
5. **V3.2-D CRM and delegation**, after the staff-role matrix. This is the phase most coupled
   to unresolved V3.3-C questions.
6. **Owner gates for B2B and campaigns** (`V32-DEC-026`, `V32-DEC-027`), then V3.2-E only if
   approved.
7. **V3.2-F payout and calendar**, only as external rails become available.
8. **V3.2-G** on evidence only.

**Which phase can start with no external dependency once its owner decisions are made:**
V3.2-A (to the sandbox milestone), V3.2-B in full, V3.2-C in full, and V3.2-D in full. V3.2-E
needs an owner yes. V3.2-F cannot start beyond provider-neutral interfaces.
