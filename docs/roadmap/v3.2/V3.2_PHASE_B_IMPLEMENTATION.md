# V3.2-B — Internal Chat Foundation: Implementation Report

**Milestone:** the externally-independent backend only. **No attachment path, external provider, push channel, realtime transport, AI integration, production frontend, or release tag was built, and none is authorized by this phase.**

**Baseline:** `649dad5f62461d21805a87a98089ed273d38b191` on `master`, verified equal to `origin/master` before any work, worktree clean apart from the untracked `start-beauclick.vbs` (unmodified, never staged).

**Decisions:** `V32-DEC-010` … `V32-DEC-015`, closed by the product owner on 2026-08-30, approving the engineering decision packet **with four corrections**. Where a correction and the packet disagree, the correction governs.

**Architecture:** ADR-031 (chat domain, immutable counterparty, proven eligibility, bounded send window) and ADR-032 (chat privacy, abuse, moderation boundary). Both committed **before** any schema or implementation code.

## 1. The four owner corrections, and why each matters

Engineering recommended one thing; the owner decided another in four places. Recording them precisely, because in three of the four the owner's answer is stricter than engineering's and the difference is the interesting part.

| # | Engineering proposed | Owner decided | Why the correction is right |
|---|---|---|---|
| 1 | Counterparty from the historical order snapshot, **falling back** to current `business_staff` affiliation when absent | **No fallback.** Missing snapshot fails closed | A fallback fires exactly when the data is least trustworthy, and reintroduces the mutability the snapshot exists to remove. `CheckoutService` creates booking and order in one transaction, so "no order" describes corrupt data, not a legitimate booking |
| 2 | Business inbox = "active staff member" | **Owner and active managers only** | `business_staff.role` is `manager\|staff` and nothing finer. An any-active-staff rule hands a private customer conversation to everyone a salon ever added |
| 3 | Any `cancelled` booking qualifies | **`cancelled` only with proven prior `confirmed`** from `booking_history` | `pending` is the one status a stranger can create unilaterally. `pending`→`cancelled` would have been an eligibility grant anybody could mint — V2's defect through the cancellation door |
| 4 | Retain the erased subject's prose as a **deliberate ADR-027 exception**, pending legal sign-off | **Destroy it.** ADR-027-consistent, neutral placeholder only | Takes no exception to the platform's own erasure rule, makes no anonymisation claim, and removes legal disclosure copy as a blocker on the backend milestone |

## 2. Decisions closed, with exact values

| Entry | Decision | Binding parameters |
|---|---|---|
| `V32-DEC-010` | Customer↔professional and customer↔business; customer never chooses | Counterparty from `commerce.orders` historical snapshot · no fallback · fail closed · business inbox = owner + active managers · watermark read state |
| `V32-DEC-011` | Proven booking relationship required | `confirmed`, `completed`, `no_show`; `cancelled` **only with proven prior confirmation**; never `pending`/`expired`; refund irrelevant; either party initiates; one conversation per counterparty |
| `V32-DEC-012` | Read open, send bounded | **90 days** from `MAX(booking.slot_end)`, absolute UTC, recomputed per send, never cached |
| `V32-DEC-013` | ADR-027-consistent erasure | Erased prose **destroyed**; neutral placeholder; **24 months** from `last_message_at`; hard delete + cascade; export = own still-existing messages |
| `V32-DEC-014` | Blocking + reporting + queue together | 7 reasons · **5** reports/24 h · 1 open per reporter+conversation · anchored to a message · note ≤ **500** code points |
| `V32-DEC-015` | Reported threads only | `bc_moderate_chat` privileged · moderator + administrator · **50**-message window · **30** days post-decision · reads audited |

## 3. Milestone boundary

**In:** polling transport; in-app opt-outable `chat` notifications; read state and unread counts; blocking, reporting, moderation queue; subject-data export and erasure; retention sweep.

**Out, and absent rather than stubbed:** attachments (no table, no contract field, no event field, no media purpose, no placeholder), push, SMS, email, SSE, WebSocket, typing, presence, delivery receipts, group and named-staff conversations, platform-support conversations, message editing, participant-initiated deletion, production frontend, release tag, and any chat→AI context port.
