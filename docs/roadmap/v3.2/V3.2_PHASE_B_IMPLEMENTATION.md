# V3.2-B — Internal Chat Foundation: Implementation Report

**Milestone:** the externally-independent backend only. **No attachment path, external provider, push channel, realtime transport, AI integration, production frontend, or release tag was built, and none is authorized by this phase.**

**Baseline:** `649dad5f62461d21805a87a98089ed273d38b191` on `master`, verified equal to `origin/master` before any work, worktree clean apart from the untracked `start-beauclick.vbs` (unmodified, never staged).

**Decisions:** `V32-DEC-010` … `V32-DEC-015`, closed by the product owner on 2026-08-30, approving the engineering decision packet **with four corrections**. Where a correction and the packet disagree, the correction governs.

**Architecture:** ADR-031 (chat domain, immutable counterparty, proven eligibility, bounded send window) and ADR-032 (chat privacy, abuse, moderation boundary). Both committed **before** any schema or implementation code.

---

## 1. The four owner corrections, and why each matters

Engineering recommended one thing; the owner decided another in four places. Recording them precisely, because in three of the four the owner's answer is stricter than engineering's and the difference is the interesting part.

| # | Engineering proposed | Owner decided | Why the correction is right |
|---|---|---|---|
| 1 | Counterparty from the historical order snapshot, **falling back** to current `business_staff` affiliation when absent | **No fallback.** Missing snapshot fails closed | A fallback fires exactly when the data is least trustworthy, and reintroduces the mutability the snapshot exists to remove. `CheckoutService` creates booking and order in one transaction, so "no order" describes corrupt data, not a legitimate booking |
| 2 | Business inbox = "active staff member" | **Owner and active managers only** | `business_staff.role` is `manager\|staff` and nothing finer. An any-active-staff rule hands a private customer conversation to everyone a salon ever added |
| 3 | Any `cancelled` booking qualifies | **`cancelled` only with proven prior `confirmed`** from `booking_history` | `pending` is the one status a stranger can create unilaterally. `pending`→`cancelled` would have been an eligibility grant anybody could mint — V2's defect through the cancellation door |
| 4 | Retain the erased subject's prose as a **deliberate ADR-027 exception**, pending legal sign-off | **Destroy it.** ADR-027-consistent, neutral placeholder only | Takes no exception to the platform's own erasure rule, makes no anonymisation claim, and removes legal disclosure copy as a blocker on the backend milestone |

## 4. What was built

### 4.1 Schema — `chat`, seven tables

`database/migrations/chat/20260830500001_create_chat_schema.sql`.

| Table | Holds | The constraint that carries the rule |
|---|---|---|
| `chat.conversations` | One thread per customer per immutable counterparty | `UNIQUE (customer_user_id, counterparty_type, counterparty_id)` — many bookings collapse into one thread. `UNIQUE (id, customer_user_id)` exists only so children can carry a composite FK and cannot be re-parented |
| `chat.conversation_participants` | The read watermark, per participant | `last_read_sequence` moves forward only, so a replayed or reordered mark-read cannot un-read |
| `chat.messages` | The prose, and only here | `UNIQUE (conversation_id, sequence)` makes a duplicated position unwritable · partial unique idempotency index on `(conversation_id, sender_user_id, idempotency_key)` · `ck_chat_messages_erasure_paired` makes a body without an author, or an author without a body, unrepresentable |
| `chat.blocks` | Directional blocks | `PRIMARY KEY (blocker_user_id, blocked_user_id)` — direction *is* the identity of the row, which is why only the blocker can lift it |
| `chat.reports` | The moderation record | `uq_chat_report_open_per_reporter` — one open report per reporter per conversation, enforced by a partial unique index rather than a read-then-write |
| `chat.send_counters` | Per-minute send buckets | `PRIMARY KEY (user_id, window_start)` — the row the conditional increment competes on |
| `chat.outbox_events` | The transactional outbox | Drained by the one shared `OutboxRelay`. No second engine |

**Every identity-bearing column carries an explicit `_user_id` suffix** — `customer_user_id`, `participant_user_id`, `sender_user_id`, `blocker_user_id`, `blocked_user_id`, `user_id`. There is no `message_attachments` table, no attachment column, and no soft-delete column anywhere in the schema; all three are asserted against `information_schema`, so adding one later fails a test rather than passing review.

`database/migrations/identity/20260830500002_add_chat_capabilities.sql` adds the two capabilities.

### 4.2 Routes

Participant API — `@Controller('v1/chat')`, `@RequireCapability('bc_use_chat')` **at the class**:

| Route | Purpose |
|---|---|
| `POST /api/v1/chat/conversations` | Open, or return, the thread with one of the caller's own eligible counterparties |
| `GET /api/v1/chat/conversations` | Inbox, keyset-paginated, both sides in one list |
| `GET /api/v1/chat/conversations/:id` | One thread summary, with a freshly computed `canSend` |
| `GET /api/v1/chat/conversations/:id/messages` | Messages, keyset by `sequence` |
| `POST /api/v1/chat/conversations/:id/messages` | Send. Re-proves eligibility inside the transaction |
| `POST /api/v1/chat/conversations/:id/read` | Move the watermark forward |
| `GET /api/v1/chat/unread-count` | The server's own unread total |
| `POST` / `DELETE /api/v1/chat/conversations/:id/block` | Block, unblock |
| `POST /api/v1/chat/conversations/:id/report` | Report, anchored to a specific message |

Moderation API — `@Controller('v1/admin/chat/reports')`, `@RequireCapability('bc_moderate_chat')`:

| Route | Purpose |
|---|---|
| `GET /api/v1/admin/chat/reports` | The queue. Reports only, never conversations |
| `GET /api/v1/admin/chat/reports/:id` | The report and its bounded window. `@AuditAction('chat.report.read')` |
| `POST /api/v1/admin/chat/reports/:id/decide` | Uphold or dismiss. `@AuditAction('chat.report.decided')` |

**No route accepts a caller-controlled customer, sender, participant, professional, business, owner, or counterparty identity.** `POST /conversations` carries a counterparty type and id, and that is not an exception: the service resolves the pair among the caller's **own** eligible relationships, so a forged value is simply not found and produces the same refusal as a professional the caller has never booked.

### 4.3 Contract package

`@beauclick/chat-contract` — zero runtime dependencies, browser-safe. Closed vocabularies (`CHAT_COUNTERPARTY_TYPES`, seven `CHAT_REPORT_REASONS`, `CHAT_REPORT_STATUSES`, `CHAT_MODERATION_ACTIONS`, `CHAT_CLOSED_REASONS`, `CHAT_REFUSAL_REASONS`, `CHAT_SIDES`), every numeric limit (`CHAT_MAX_MESSAGE_CHARACTERS = 2000`, `CHAT_MAX_MESSAGES_PER_MINUTE = 20`, `CHAT_MAX_MESSAGES_PER_DAY = 300`, `CHAT_MAX_REPORTS_PER_DAY = 5`, `CHAT_MAX_REPORT_NOTE_CHARACTERS = 500`, `CHAT_SEND_WINDOW_DAYS = 90`, `CHAT_RETENTION_MONTHS = 24`, `CHAT_MODERATOR_WINDOW_MESSAGES = 50`, `CHAT_MODERATOR_POST_DECISION_DAYS = 30`), `chatTextLength` (NFC-normalised code points, so the server counts what the browser's character counter counts), and the view types. **It has no attachment surface of any kind.**

### 4.4 Events

`ConversationStarted` v1 and `MessageSent` v1, registered in the existing catalog, produced by `chat`, drained by the existing relay.

`MessageSent` carries `conversationId`, `messageId`, `senderUserId`, `recipientUserId`, `sequence`, `bodyLength`, `occurredAt`. **`bodyLength` is a count, and it is the field somebody would eventually try to widen into a preview — the schema is what stops that happening quietly.** Neither event has a body, an excerpt, a report note, or an attachment field. A business-side message emits one event per authorized recipient, resolved at emit time, so each notification is separately idempotent.

### 4.5 Capabilities

- `bc_use_chat` — `customer`, `professional`, and `business`. The `business` grant is load-bearing: without it a salon **owner** is refused at the capability guard before membership is ever consulted.
- `bc_moderate_chat` — in `PRIVILEGED_CAPABILITIES`, held by `moderator` and `administrator`. **Not `platform_operator`.** Because it is privileged, `libs/audit`'s boot-time check refuses to start the application if either gated mutation loses its `@AuditAction`.

## 5. The four proofs

### 5.1 `pending` → `cancelled` never enables chat

Eligibility is an `INNER JOIN` from `booking.bookings` to `commerce.orders`, and a `cancelled` booking must additionally satisfy

```sql
EXISTS (SELECT 1 FROM booking.booking_history h
         WHERE h.booking_id = b.id AND h.to_status = 'confirmed')
```

against the append-only history. A booking cancelled straight from `pending` has no such row and contributes nothing — and `pending` is the one status a stranger can create unilaterally, which is exactly why a `status`-only rule would have been an eligibility grant anybody could mint.

Two tests hold this: the natural path, and one that constructs a `cancelled` booking whose row is **byte-identical** to an eligible one and differs only in its history. The second is the case a status-only rule passes.

### 5.2 The historical counterparty never moves

The counterparty is `(seller_party_type, seller_party_id)` read from the booking's `commerce.orders` snapshot, recorded on the conversation at creation, and never rewritten. **There is no fallback to current `business_staff` affiliation** (owner correction 1): a qualifying booking whose order is missing fails closed even when the practitioner has an active salon affiliation that would have "worked".

Four tests: a professional joining a salon after the fact, the same professional leaving one, an order whose snapshot disagrees with the booking's own `professional_id` (the snapshot wins), and the missing-order case with an active affiliation deliberately present.

### 5.3 Business inbox access

Business-side access is **the business owner, and members whose `business_staff.role = 'manager'` with an active membership** — nothing wider. An ordinary active staff member is refused **including when they are the booked practitioner**, because `business_staff.role` distinguishes only `manager` from `staff`, and an any-active-staff rule would hand a private customer conversation to everyone a salon has ever added. A manager whose membership goes inactive loses access on their next request, because access is evaluated per request and never cached on the conversation row.

### 5.4 Erasure destroys the subject's prose

`ChatSubjectDataContract.eraseSubjectData` sets `body = NULL, sender_user_id = NULL, erased_at = <stamp>` in one statement, so a row can never exist with one gone and the other present — which `ck_chat_messages_erasure_paired` would refuse anyway. What remains is a structural placeholder carrying **no original body, no excerpt, no searchable text, no preserved length, and nothing reconstructable**. Blocks in both directions and the send counters are deleted. A filed report survives with the reporter tombstoned («کاربر حذف‌شده») and the note destroyed, because a privileged decision must stay attributable after the subject of a complaint closes their account. The counterparty's own messages are untouched, and their thread stays readable and correctly ordered.

**No anonymisation claim is made anywhere in the module**, and that is the practical benefit of owner correction 4: no subject-authored prose is retained, so there is nothing whose identifiability would ever have to be argued.

## 6. Moderation and audit boundaries

Entry is **by report id only**. A moderator sees at most a **50-message window centred on the reported message**, may act while the report is open and for **30 days after the decision**, and gets nothing else: no conversation browsing, no user search, no message search, no arbitrary conversation-id access, no sending, no impersonation, no editing, and no deletion of a participant's message.

**Reading the window is itself audited** — `chat.report.read` is recorded, not only `chat.report.decided` — so a moderator who opens a thread and does nothing still leaves a record.

Deciding is a compare-and-swap on `status = 'open'`: two moderators deciding at once produce one decision, and the loser is told the report is gone rather than silently overwriting a colleague's verdict.

Upheld actions are exactly three: warn the sender, close the conversation for sending, restrict the sender platform-wide.

## 8. Bugs found during implementation

Four, none of which review caught, and each of which failed as something other than itself.

**1. Business chat was unreachable.** `bc_use_chat` was withheld from the `business` role on the reasoning that business-side access is membership rather than a role. The reasoning is right and the conclusion was wrong: the capability gates the **action**, and *which* conversations is a separate per-request question. Withholding it narrowed nothing — the capability guard runs before any membership check, so a salon **owner** was refused at the door. The test that caught it is the one that asserts an owner can read their own business inbox.

**2. Connection-pool exhaustion, presenting as a hang.** The eligibility and seller-access ports opened their own connections while the caller's send transaction already held one, so N concurrent sends needed 2N connections against a pool of 10. Past five senders, every request waited on a connection only another waiting request could free. **The suite did not fail — it stopped**, with no error and no timeout, which is the most expensive shape a bug can take. Every port method now takes the caller's `EntityManager`.

**3. `UPDATE … RETURNING` never reported zero rows.** TypeORM's postgres driver returns `[rows, rowCount]` for `UPDATE` and `DELETE` **including** when the statement carries `RETURNING`, so `result.length` is always 2. `decide`'s compare-and-swap on `status = 'open'` could therefore never observe its own loss, and **a second moderator silently overwrote the first moderator's verdict**; separately, every erasure reported a fabricated `anonymized` count. `INSERT … ON CONFLICT DO UPDATE … RETURNING` is unaffected, which is why the send throttle and the AI quota were always correct — and why the defect was invisible by analogy to code that looked identical.

**4. The container could not resolve the new packages.** `tsconfig.runtime.json` carried no path mapping for `@beauclick/chat` or `@beauclick/chat-contract`, so the image would have failed at **startup** rather than at build.

A fifth was a test defect rather than a product one, and is recorded because the fix is a permanent property of the harness: the throttle tests were flaky roughly one run in twenty because `chat.send_counters` buckets by wall-clock UTC minute and a twenty-send burst can straddle `:59 → :00`. The bucketing is correct — a rolling window would make one row the hottest in the schema and serialise every sender against every other. `FreezableChatClock` removes the coin flip without weakening what is proved.

## 10. What was deliberately not added

No frontend. No attachment path of any kind. No external provider. No push, SMS, email, SSE, or WebSocket channel. No AI summarisation, AI reply assistance, or chat→AI context port — asserted by two tests, one that no such port exists and one that no chat message reaches the `ai` schema. No release tag.
