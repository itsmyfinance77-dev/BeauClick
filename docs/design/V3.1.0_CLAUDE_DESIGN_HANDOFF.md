# V3.1.0 — Claude Design Handoff

**Baseline:** tag `v3.1.0`, commit `7196041556fb0fb857c1dd97172e80b3cebddbbc`.
**Produced by:** engineering preparation audit, 2026-08-28. No product code was changed.
**Status of this document:** the sole design input for the V3.1 design pass.

## How to read this document

Everything below was read out of the `v3.1.0` tree or measured against a running build of
it. Where a claim was verified in a real browser it says so; where it is static analysis it
says so. Nothing here is aspirational, and nothing describes a screen, feature, or visual
language that does not exist in this codebase today.

**The only inputs to this design pass are this document and the `v3.1.0` source tree.** No
other document in this repository is an input to it, and none should be read as one. If a
capability is not listed in §4 or §14 below, the backend cannot supply it — see §13.

Three words are used precisely throughout:

- **IMPLEMENTABLE** — the API returns this today; design against it freely.
- **BACKEND GAP** — the product behaviour is understood but no API can supply the data.
- **PRODUCT DECISION REQUIRED** — nobody has decided what this should do.

## 1. Current product UI map

One Next.js 14 App Router application, `v3/apps/web`, Persian-only, RTL. There is no second
app, no admin app, no marketing site. Three route groups share one shell, one design system,
one auth implementation:

```
AppShell  (header + main, all routes)
│
├─ Public                /  /search  /providers  /providers/[id]
│                        /auth  /checkout/result  /sandbox-gateway
│
├─ Customer (session)    /dashboard  /bookings  /journey  /loyalty
│                        /notifications  /waitlist  /business
│
├─ /pro      ProtectedRoute → ProProvider → ProShell
│                        /pro  /pro/bookings  /pro/availability  /pro/services
│                        /pro/finance  /pro/analytics  /pro/profile
│
└─ /admin    ProtectedRoute → AdminGuard → AdminShell
                             /admin  /admin/verification  /admin/users
                             /admin/audit-log  /admin/settlements
                             /admin/notifications  /admin/search
                             /admin/loyalty  /admin/phone-conflicts
```

**30 page routes, 3 layouts.** `/pro` and `/admin` are route groups inside the same app, not
separate applications.

Mode switching is visual, not structural: `ContextBand` renders a coloured band at the top of
`/pro` (primary) and `/admin` (warning) carrying the mode badge, who you are acting as,
context status, the mode's own nav, and a mandatory exit link back to customer view.

### Guard model — read this before designing any signed-in state

`ProtectedRoute`, `ProGuard`, and `AdminGuard` are **UX guards, not security boundaries.**
Real authorization is server-side on every request (`JwtAuthGuard`, `OwnershipGuard`,
`CapabilityGuard`, the last re-reading role assignments from the database so a revoked
operator is refused even holding a valid token). A user who defeats a client guard sees empty
screens and 403s, never data.

Design consequence: guards exist to *explain*, not to protect. Their empty states are real
product copy and are worth designing. `AdminGuard` currently renders an `EmptyState` with a
message and one link for each of: loading, unauthenticated, and lacking-capability.

## 3. Current design system

### 3.1 What exists

Two files, ~20 exports total.

`components/ui.tsx` — `Button` (primary/ghost/danger, `loading`, `inline`), `Input`,
`Alert` (error/success), `Card`, `ErrorState`, `LoadingState`.

`components/kit.tsx` — `TextLink`, `PageHeader`, `EmptyState`, `Badge` (neutral/success/
warning/error/primary), `Select`, `Textarea`, `ConfirmDialog`, `NavLink`, `ContextBand`,
`SegmentedControl`, `StatGrid`, `StatCard`.

Shells: `AppShell`, `ProShell`, `AdminShell`. Guards: `ProtectedRoute`, `ProGuard`,
`AdminGuard`. Plus `ErrorBoundary`.

The kit is disciplined: every export has at least two real call sites, and each replaced two
or more hand-written implementations that had already drifted. `ConfirmDialog` is genuinely
well built — focus trap wrapping both directions, focus restore on close, Escape, `aria-modal`,
`aria-labelledby`, and a backdrop-click guard that ignores a drag that started inside the panel.

### 3.2 What does not exist

No `Rating`, `Avatar`, `Tabs`, `Table`, `Pagination`, `Toast`, `Tooltip`, `Skeleton`,
`Modal` (other than `ConfirmDialog`), `Drawer`, `Breadcrumb`, `Stepper`, `Chip`, `Switch`,
`Checkbox`, `Radio`, `DatePicker`, `TimePicker`, `FileUpload`, or image component.

**Zero images. Zero SVG. Zero icons. Zero emoji.** Verified by search across `app/` and
`components/`: `<img>` 0, `next/image` 0, `<svg>` 0. There is no `public/` directory. The
entire product is text, colour, borders, and spacing.

### 3.3 The styling architecture — the single most important fact for this pass

| | |
|---|---|
| CSS files | **1** (`app/globals.css`, 96 lines) |
| `className=` usages | **2** (both the skip link) |
| Inline `style={{ }}` objects | **524** |
| Width-based `@media` queries | **0** |

There is no CSS architecture. Every visual decision in the product lives in a TSX inline
style object. `globals.css` sets box-sizing, body font/background/colour, heading margins,
link colour, one `:focus-visible` rule, the visually-hidden/skip-link pair, and a
`prefers-reduced-motion` block. Nothing else.

Two consequences the design pass must plan around:

1. **Inline styles cannot express media queries, `:hover`, `:active`, or pseudo-elements.**
   Any design that needs a different layout at a breakpoint, or a hover treatment, has **no
   mechanism to express it today.** Introducing one is a Claude Code decision that must
   happen before or alongside implementation.
2. **A visual change touches TSX, not a stylesheet.** There is no theme layer to swap.

### 3.4 Tokens

`packages/design-tokens/src/tokens.json` is the declared source; `tokens.css` emits the CSS
custom properties actually consumed. **38 tokens are defined; 27 are referenced.**

Defined and in use: 18 colours (`ink`, `ink-soft`, `ink-faint`, `line`, `background`,
`surface`, `surface-tint`, `primary`, `primary-hover`, `primary-soft`, `accent`,
`accent-soft`, `success`(+soft), `warning`(+soft), `error`(+soft)), 1 gradient, 1 font family,
7 spacing values, 7 radii, 4 shadows. Colour space is `oklch` throughout.

**Gaps in the token layer itself:**

- **`tokens.json` declares a full typography scale** (`heroH1`, `pageTitle`, `sectionTitle`,
  `body`, `meta`, with mobile/desktop sizes, weights and line-heights) **and none of it is
  emitted to CSS or used anywhere.** Every font size in the product is a hardcoded number in
  an inline style. Observed values in the kit alone: 12, 13, 14, 18, 20, 22, 24.
- **`tokens.json` declares `breakpoint.mobile: 900px`** and it is emitted nowhere and used
  nowhere.
- No spacing *scale* — seven named one-off values, not a ramp.
- No z-index tokens. Observed raw values: `10` (search suggestions), `50` (dialog),
  `100` (skip link).
- No motion/duration tokens.
- **`--bc-font-family` names `Vazirmatn`, and Vazirmatn is never loaded.** No `@font-face`,
  no `next/font`, no font file, no `public/`. The product renders in the system fallback.
  Verified in a live browser.

### 3.5 Consistency findings

- **Two undefined tokens are referenced at 7 call sites** — see §5.1. Real, visible.
- **Failed-load handling is inconsistent.** `ErrorState` (message + retry) is the intended
  pattern and is enforced by test on `/notifications` and `/waitlist` only. `/search`,
  `/providers`, `/providers/[id]`, `/loyalty`, `/checkout/result`, `/bookings`,
  `/admin/users`, `/admin/settlements` surface a failed load as a bare `Alert` with **no
  retry**, leaving a dead end whose only escape is a manual reload.
- **`Card` padding is a fixed `24px` at every viewport width.** At 390px that is 48px of the
  screen spent on padding.
- **Three raw `<table>` elements** (`/admin/loyalty`, `/checkout/result`, `/pro/finance`)
  with no shared primitive. All three do carry `<caption>` and `scope` — accessible, but
  each re-decides its own visual treatment.
- **`PageHeader` hardcodes `<h1>` at 24px** with no size variants, so page titles cannot
  differ in weight between a dense admin table and a public landing screen.
- **`Button` has no size scale.** `inline` toggles padding and width only. Primary and
  secondary CTAs are identical in size, so visual hierarchy rests entirely on colour.
- **`StatGrid`'s `min` is a per-caller number** (default 180). Deliberate, and it is the one
  place a caller may still make a spacing decision.

## 5. Existing UI/UX issues

Ordered by how much they constrain design work, not by severity to a user.

### 5.1 Two undefined design tokens, 7 call sites — real and visible

Verified in a live browser at `v3.1.0`:

| Token | Referenced at | Resolves to | Visible effect |
|---|---|---|---|
| `--bc-radius-input` | `/search` ×3, `/journey` ×2 | *undefined* | `border-radius: 0px` — the search input, its suggestion dropdown and each suggestion button render **square**, while every `Input` elsewhere renders at 12px (`--bc-radius-button`) |
| `--bc-color-surface-muted` | `/search` ×1, `/loyalty` ×1 | *undefined* | `rgba(0,0,0,0)` — an element intended to have a muted background has **none** |

**Deliberately not fixed by this audit.** The intent is legible but the correct *value* is a
design decision, and changing it would alter the visual baseline in the same pass that is
about to audit it. The design system has no input-radius token and no muted-surface token;
two screens assumed both existed. **Claude Design should decide whether these tokens should
exist**, and Claude Code will then either define them or repoint the call sites.

### 5.2 `/pro/analytics` displays a metric that can never be non-zero

`recordProfileView()` is implemented in `lib/phase3-api.ts` and exported. **No page calls it.**
`POST /v1/search/providers/:id/view` therefore never fires, `search.ranking_signals.profile_views`
stays at 0 for every professional, and `/pro/analytics` renders «بازدید پروفایل ۰» permanently.
It is also summed into the funnel total.

**Do not design around profile views as live data.** Wiring the call into `/providers/[id]` is
a small Claude Code task, but whether a profile view should be recorded at all — and what
counts as one — is **PRODUCT DECISION REQUIRED**.

## 6. Open design decisions

These are the questions this design pass exists to answer. None has a right answer in the code.

1. **Does the product get a visual language beyond text and colour?** No images, icons, or
   illustrations exist and none can be uploaded (§7 backend gaps). Whether the redesign is
   typographic-and-spatial only, or assumes vector iconography that ships in the bundle, is
   the first decision and it governs everything else.
2. **Mobile navigation pattern.** Seven wrapped links is what exists. Drawer, bottom bar,
   collapsed menu, or a deliberate reduction in destinations.
3. **What is the homepage for?** Discovery entry, product explanation, or a signed-in
   dashboard that changes with session state.
4. **`/dashboard` vs `/bookings` vs `/journey` vs `/loyalty`.** Four customer surfaces, one
   of them empty. Merge, or give `/dashboard` a real job.
5. **`/providers` vs `/search`.** Keep both, or fold browse into search.
6. **Booking flow shape.** Today it is inline on the profile page. Inline, modal, or a routed
   multi-step flow — each has different state and URL consequences.
7. **Jalali date entry.** Native `date`/`time` inputs are Gregorian and cannot be localized
   or styled. A Jalali picker is a real component build (§7).
8. **Breakpoint set.** None exists. The design pass must name the widths it designs for so
   Claude Code can build the mechanism.
9. **Typography scale.** Declared in `tokens.json`, unused. Adopt it, replace it, or keep
   ad-hoc sizes.
10. **Density for money and operations screens.** `/pro/finance`, `/admin/settlements`,
    `/admin/audit-log` are table-shaped; the rest is card-shaped.
11. **Should `--bc-radius-input` and `--bc-color-surface-muted` exist?** (§5.1)
12. **Empty and first-run states.** `/pro`'s "you have no professional profile" is the only
    designed onboarding moment. Every other empty state is one sentence in a `Card`.

## 8. Accessibility considerations

Separated exactly as the audit brief requires. **No WCAG compliance claim is made.**

### 8.1 Already verified

- **Colour contrast.** All 25 rendered token pairs pass WCAG AA for normal text, worst ratio
  **4.66**, measured in a real browser by canvas readback (forcing the browser's own
  `oklch`→sRGB conversion) and independently asserted in 71 test cases computed from
  `tokens.json`. AA for **normal text only** — large-text, non-text and UI-component contrast
  were not separately assessed.
- **Touch targets.** A 44px minimum height is enforced in `Button`, `TextLink`, `NavLink`,
  `SegmentedControl`, `Input`, `Select`, `Textarea`, and asserted in tests, so a new violation
  fails CI. Verified live at 375px and 390px: every interactive element is ≥44px tall.
- **Document structure.** `<html lang="fa" dir="rtl">`, a working skip link
  (visually hidden, becomes visible on focus), `role="search"`, named `nav` landmarks.
- **Focus ring.** A 2px `:focus-visible` outline on every interactive element, defined once
  globally. Verified visible in a real browser during forward keyboard traversal.
- **Forms.** `Input`, `Select` and `Textarea` all wire `label`/`htmlFor`, `aria-invalid`,
  and `aria-describedby` for both hint and error, with errors in `role="alert"`.
- **Dialogs.** `ConfirmDialog` implements a two-directional focus trap, focus restore,
  Escape, `aria-modal`, and `aria-labelledby`.
- **Tables.** All three raw tables carry `<caption>` and `scope`.
- **Reduced motion.** `prefers-reduced-motion` is honoured globally.

### 8.2 Needs a design decision

- **Icon-only controls.** None exist today, so no icon needs a label yet. If the redesign
  introduces icons, every icon-only control needs an accessible name — decide the convention.
- **Hover-only affordances.** Inline styles cannot express `:hover`, so nothing is
  hover-dependent today. Keep it that way, or introduce a mechanism that has a focus twin.
- **Colour as sole meaning.** `NavLink` and `SegmentedControl` deliberately carry both weight
  **and** colour for the current/selected state. `Badge` tone is colour-only, with the label
  carrying the meaning. Preserve this rule in any new component.
- **Density vs target size.** Any denser table design must keep the 44px row-action baseline.

### 8.3 Needs implementation

- **`/search` combobox keyboard support.** The input declares `role="combobox"`,
  `aria-expanded`, `aria-controls`, `aria-autocomplete="list"`, and the suggestions are a
  `role="listbox"` of `role="option"` items. There is **no `onKeyDown`**: no ArrowDown/ArrowUp
  traversal, no Enter-to-select, no Escape-to-dismiss, no `aria-activedescendant`, and
  `aria-selected` is hardcoded `false` on every option. Each option additionally **contains a
  `<button>`**, which is an invalid ARIA structure — an `option` must not have interactive
  descendants. It is reachable by Tab, so it works; but it announces a contract it does not
  honour. This is the one place the codebase violates its own stated rule (`SegmentedControl`
  explicitly refuses `role="tablist"` for exactly this reason).
- **`ConfirmDialog` background isolation.** The dialog traps focus but does not mark the rest
  of the page `inert` or `aria-hidden`, so a screen-reader virtual cursor can still reach
  content behind it.
- **`ConfirmDialog` body association.** `aria-labelledby` is wired; `aria-describedby` for the
  consequence copy is not.
- **`aria-live` for async results.** Present in 3 places; search results, list refreshes and
  save confirmations elsewhere are not announced.

### 8.4 Needs real-browser verification

- **Reverse keyboard traversal (Shift+Tab)** has never been walked, in any route.
- **Forward traversal on authenticated routes** — walked on public routes only.
- **Focus management on route change** — never verified.
- **Dialog focus trap under a real screen reader** — implemented and unit-tested, never
  verified with assistive technology.

### 8.5 Needs screen-reader verification

**No screen-reader testing has ever been performed on this product.** No NVDA, JAWS, VoiceOver
or TalkBack pass exists. Every ARIA claim above is a code-level claim. Persian + RTL + screen
reader is a combination with its own failure modes and none of them have been checked.

## 9. Responsive considerations

### 9.1 How responsiveness currently works

**There are zero width-based media queries in the product.** The only `@media` block is
`prefers-reduced-motion`. Responsiveness is achieved by three mechanisms only:

1. `flexWrap: 'wrap'` — **56 occurrences.** The dominant technique. Rows become columns by
   wrapping, not by a breakpoint.
2. `clamp()` — 4 occurrences. The shell's section padding is
   `clamp(--bc-spacing-section-mobile, 4vw, --bc-spacing-section-desktop)`, measured live at
   **30.72px at 768px** and **40px at 1280px**.
3. CSS Grid `repeat(auto-fit, minmax(Npx, 1fr))` — 2 occurrences, both `StatGrid`.

Layout is a single fluid column capped at `--bc-spacing-content-max-width: 1280px`, verified
live: `main` measures exactly 1280px wide with 40px padding at a 1280px viewport.

**This means a design that requires a different *layout* at a breakpoint — not merely a
narrower one — has no mechanism to express it.** Naming the required breakpoints is part of
this design pass; building the mechanism is a Claude Code prerequisite.

### 9.2 Measured behaviour

Primary targets **390px** and **1280px**, with 375/412/768 recorded.

Live measurement, `v3.1.0` production build, public routes:

| Route | 375 | 390 | 768 | 1280 |
|---|---|---|---|---|
| `/` | — | no overflow | — | no overflow |
| `/search` | no overflow | no overflow | no overflow | no overflow, main 1280px |
| `/providers` | — | no overflow | — | — |
| `/auth` | — | no overflow | — | — |
| `/providers/[id]` | — | no overflow | — | — |

No horizontal overflow at any tested width, and the only sub-44px interactive element is the
skip link (1×1 until focused, which is correct).

Authenticated routes were measured at 375px in the preceding release QA — `dir="rtl"`,
`lang="fa"`, no horizontal overflow, all interactive elements ≥44px tall, with several header
nav links narrower than 44px **horizontally** (25–44px) while meeting the height baseline.

**Limitation, stated rather than omitted:** the development QA authentication seam is disabled
in the released runtime, so authenticated routes could not be re-measured in this pass at
390/412/768/1280. Their responsive behaviour above is **static analysis plus prior 375px
evidence**, not fresh measurement. Since no route contains a media query, behaviour is fully
determined by the flex/grid declarations, which were read.

### 9.3 Known responsive weaknesses

- **`Card` padding is fixed at 24px** at every width — 48px of a 390px screen.
- **Signed-in header nav wraps to multiple lines** on mobile with seven destinations.
- **Three `<table>` elements have no narrow-width strategy** — no horizontal scroll container,
  no card-per-row fallback.
- **`/pro/availability`'s seven native date/time inputs** size themselves by browser default
  and cannot be styled.
- **`/pro/bookings` (588 lines) and `/business` (392 lines)** are the densest screens and rely
  entirely on wrapping.

### Persian, RTL and formatting — current state

- `<html lang="fa" dir="rtl">` at the root; RTL is structural, with CSS **logical properties**
  everywhere and no LTR branching in any component.
- All formatting flows through `@beauclick/persian-utils`: `toPersianDigits` (26 call sites),
  `formatToman` (10), `zonedIsoDate`/`zonedIsoTime`, plus Jalali conversion and Persian
  weekday/month labels.
- **No raw `toLocaleDateString`, `toLocaleTimeString`, or `new Intl.*` anywhere outside that
  package** — verified. Formatting discipline is genuinely clean.
- Platform timezone is `Asia/Tehran`, applied server-side and client-side; a 14:00 Tehran slot
  stores as 10:30 UTC and reads back as ۱۴:۰۰ in Jalali with Persian digits. Verified end to
  end in a real browser.
- Numeric inputs (phone, OTP) are explicitly `direction: ltr` + centred inside the RTL
  document so digit strings do not visually reverse.
- `font-variant-numeric: tabular-nums` is set globally.

**The one RTL/Persian defect:** the seven native `<input type="date">` / `type="time">`
controls on `/pro/availability` render in the browser's own locale — **Gregorian calendar,
Latin digits, LTR** — inside a product that displays every other date as Jalali with Persian
digits. A professional types `2026-08-29` and reads back «شنبه، ۷ شهریور ۱۴۰۵». Native date
inputs cannot be localized or styled to fix this; it requires a real Jalali picker component.
