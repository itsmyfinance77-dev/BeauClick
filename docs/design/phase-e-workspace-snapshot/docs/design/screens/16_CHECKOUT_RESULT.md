# نتیجهٔ پرداخت — /checkout/result

مسیر: `/checkout/result`

## هدف
نمایش نتیجهٔ نهایی پرداخت پس از بازگشت از درگاه (واقعی یا سندباکس).

## کاربر و زمینه
بدون نیاز به ورود (لینک از درگاه).

## وابستگی API
bookingApi.getOrder

## فیلدهای واقعی داده
status (succeeded/replayed/failed/refunded/duplicate_refunded)، currency، subtotal، discountTotal، feeTotal، total، refundedTotal، paidAt، items، adjustments.

## چیدمان
بنر نتیجه بالا (رنگ بر اساس status)؛ جدول رسید با caption و scope زیر آن.

## اجزا
Alert/بنر وضعیت، Table (رسید)، Button

## حالت‌ها
بارگذاری اسکلتی؛ پنج حالت نتیجهٔ متمایز با متن جدا برای هرکدام؛ خطای بارگیری با تلاش دوباره.

## کنش‌ها
succeeded/replayed → دیدن نوبت؛ failed → تلاش دوباره در پرداخت (نیاز به تصمیم — گاف زیر)؛ refunded/duplicate_refunded → توضیح + بازگشت به داشبورد.

## قواعد واکنش‌گرایی
۳۹۰: بنر و جدول تمام‌عرض؛ ۱۲۸۰: کارت مرکز با عرض محدود.

## قواعد راست‌به‌چپ و فارسی
مبالغ فارسی و tabular-nums؛ شناسهٔ سفارش لاتین با direction:ltr.

## دسترس‌پذیری
جدول با caption و scope (امروز رعایت شده)؛ بنر نتیجه role=status.

## رفتار تعامل
ادیت کردن query string نمی‌تواند رسید را جعل کند — ارقام همیشه از سرور تازه خوانده می‌شود؛ این رفتار حفظ می‌شود.

## عناصر آینده/شکاف
دکمهٔ «تلاش دوباره» روی پرداخت ناموفق — امروز endpoint آن (initiate) هست اما هیچ صفحه آن را صدا نمی‌زند؛ طراحی دکمه IMPLEMENTABLE است، فقط اتصال کلاینت لازم دارد. تمایز متن مشتری-لغو-کرده در برابر بانک-رد-کرده — BACKEND GAP (نیاز به failureCode).

## یادداشت پیاده‌سازی
مهم‌ترین کار این صفحه، افزودن دکمهٔ تلاش دوباره روی حالت failed است — endpoint موجود، فقط سیم‌کشی کلاینت لازم است.
