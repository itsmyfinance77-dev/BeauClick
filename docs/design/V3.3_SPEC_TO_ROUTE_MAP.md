# V3.3 — the design's screen specs mapped onto the web app's routes

**Date:** 2026-09-23 · **Story:** #221 (conformance phase D, sizing) · **Baseline:** `master` at `938202d`
**Inputs:** the numbered specs under `docs/design/screens/` in the design pack — `00`–`50` with no `43`, plus the `46` amendment: **50 numbered files** — and the 33 `page.tsx` files under `v3/apps/web/app/`.

This document produces the map and the sizing. It does not rebuild anything.

## How the verdicts were reached

Two kinds of evidence, and the columns say which is which.

- **Measured** — the route was rebuilt to the design and checked in a browser (`#216`, `#222`, `#211`, `#207`/`#213`). Those are recorded in `V3.3_FRONTEND_OPEN_ITEMS.md`.
- **By presence** — the route exists and has not been rebuilt. The verdict `partial` means only: *it renders in the new tokens and inside the new shell, but its own layout is the pre-design one*. It is **not** a per-screen measurement against the drawing. Each such row carries its count of inline `style={{` objects, which is the honest size of the migration that remains (`grep -c "style={{"`).

| Verdict | Meaning |
|---|---|
| ✅ conformant | Built to the spec and measured. Server gaps, if any, are named and rendered as absence. |
| ◐ partial | The route exists; layout not yet rebuilt to the design. |
| ⬜ not built | No route exists. |
| ⛔ blocked | Cannot be built as specified until a server fact, a decision or a legal text exists. |
| ⊕ cross-cutting | Not a route: a component, a rule or a set of files. |

## What the map shows

**Counts.** Of the 50 numbered specs plus the `46` amendment (51 rows): **39 ✅** routes (was 8 when this map was written; the six customer pages of `#231`, the five professional pages of `#232`, the business, finance and five admin pages of `#233` and `#234`, the wishlist, referral, privacy and devices pages of `#235` and `#236`, the four operator queues of `#238`, and the three admin commercial screens of `#239` moved), **1 ◐** route (`46a`), **5** with no route (**2 ⬜** and **3 ⛔**), and **6 cross-cutting** (of which SEO metadata now moved to `✅` and the footer's legal routes to `◐`, both by `#240`). The issue's "46 specs onto 33 routes" was the wrong shape of question — the honest answer is *not a shortfall of routes but three different gaps*:

1. **Existing routes not yet rebuilt.** The professional panel's own layout migration (open-items §1-1) plus `MoneyChart` not yet wired into `/pro/finance`. `#219` (the inline-style migration) is now fully done, app-wide (`#277`) — the last 173 objects moved to CSS modules; 9 named, genuinely dynamic values remain, the same custom-property pattern `ProgressBar` already used.
2. **Routes that do not exist and whose backend does.** `/messages` and the AI assistant (`35`, `36`) — blocked on legal-approved consent copy, not attempted. Everything else in this category from earlier passes has moved to `✅`: the four operator queues (`#238`, reachable only by an operator holding `bc_manage_platform` until `#264` is decided) and the admin commercial family (`#239`, `40`/`44`/`47`). **Two of the gaps named here have since closed** in `#297`: the privacy queue's missing `kind` filter (`#266`) and the unreachable schedule-version id that blocked new plan drafts (`#271`). What remains of this list is `#265` (a media moderation report carries no way to show the reported image) and `#274` (the collection-policy publish dialog states a consequence the backend refuses to perform).
3. **Routes that cannot be built as drawn.** `41`, `42`, `49`. Each names its blocker in its own spec, and each blocker is already an issue (`#210`, `#212`) or a legal decision.

**One spec still describes what does not exist in code at all: `MoneyChart` on `/pro/finance`.** The four legal pages and the SEO files moved to built (`#240`) — the legal pages as a labelled, `noindex`ed placeholder pending the owner's approved text.

## Ordering

1. **`#219`'s migration is done** (`#277`) — no longer an ordering constraint for future groups.
2. **Shells before pages** — done for the customer, professional and admin shells. (The admin shell's remaining item was never a drawer — see `25`'s corrected row above; that's now closed by `#272`.)
3. **Existing routes before new ones.** A rebuilt route is a smaller, more certain change than a new screen and every one improves something a user already sees.
4. **New routes by user reach:** wishlist and referral (customer-facing, small), then account privacy and devices, then the operator queues.
5. **Never start a ⛔ row** — start the issue that unblocks it.
