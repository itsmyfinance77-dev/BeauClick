## 2. Product/UI inventory

30 page routes, 3 layouts (`AppShell`, `ProShell`, `AdminShell`), ~20 shared component exports across `ui.tsx` and `kit.tsx`. Full route table: §2 of the source audit. Full component-by-component verdict (keep / redesign / extract / new / not-built): `V3_COMPONENT_INVENTORY.md`.

Critical fact governing every visual decision: **524 inline `style={{}}` objects, 1 stylesheet (96 lines), 0 width-based media queries.** Inline styles cannot express breakpoints, `:hover`, or pseudo-elements. Any design requiring a different *layout* (not just narrower spacing) at a breakpoint has no mechanism today — naming breakpoints is design's job; building the CSS mechanism is a Claude Code prerequisite that gates every responsive decision below.

## 3. Design system decisions

Full spec: `V3_DESIGN_SYSTEM.md`. Summary of decisions:

- **Evolve, don't replace.** The existing `oklch` palette, 8px spacing scale, and shadow set are kept and completed, not swapped.
- **Density, not palette, distinguishes surfaces.** Customer / professional / business / admin share one visual language at three densities (open / medium / dense) — see §1 of the design system doc.
- **Fix the three token defects:** define `--bc-radius-input`, define `--bc-color-surface-muted`, add an `info` Alert variant. Zero risk, zero structural change — this is Phase 0 in the gap matrix's implementation map and should ship alone, first.
- **Typography:** two fonts only, Vazir (all UI/body/numerals) and Anjoman (customer-surface display headings ≥24px only). Vazir is declared as the token font-family but never actually loaded in the shipped product (§3.4 of the source audit) — loading it, or repointing the token to what actually renders, is a Phase 0 task.
- **No third font, no icon set exists in the repo today.** Open decision #1 in the source audit (§6) — whether the redesign assumes vector iconography that ships in the bundle — is answered here as: **not for V3.1.** The prototypes in this project are deliberately icon-free, using shape/weight/color for affordance, consistent with what the product can ship without a new asset pipeline decision.

## 4. Typography decisions

Scale, Persian line-height table, digit and currency formatting rules: `V3_DESIGN_SYSTEM.md` §3. Persian digits everywhere except technical hex ids; `tabular-nums` on all columnar figures; clock times in an isolated `direction: ltr` span.

## 5. Responsive decisions

Primary targets 390 and 1280, with 375/412/768 as secondary checkpoints (matches the source audit's measured set). Breakpoint behavior table: `V3_DESIGN_SYSTEM.md` §9. Mobile is not a shrunk desktop: filter columns become bottom sheets, sticky booking panels become bottom bars, weekly grids become single-day views. This requires the CSS mechanism noted in §2 above before Claude Code can build it as specified.

## 6. RTL/Persian decisions

`<html lang="fa" dir="rtl">` stays structural. CSS logical properties throughout, with the one documented exception: check/chevron glyphs that must not mirror are written with physical `border-left`/`border-bottom`, not logical properties — call this out explicitly in code review, since it looks like an RTL bug and isn't. Full rule set: `V3_DESIGN_SYSTEM.md` §10.

## 7. Accessibility decisions

No WCAG compliance claim is made — consistent with the source audit's own caution. Contrast, focus rings, 44px targets, and form labeling are already verified in the current build and are preserved, not redesigned. Two accessibility items are **implementation prerequisites, not polish**, and are called out per-screen in `docs/design/screens/`:

- `/search` combobox: missing keyboard support (`onKeyDown`, `aria-activedescendant`) and an invalid ARIA structure (`<button>` inside `role="option"`).
- `ConfirmDialog`: missing `inert`/`aria-hidden` background isolation and `aria-describedby` on the consequence copy.

## 14. Backend gaps (do not implement without backend work)

Consolidated from the source audit §7/§15 and `V3_UIUX_GAP_MATRIX.md`:

- Star ratings, review counts, written reviews — no domain; the `rating` field returned by search is permanently 0.
- Any image, avatar, cover photo, portfolio, or verification-evidence upload — no object storage, no upload endpoint.
- Customer name on `/pro/bookings` and `/pro` — payload has only `customerId`. **Highest-frequency gap in the product** — a professional sees it multiple times a day.
- Professional name and service name on `/bookings` and `/dashboard` — payload has only `providerId`/`serviceId`.
- `profileViews` on `/pro/analytics` — the recording call is never invoked; the field is structurally always 0.
- District, neighbourhood, province, map, or "near me" — the city record has only id/name/is_launched.
- Distinct copy for customer-cancelled vs. bank-declined payment — needs a `failureCode` contract that doesn't exist yet.
- OTP resend countdown — the cooldown is enforced server-side but its remaining time isn't exposed.
- Nearest-available-slot in search results — `listAvailability` exists but there's no bulk call for a result list.
- A persistent weekly availability pattern for bulk generation — today's bulk-create is stateless.

## 25. Sync update — payment-result design sync (V3.1 Phase F), this pass

Baseline moved to `0bb226377ed1fe4ddb2e880632c79295ce4ca13e` (CI run `33229069474`, green). Read the real implementation this time, not just the backend report: `checkout/result/page.tsx`, `ui.tsx`, `checkout-result.spec.tsx`, `payment-failure.ts`, `checkout.controller.ts`, plus `V3.1_PHASE_F_IMPLEMENTATION.md` and the Phase E handoff for cross-reference. Narrow scope by request: the payment-result screen only, `Prototype - Customer.dc.html` only.

**Contradiction found and corrected:** the live `unresolved` copy promises "به‌صورت خودکار تعیین تکلیف می‌شود" (automatically resolved) — but `V3.1_PHASE_F_IMPLEMENTATION.md` §8 states plainly that no reconciliation sweep exists for ambiguous verifications, because gateway settlement semantics are unknown. The design replaces that sentence with one that states only what's true: outcome unknown, money may or may not have moved, don't retry, check bookings, contact support if money moved without a confirmed booking. A second, milder finding on `gateway_error`: its conditional refund promise is also unsupported for a definite-failure state and was reworded to a support referral.
