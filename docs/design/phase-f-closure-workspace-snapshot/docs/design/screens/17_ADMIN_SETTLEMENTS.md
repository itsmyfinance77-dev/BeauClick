# تسویه‌ها — /admin/settlements

مسیر: `/admin/settlements`

## هدف
مهم‌ترین صفحهٔ مدیریتی از نظر پیامد — انتقال واقعی پول بین پلتفرم و متخصص.

## کاربر و زمینه
نیاز به bc_manage_platform.

## وابستگی API
platformTotals، partySummary، partyOutstandingOrders، createSettlement

## فیلدهای واقعی داده
جمع پلتفرم، خلاصهٔ هر طرف، سفارش‌های معوقِ هر طرف.

## چیدمان
جدول طرف‌ها با جمع بدهی؛ پنل ساخت تسویه با فهرست سفارش‌های انتخاب‌شده.

## اجزا
Table، Button (تأکید بیشتر از سایر دکمه‌های مدیریتی — این صفحه پول حرکت می‌دهد)، ConfirmDialog

## حالت‌ها
بارگذاری اسکلتی جدول؛ خالی: «بدهی معوقی نیست»؛ خطا — امروز بدون تلاش دوباره، باید ErrorState بگیرد.

## کنش‌ها
ساخت تسویه پشت ConfirmDialog با خلاصهٔ مبلغ و طرف.

## قواعد واکنش‌گرایی
۱۲۸۰ اصلی است؛ ۳۹۰ ثانویه با جدول به‌صورت کارت.

## قواعد راست‌به‌چپ و فارسی
ارقام فارسی tabular-nums.

## دسترس‌پذیری
ConfirmDialog این صفحه باید aria-describedby روی خلاصهٔ مبلغ داشته باشد — خطای برگشت‌ناپذیر گران است.

## رفتار تعامل
وزن بصری این صفحه باید از سایر صفحات فقط-خوانای مدیریت بیشتر باشد (طبق تصمیم سند وضعیت — دستهٔ P1، نه P2).

## عناصر آینده/شکاف
برگشت تسویه (settlement reversal) در API هست بدون UI — سطح آزاد طراحی برای نسخهٔ بعد.

## یادداشت پیاده‌سازی
بدون تلاش دوباره روی خطای بار — این صفحه یکی از هشت صفحه‌ای است که باید روی ErrorState برود (فاز ۱ سند سیستم طراحی).
