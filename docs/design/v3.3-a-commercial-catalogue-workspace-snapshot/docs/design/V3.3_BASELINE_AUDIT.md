## 2. Contradictions found — reported, not resolved

### C-1 — Design workspace is 50 commits stale; the documented admin route count is wrong
`40_ADMIN_COMMERCIAL_CATALOGUE.md` §1 and `MANIFEST.md` state 18 administrator routes. The merged
controller declares **27**. Not a repository defect — a design-artifact defect. Correcting it is
inside this pass's scope.

### C-2 — The brief's eleven personas do not exist in the authorization model, and four of them have no representation at all
`ROLES` is exactly `['customer', 'professional', 'business', 'moderator', 'platform_operator', 'administrator']`.

| Brief persona | Real representation | Authority actually held |
|---|---|---|
| customer | `customer` role | book, view own orders, chat, AI |
| independent beauty professional | `professional` role | own profile/services/availability/finance/subscription/collection policy |
| salon owner/manager | `business` role — **owner only** | as above, plus `bc_manage_business_staff` |
| salon staff professional | `business_staff` membership | **nothing financial or commercial** |
| reception or scoped staff member | `business.staff_role_grants`, and `SCOPED_STAFF_ROLES` is exactly `['practitioner_chat']` | **chat scope only.** No booking, calendar, resource, location or finance scope exists |
| multi-location business manager | **does not exist.** Locations, resources and service resource requirements are `@ResolveOwner` owner-only; an *active manager* receives the same `NOT_FOUND_OR_NOT_YOURS` as a stranger | none |
| retail seller | **does not exist** in V3.3 code | — |
| B2B seller | **does not exist** in V3.3 code | — |
| finance/support operator | **does not exist.** `platform_operator` holds only `bc_manage_platform` | — |
| dispute-resolution operator | **does not exist.** No dispute capability, table, service or route anywhere | — |
| platform administrator | `administrator` | `bc_manage_platform`, `bc_manage_commercial_plans`, moderation |

**Design consequence, applied and not worked around:** all eleven personas appear in the design
model, but the six with no merged authority are rendered as *declared personas in an explicit
unauthorized / not-yet-granted state*, never as screens implying access. No screen grants a staff
member, manager, operator or dispute handler an authority the code does not give them.

### C-3 — Phase 3's cancellation, retention, no-show, dispute-deadline and policy-acceptance disclosure cannot be implemented, and the blocker is legal, not technical
`BookingCommercialTermsV1` requires six values owned elsewhere:
`cancellationCutoffMinutesBeforeStart`, `lateCancellationRetainBasisPointsOfDeposit`,
`noShowRetainBasisPointsOfDeposit`, `rescheduleDepositAction`, `disputeWindowMinutes` (**#42,
`gate:legal`**) and `settlementDelayMinutes` (**#43, `gate:external`**). It also requires a
non-empty `customerPolicyCopyVersion`, **and no approved Persian copy exists anywhere in the
repository**. `#41d-1` therefore shipped a deliberately *narrower* `BookingCollectionTermsV1`
carrying mode, deposit rule, calculation base and contract version — and nothing else.

`commerce.order_payment_schedules.policy_accepted_at` is **NULL for every row by construction**;
`V33-DEC-029` Ruling 3 keeps it null and neither #104 nor #115 writes it.

**Design consequence:** the pre-confirmation disclosure block is designed as a complete component
with every required line present, and the six unavailable lines plus the policy-version/acceptance
control are rendered in an explicit `منتشرنشده — در انتظار تأیید حقوقی` state. No cutoff, no
retention percentage, no grace period, no dispute window and no acceptance checkbox text is
invented.

### C-4 — The dispute domain does not exist
No dispute capability, entity, migration, service, controller or event was found. Phase 3.5
(objection, evidence upload, held amount, review, decision, one-level appeal, evidence retention)
is therefore **specification and placeholder states only**, with evidence categories and retention
copy marked `LEGAL/PRIVACY REVIEW REQUIRED`. Nothing in the prototypes implies a working dispute
route.

### C-5 — An implemented contract contradicts a ratified decision, and it is still live in code
`V33-DEC-028` Ruling 1 forbids any commercial number surviving as a code constant, fallback, seed
or environment variable, and Ruling 2 names this exact case: a commission-bearing ledger write must
**fail closed** until a versioned commission policy is published.

The merged code still contains `FinancialConfig.DEFAULT_COMMISSION_RATE_BP = 1500`, still reads
`FINANCIAL_COMMISSION_RATE_BP`, and `ledger.service.ts` still stamps `commissionRateBp` from it on
every commission and reversal write.

This is the one case the brief's constraint names explicitly. **It is reported, not designed
around.** The repository already records it as a verified contradiction assigned to **#43**
(`gate:external`, re-estimated 13 → 21 SP). Consequences enforced in this pass:

- no commission rate, percentage or amount appears in any screen, including 15% or 1500 bp;
- the seller settlement view shows the amount families as states, never a computed commission;
- no screen describes any amount as platform revenue or seller earnings.

### C-6 — A seller can assign a collection policy and it changes no booking (HISTORICAL — superseded by §0-a)
Publication (`#41d-1`) and seller assignment (`#41d-2a`/#104) are merged. **Order resolution
(`#41d-2b`/#115, 8 SP) is `status:proposed` and unmerged.** Every `commerce.order_payment_schedules`
row today reads `full_payment_online`, `platformCollectibleToman === serviceTotalToman`,
`venueBalanceToman === 0`, `policyKey NULL`, `policyVersion NULL`.

So the three collection modes exist in the contract, the schema, the admin publication plane and
the seller assignment plane — and **not** in any order. The customer-side three-amount display is
real on the *receipt* (`checkout/result`) and absent from the pre-confirmation flow.

**Design consequence:** the seller assignment screen states plainly that an assignment governs
future bookings only once order resolution ships, and the customer deposit/venue-balance checkout
is marked `CONTRACT EXISTS — UI PENDING #115`, not `IMPLEMENTED`.

### C-7 — Booking-credit enforcement is structurally complete and globally inert (HISTORICAL — superseded by §0-a)
`#58a` enforces selectively: only for a party holding a positive grant. The seeded `D-7` plan
version confers **zero** credits, every existing seller sits on it, and zero means *absence of
entitlement*, never unlimited. `#95` (`#58b-1`, the control foundation — rollout state, monotonic
per-party governance fact, aggregate-only non-mutating preview, platform-wide kill switch, named
privileged sub-resource under `v1/admin/commercial`) was ratified **today, 2026-09-11**
(`V33-DEC-036`) with `ADR-050` committed, and **no line of it is implemented**. `#141` (`#58b-2`,
global activation) is proposed.

**Design consequence:** the admin rollout/entitlement/kill-switch/preview screens the brief's
Phase 5 asks for are designed against `ADR-050`'s ratified rulings and labelled
`RATIFIED — NOT IMPLEMENTED (#95, #141)`. The preview is aggregate-only with no seller-identifying
data, because R6 authorises no per-seller operator reference.

### C-8 — The primary decision DOCX was not readable
`E:\BeauClick\output\BeauClick-Final-Decision-List.docx` is on a local drive this workspace cannot
reach and was not attached. Its stated shape — 15 fixed decisions and 25 pending questions — could
not be verified, and one likely tension must be flagged rather than resolved: the repository states
that **#46 closed as a *structural* decision with every launch value explicitly `OPEN /
UNPUBLISHED`**, so any DOCX item presenting a price, allowance, percentage, cutoff, commission,
settlement delay or legal wording as "قطعی" would contradict the register. The register wins by the
brief's own ordering, and no such value was adopted from any source in this pass.

## 5. What this pass will and will not change

**Will:** correct the stale admin route count; add the V3.3 commercial, subscription, credit,
collection-policy, location/resource and settlement surfaces to the seller and admin prototypes as
configurable structures with labelled sample values; add the customer collection-mode disclosure
and payment/refund state families; design every unavailable state explicitly; produce the
requirement-to-screen, component/state, decision-status and backend-support matrices and the
frontend story list.

**Will not:** choose any open value; publish, default or hardcode any price, allowance, percentage,
cutoff, grace, threshold, commission, settlement delay or reserve; write legal or policy copy;
imply any persona holds authority the merged code does not grant; describe a retained amount as
non-refundable, a penalty or a statutory charge; change production code, schema, migrations, issues,
decision statuses, tags, releases or deployments; activate a payment provider.
