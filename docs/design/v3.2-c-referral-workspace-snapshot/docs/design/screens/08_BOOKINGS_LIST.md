# رزروهای من — /bookings

مسیر: `/bookings`

## هدف
مشاهده و مدیریت نوبت‌های پیش‌رو و گذشتهٔ مشتری؛ لغو نوبت.

## کاربر و زمینه
نیاز به ورود.

## وابستگی API
GET /v1/me/bookings، POST cancelBooking، GET /v1/me/reviews (فاز D، برای تشخیص نوبتِ قابل‌نظردهی)، POST /v1/bookings/:id/review

## فیلدهای واقعی داده
id، status، startAt، endAt، professionalId، serviceId، rescheduleCount، cancellationReason.

## چیدمان
SegmentedControl پیش‌رو/گذشته؛ فهرست BookingCard عمودی؛ روی هر نوبتِ برگهٔ گذشته با status=completed دکمهٔ «ثبت نظر» (یا نشانِ «نظر ثبت شد» وقتی bookingId آن در GET /v1/me/reviews موجود است).

## اجزا
SegmentedControl، BookingCard، ConfirmDialog، EmptyState، ReviewComposer (Rating + Textarea اختیاری)

## حالت‌ها
بارگذاری اسکلتی؛ خالی هر برگه جدا («نوبتی ثبت نشده» + دکمهٔ جست‌وجو)؛ خطا با تلاش دوباره.

## کنش‌ها
لغو نوبت پشت ConfirmDialog با متن پیامد و دلیل اختیاری. ثبت نظر → گفت‌وگوی ستارهٔ اجباری + متن اختیاری (حداکثر ۲۰۰۰ نویسه) → یک‌بار برای همیشه، بدون امکان ویرایش بعدی؛ ستارهٔ تنها بدون متن باید فرم ناقص جلوه نکند.

## قواعد واکنش‌گرایی
۳۹۰: کارت تمام‌عرض تک‌ستونه؛ ۱۲۸۰: دو‌ستونه یا فهرست باریک‌تر با حداکثر عرض محتوا.

## قواعد راست‌به‌چپ و فارسی
تاریخ جلالی فارسی؛ ساعت LTR در span جدا.

## دسترس‌پذیری
دکمهٔ لغو حداقل ۴۴px؛ aria-describedby روی متن پیامد گفت‌وگو.

## رفتار تعامل
صفحهٔ کامل می‌ماند و به‌عنوان بخش نوبت‌ها در /dashboard هم پیوند می‌خورد — هیچ مسیری حذف نمی‌شود.

## عناصر آینده/شکاف
نام متخصص و خدمت روی کارت — BACKEND GAP (فقط providerId/serviceId در پاسخ). ثبت نظر روی نوبت تکمیل‌شده — دیگر شکاف نیست، IMPLEMENTABLE NOW (فاز D)؛ تشخیص «قابل نظردهی» سرور-طرف نیست — کلاینت باید فهرست نوبت را با GET /v1/me/reviews جمع بزند (نوبتِ completed که bookingId آن در فهرست نظرها نیست)، یک درخواستِ اضافه در هر صفحه نه در هر نوبت. خطای ۴۰۹ REVIEW_NOT_ELIGIBLE یک پیام واحد برای «تکمیل‌نشده/متعلق به دیگری/ناموجود» است — پیام دقیق‌تر نباید ساخته شود.

## یادداشت پیاده‌سازی
BookingCard باید طوری طراحی شود که فیلد نام را بپذیرد وقتی سرور آن را اضافه کرد، بدون تغییر چیدمان.
